Section 1 of 8

1. Parallelism

Before getting into any one technique, here is the map: what the axes are, what each costs, and how they relate.

Parallelization is a technique for handling several things at the same time, and it is one of the most important techniques in large-scale modeling. In machine learning it is mainly used to parallelize computation across multiple devices in order to improve speed or memory efficiency.

Note — there are two different reasons to parallelize, and confusing them causes bad design choices

The stock description of parallelism — "improve speed or memory efficiency" — quietly contains both goals. They are not the same, and the right strategy depends entirely on which one is binding.

Throughput problem Capacity problem
Symptom Training works, but an epoch takes too long CUDA out of memory — training doesn't start at all
Cause Too much data Model state too large for one device
Fix Data parallelism (replicate the model, split the batch) Model parallelism (split the model) or sharding (ZeRO/FSDP)
Scaling limit Statistical — beyond some batch size, more data per step stops helping Physical — you need enough aggregate memory, period
Communication cost Once per step Many times per step (TP) or per stage (PP)

Rule of thumb: reach for data parallelism first, because it's the cheapest form of communication you can buy. Only introduce model parallelism when memory forces you to. Every other axis exists because someone hit a wall that data parallelism couldn't get them over.

Note — the three resources you can exhaust

Parallelism is always a trade among these:

   COMPUTE          MEMORY            BANDWIDTH
   (FLOPs)          (bytes on device) (bytes/sec between devices)
      │                  │                    │
      │  more devices    │  more devices      │  more devices
      │  → more FLOPs    │  → more capacity   │  → MORE traffic
      ▼                  ▼                    ▼
   scales well       scales well        gets WORSE

Two of the three get better as you add GPUs. The third gets worse. That asymmetry is the entire subject: every parallelism strategy is a scheme for buying compute and memory with bandwidth, and the strategies differ in how efficiently they make that trade.

Note — strong vs weak scaling

Borrowed from HPC, and useful for setting expectations:

  • Strong scaling: fixed total work, more devices → is it faster? Limited by Amdahl's law — the serial fraction and the communication you added become the floor.
  • Weak scaling: work per device fixed, more devices → does time per step stay flat? This is what data-parallel training actually does, and it's the more achievable goal.

When someone says "we got 90% scaling efficiency at 1,024 GPUs," they almost always mean weak scaling. Reported as MFU (Model FLOPs Utilization) — achieved FLOPs ÷ theoretical peak — which for well-tuned large-model training typically lands somewhere in the 35–55% range on modern hardware. It is essentially never close to 100%, and the gap is mostly communication and pipeline bubbles.

2. Data Parallelism

Data parallelism is a method for speeding up training when the number of data items is large, by processing the data in parallel. It works by replicating the model onto every device and feeding different data to each device. This lets you feed in a batch size that is larger by a factor of the number of devices. However, this kind of data parallelism is only possible when a single model can fit entirely onto a single device.

                  ┌──────────────── one global batch ────────────────┐
                  │  shard 0    shard 1    shard 2    shard 3        │
                  └────┬──────────┬──────────┬──────────┬────────────┘
                       │          │          │          │
                  ┌────▼────┐┌────▼────┐┌────▼────┐┌────▼────┐
                  │  GPU 0  ││  GPU 1  ││  GPU 2  ││  GPU 3  │
                  │ ┌─────┐ ││ ┌─────┐ ││ ┌─────┐ ││ ┌─────┐ │
                  │ │FULL │ ││ │FULL │ ││ │FULL │ ││ │FULL │ │   ← identical
                  │ │MODEL│ ││ │MODEL│ ││ │MODEL│ ││ │MODEL│ │     replicas
                  │ └─────┘ ││ └─────┘ ││ └─────┘ ││ └─────┘ │
                  └────┬────┘└────┬────┘└────┬────┘└────┬────┘
                       │  ∇L₀     │  ∇L₁     │  ∇L₂     │  ∇L₃
                       └──────────┴────┬─────┴──────────┘
                                       │
                            all_reduce(SUM) / world_size
                                       │
                       ┌──────────┬────┴─────┬──────────┐
                       ▼          ▼          ▼          ▼
                   identical gradient → identical optimizer step
                        → replicas stay bit-identical forever
Note — the invariant that makes it work

Data parallelism rests on one property: at the start of every step, all replicas hold identical weights. Maintaining it requires exactly three things:

  1. Replicas start identical (broadcast from rank 0 at construction — DDP does this for you).
  2. Every replica sees the same averaged gradient (the all_reduce).
  3. Every replica runs the same deterministic optimizer update.

Break any one and the replicas silently diverge — no error, just a model that trains worse than it should. This is why "just call .backward() on each GPU and average the weights occasionally" (sometimes proposed as a cheaper alternative) is a different algorithm with different convergence properties, not an optimization.

`DataParallel` vs `DistributedDataParallel`

PyTorch ships two implementations of data parallelism, and material that says only "data parallelism" often fails to distinguish them. nn.DataParallel was once commonly used. It should not be now.

nn.DataParallel (DP) nn.parallel.DistributedDataParallel (DDP)
Processes One, multi-threaded One per GPU
GIL contention Yes — a real bottleneck No
Model replication Re-scattered every forward pass Once, at construction
Gradient sync Gather to GPU 0, update, re-broadcast all_reduce, overlapped with backward
GPU 0 load Imbalanced (holds outputs and does the update) Balanced
Multi-node ✗ ✓
Status Deprecated in practice The baseline

Use DDP. The one-line summary of why: DP's single process must serialize everything through the GIL and reload the model onto each device every iteration, so it commonly delivers a fraction of the speedup DDP does on the same hardware.

python
model = model.to(local_rank)
model = torch.nn.parallel.DistributedDataParallel(model, device_ids=[local_rank])
Note — why DDP is faster than the diagram suggests: bucketing and overlap

The naive reading of the diagram is: compute the whole backward pass, then all-reduce all gradients, then step. That would leave the network idle during backward and the GPU idle during communication.

DDP doesn't do that. Gradients become available in reverse layer order as backward proceeds, so DDP groups them into buckets (~25 MB by default) and fires an asynchronous all_reduce for each bucket the moment it fills:

backward:  [layer N]──[layer N-1]──[layer N-2]──[layer N-3]── … ──[layer 1]
              │            │            │            │
              └─bucket 3 ──┴─ bucket 2 ─┴─ bucket 1 ─┴─ bucket 0
                    ↓            ↓            ↓            ↓
comm:            all_reduce   all_reduce   all_reduce   all_reduce   ← overlapped

Two consequences worth knowing:

  • Many small all-reduces are latency-bound, which is exactly why bucketing exists. Tuning bucket_cap_mb matters on slow interconnects.
  • This is why find_unused_parameters=True is expensive. DDP needs to know when a bucket is complete. If some parameters don't receive gradients on some steps, DDP must traverse the autograd graph every iteration to figure that out. Set it only if you truly have conditionally-used parameters, and prefer restructuring the model so you don't.
Note — what "larger batch size" actually buys you, and where it stops

You can feed a batch larger by a factor of the device count. Three refinements:

global_batch = per_device_batch × world_size × grad_accumulation_steps
  1. Learning rate must scale with it. The standard recipe (Goyal et al., 2017) is the linear scaling rule: multiply the LR by the same factor you multiplied the batch by, and add a few hundred steps of warmup to avoid blowing up early. Skipping this is the most common reason "it trained fine on 1 GPU but diverges on 8."
  2. There is a point of diminishing returns — the critical batch size. Past it, doubling the batch stops halving the number of steps needed; you're just burning FLOPs to reduce gradient noise that was already small enough. The gradient noise scale (McCandlish et al., 2018) is the standard way to estimate where that is. Critical batch size grows as the model gets better trained, which is why large runs often ramp batch size over training.
  3. Gradient accumulation is "free" data parallelism in time rather than space. If you can't afford more GPUs, run k micro-steps before stepping the optimizer. Wrap the non-final micro-steps in model.no_sync() so DDP doesn't all-reduce on every one:
python
for i, batch in enumerate(loader):
    is_last = (i + 1) % accum == 0
    ctx = contextlib.nullcontext() if is_last else model.no_sync()
    with ctx:
        loss = model(batch).loss / accum
        loss.backward()          # gradients accumulate; no all_reduce unless is_last
    if is_last:
        optimizer.step(); optimizer.zero_grad(set_to_none=True)
Note — the memory arithmetic behind that caveat

"Only possible when a single model fits on a single device" deserves numbers, because they explain everything that follows in this chapter. For mixed-precision training with Adam, per parameter:

Item Bytes / param
bf16/fp16 weights 2
bf16/fp16 gradients 2
fp32 master weights 4
Adam momentum (fp32) 4
Adam variance (fp32) 4
Total model state ~16

Plus activations, which depend on batch size, sequence length, and whether you use activation checkpointing.

16 is a recipe, not a constant — and it was often the optimistic figure

Treat 16 B/param as one point on a range that now runs from about 5 to 20. Two things set it, and neither is the tensor-core format: which optimizer you use, and what precision you store its state in.

This is the single most misread number in low-precision training. FP8 and FP4 headlines are almost entirely about GEMM throughput and activation memory, not persistent model state. DeepSeek-V3, the NVFP4 recipes and MXFP8 all still keep master weights and optimizer moments wider than the GEMM format; NVFP4-style recipes hold optimizer state in FP8/FP16/BF16 with moments accumulated higher, and keep some layers in BF16 outright for stability — NVIDIA's 12B run kept the last eight blocks in BF16, about 15% of the model. Anyone arriving from "FP4 is 4× smaller than BF16" will expect this table to shrink 4× and it will not.

RecipeWorking weightsMasterGradsOptimizer stateTotal
fp32 everything4—44 + 416
Textbook bf16 + AdamW2424 + 416
Megatron default (fp32 grad accumulation)242 + 44 + 420
bf16 moments (DeepSeek-V3 style)2422 + 212
8-bit AdamW (blockwise)2421 + 110
FP8-LM style (fp16 master, fp8 grads + m)2—11 + 2~6
Muon, fp32 momentum242412
Muon, bf16 momentum242210
Muon, 8-bit momentum, bf16 master w/ stochastic rounding2—21~5

16 was frequently optimistic, not conservative. Megatron-style fp32 gradient-accumulation buffers push the real figure to 18–20, and an EMA weight copy for checkpoint averaging adds another 2–4. Plenty of production runs were nearer 22 B/param than 16.

The floor is about 5–6, not 4. Below that you are fighting the second moment, which is the genuinely fragile piece: non-negative, heavy-tailed, and sitting in a denominator — exactly the worst profile for aggressive quantization. COAT measured Llama-2-7B optimizer memory falling from 26.2 GB to 6.4 GB with fp8 optimizer states, which is roughly the 16 → 6 move in the table.

Note — Muon halves the optimizer state, weighted by the 2-D fraction

Muon keeps only a first moment, so it allocates one buffer per parameter where AdamW allocates two. That is the lightest footprint of any optimizer in common use.

The asterisk: Muon is a hybrid. It applies Newton–Schulz orthogonalization to the momentum matrix, which requires the weight to be 2-D, so embeddings, norms, biases and the LM head fall back to AdamW. The saving is therefore weighted by the 2-D fraction — and that fraction is strongly scale-dependent:

   7B, 128K vocab, untied embeddings
     ~1B params in embed + lm_head  ->  ~15% still on AdamW
     blended moment cost  ~4.6 B/param   (not 8, not 4)

   70B
     embedding fraction below 5%    ->  close to the full 2x saving

Worth noticing because it is a rare case where the memory arithmetic gets better as you scale.

The momentum buffer also quantizes far more gracefully than Adam's second moment, precisely because there is no denominator. 8-bit Muon has been reported around 74% below full-precision Muon while staying stable under both linear and dynamic quantization, where 8-bit AdamW is typically stable only under dynamic. That asymmetry is why the Muon row bottoms out lower than the AdamW row. The honest cost: Newton–Schulz needs transient workspace for the largest weight matrix and adds roughly 1.0–1.2× per-step overhead, and the distributed implementation is more involved than AdamW's under FSDP/ZeRO. Chapter 10 §5 places it among the not-yet-settled choices.

So: plain DDP topped out around 3–4B a few years ago and tops out around 10–20B today, depending on how much optimizer-state risk you are willing to carry. That is roughly a 4× move against frontier models that grew far more than 4×. The conclusion of this section does not merely survive the arithmetic getting cheaper — it strengthens. Everything in §3 onward is a response to that gap.

Three things the per-parameter table leaves out

Activations are the term that actually moves. This is where low precision pays real memory dividends: COAT reports Llama-2-7B activation memory falling from 25.8 GB to 16.9 GB in fp8, with peak memory going from OOM to 35.6 GB on two GPUs once fp8 optimizer states are combined with it. Past 128K context, activations dominate model state even without checkpointing — so "plus activations" is not a footnote at long context, it is the budget.

MoE breaks the arithmetic. State memory scales with total parameters; FLOPs scale with active ones. DeepSeek-V3 at 671B total is ~8 TB of persistent state even at a lean 12 B/param — around 45 H100s just to hold it — while its per-token compute is that of a ~37B dense model. Kimi K2 at ~1T total is worse. Every sparse frontier model makes the "must fit on one device" caveat more absurd, not less.

Sharding is orthogonal, and it is the actual answer. ZeRO-2/3 and FSDP divide every number above by the shard count. Low precision and sharding compose; low precision alone was never going to be the answer, it just buys a slightly later crossover point. §5 is where that starts.

the caveat is no longer absolute

"Data parallelism is only possible when one model fits on one device" was true of classical data parallelism, and it is the historical motivation for model parallelism. But ZeRO / FSDP break that assumption without changing the programming model: the model is still logically replicated and the batch is still split, but the 16 bytes/param of state are sharded across the same data-parallel ranks and reassembled layer-by-layer on demand.

With FSDP, a 70B model trains across 64 GPUs using data parallelism alone — no tensor or pipeline parallelism required. This is the single biggest change in the field since 2021, and it's covered in §5.

3. Model Parallelism

Inter-layer Model ParallelismIntra-layer Model ParallelismPipeline Parallelism

If a model is so large that it cannot fit entirely onto a single device, you have to split the parameters and place them across multiple devices. Each device therefore holds a portion of the parameters. This makes it possible to handle even a large model by using several small devices, and depending on which dimension is parallelized, we can distinguish inter-layer and intra-layer model parallelism.

        The model is a stack of layers, each layer a set of tensors.
        There are two independent directions you can cut it.

                        ┌───────────────────────────┐
              layer 4   │ ███████████ │ ███████████ │
              layer 3   │ ███████████ │ ███████████ │   ← INTRA-layer cut
              ─ ─ ─ ─ ─ ┼ ─ ─ ─ ─ ─ ─ ┼ ─ ─ ─ ─ ─ ─ ┤     (split each tensor)
              layer 2   │ ███████████ │ ███████████ │
              layer 1   │ ███████████ │ ███████████ │
                        └───────────────────────────┘
                              ▲
                              │ INTER-layer cut
                                (split the stack)
Note — the two cuts are orthogonal, which is why you can use both at once

Inter-layer splits depth; intra-layer splits width. They compose without conflicting, and combining them is exactly what "3-D parallelism" means in §4. Keep the distinction crisp:

Inter-layer (→ pipeline) Intra-layer (→ tensor)
Unit of splitting Whole layers Individual weight matrices
Communication Activations, at stage boundaries Partial sums, inside every layer
Frequency Once per stage per microbatch ~4 collectives per transformer layer per step
Volume per event Small (one activation tensor) Small, but constant × huge count
Tolerates slow links ✓ (works across nodes) ✗ (needs NVLink; keep inside a node)
Main inefficiency Pipeline bubble (idle devices) Communication overhead + can't overlap easily
Canonical system GPipe, PipeDream Megatron-LM

Inter-layer Model Parallelism

Inter-layer model parallelism is a parallelization scheme that splits the model along layer boundaries. As shown below, layers 1, 2, 3 can be assigned to GPU 1 and layers 4, 5 to GPU 2. Google's GPipe is a representative example.

        ┌──────── GPU 1 ────────┐   ┌──────── GPU 2 ────────┐
  x ──▶ │ layer1 → layer2 → l3  │ ──▶ │ layer4 → layer5     │ ──▶ ŷ
        └───────────────────────┘   └───────────────────────┘
                                ▲
                        activations cross here
                        via send/recv  (P2P)
Note — this is the easiest form of model parallelism to implement and the worst-performing if you stop here

Splitting a nn.Sequential across devices is almost trivial, which is why it's often someone's first attempt. But note what the diagram implies about time: GPU 2 cannot start until GPU 1 finishes, and GPU 1 has nothing to do while GPU 2 works. With p stages you are using 1/p of your hardware. The pipeline section below addresses this directly — inter-layer parallelism is best understood as the naive version that pipelining fixes.

Note — a second, subtler cost: it splits parameters but not activations well

Each stage stores the activations it needs for its own backward pass. With a naive schedule and one large batch, the first stage holds activations for the entire batch across all its layers. Activation memory is often the actual constraint in transformer training, so a scheme that only addresses parameter memory solves half the problem.

Intra-layer Model Parallelism

Intra-layer model parallelism is a scheme that splits the tensors themselves, independently of layers. For example, if there is a parameter of size [256, 256], it can be split into [128, 256] or [256, 128]. NVIDIA's Megatron-LM is a representative example.

              A single weight matrix, split two ways
              ─────────────────────────────────────

    column-parallel                       row-parallel
    (split output dim)                    (split input dim)

    ┌─────────┬─────────┐                ┌───────────────────┐
    │         │         │                │      A_row0       │  → GPU 0
    │  A_col0 │  A_col1 │                ├───────────────────┤
    │         │         │                │      A_row1       │  → GPU 1
    └─────────┴─────────┘                └───────────────────┘
       GPU 0     GPU 1

    Y = X·A   →  [Y0 | Y1]               Y = X·A  →  Y0 + Y1
    no comm in forward                    all_reduce in forward
Note — how Megatron actually splits a transformer block, and why the pairing matters

The trick is to chain a column-parallel layer into a row-parallel layer so that only one collective is needed per block, not two.

Take the MLP: Z = GeLU(X·A)·B.

  1. Split A column-wise: A = [A₀ | A₁]. Each rank computes Y_i = GeLU(X·A_i). GeLU is elementwise, so this is exact — no communication needed, and this is precisely why the split must be column-wise here (a row-wise split would require summing before the nonlinearity).
  2. Split B row-wise to match: B = [B₀ ; B₁]. Each rank computes Z_i = Y_i·B_i, and the true result is Z = Z₀ + Z₁ → one all_reduce.
   X ──┬──▶ [A₀] ──▶ GeLU ──▶ [B₀] ──┐
       │                              ├──▶ all_reduce ──▶ Z
       └──▶ [A₁] ──▶ GeLU ──▶ [B₁] ──┘
       ↑                              ↑
       f (identity fwd,               g (all_reduce fwd,
          all_reduce bwd)                identity bwd)

Attention is split the same way: each rank owns a subset of the attention heads (Q/K/V projections column-parallel), and the output projection is row-parallel. Heads are independent, so this is clean.

Note — the f/g operators are the autograd pairing from chapter 03

That chapter's _ScatterToModelParallelRegion snippet, with forward=_split and backward=_gather, is one of these. Megatron defines four:

Operator Forward Backward
f identity all_reduce
g all_reduce identity
scatter split gather
gather gather split

Communication operations come in adjoint pairs because gradients flow backward through the same data movement. Once you accept that, tensor parallelism reduces to: pick a split for each weight matrix, then insert whichever f/g pair makes the math close.

Note — the cost, and why TP must stay inside a node

Per transformer layer, per step: 2 all-reduces forward (one for attention, one for MLP) + 2 backward = 4. For a 40-layer model that's 160 all-reduces per step, each on a tensor of size batch × seq_len × hidden.

Compare to data parallelism: one all-reduce per step, on the gradients.

   DP  : 1 collective / step,   volume ≈ 2 × model size
   TP  : 4 collectives / layer / step,  volume ≈ 2 × activation size, ×L layers

That's a difference of two or three orders of magnitude in frequency, and it's unavoidable — these all-reduces sit on the critical path and can't be overlapped with computation the way DDP's gradient reduction can (the next layer literally needs the result).

The practical consequence, and it is close to a hard rule: keep the tensor-parallel group within a single node, over NVLink.

Approximate per-GPU bandwidths (hardware dependent, order of magnitude only):

Link Rough bandwidth Use for
NVLink / NVSwitch (intra-node) hundreds of GB/s Tensor parallelism
PCIe (intra-node, no NVLink) tens of GB/s Marginal for TP
InfiniBand (inter-node, per NIC) ~25–50 GB/s Pipeline, data parallelism
Ethernet often less Data parallelism only

This single fact — TP is bandwidth-hungry and therefore node-local — is what determines the layout of every large training job, and it's the punchline of §4. It also caps TP degree at the number of GPUs per node (typically 8).

Note — two details that bite people
  • Vocabulary-parallel embeddings. The embedding table and output projection are enormous for large vocabularies (e.g. 128k × 8192). Megatron splits them along the vocabulary dimension; each rank looks up only the token IDs in its range and masks the rest, then all-reduces. The output side is usually fused with cross-entropy so the full [batch, seq, vocab] logit tensor is never materialized — that tensor alone can be tens of GB.
  • Dropout and LayerNorm are replicated, not split, in vanilla TP — every rank computes them redundantly on the full activation. This wastes both compute and memory, and it's exactly the redundancy that sequence parallelism was invented to remove (§6).

Pipeline Parallelism

Pipeline parallelism is a model-parallel technique that improves on the shortcoming of inter-layer model parallelism. When you perform inter-layer model parallelism, an ordering of GPU computation is necessarily created. For example, if layers 1, 2, 3 have not run, layers 4, 5 cannot run, so GPU 2 must wait until GPU 1's computation is finished.

   Naive inter-layer execution — one big batch, 4 stages

   time ──────────────────────────────────────────────────────────▶
   GPU0  ███████                                         ███████
   GPU1         ███████                           ███████
   GPU2                ███████             ███████
   GPU3                       ███████ ███████
         └── forward ────────────────┘└──── backward ────────────┘

         ███ = working      (blank) = IDLE

   Utilization ≈ 1/4.  Three quarters of your cluster is doing nothing.

This is very inefficient. Even though there are several GPUs, in practice only one GPU can be used at a time. To solve this problem, pipeline parallelism pipelines the computation process in parallel as shown below.

   Pipelined execution — the batch is split into m microbatches

   time ─────────────────────────────────────────────────────────────▶
   GPU0  F1 F2 F3 F4                         B4 B3 B2 B1
   GPU1     F1 F2 F3 F4                   B4 B3 B2 B1
   GPU2        F1 F2 F3 F4             B4 B3 B2 B1
   GPU3           F1 F2 F3 F4       B4 B3 B2 B1
         └ fill ┘                             └ drain ┘
            ▲                                     ▲
            └────────── "bubble" (idle) ──────────┘

   Fk = forward on microbatch k     Bk = backward on microbatch k
Note — the one idea: split the batch, not just the model

The batch of size B is divided into m microbatches of size B/m. As soon as GPU 0 finishes microbatch 1 it hands it to GPU 1 and immediately starts microbatch 2. The stages fill up like an assembly line. Nothing about the model changed — only the scheduling of work through it.

Note — the bubble, quantified

This is the one formula worth memorizing from this chapter.

With p stages and m microbatches, the pipeline takes m + p − 1 time slots instead of the ideal m:

bubble fraction = (p−1) / (m+p−1) · equivalently · overhead vs. ideal = (p−1) / m

Fraction of total time spent idle, for p = 4 and p = 8:

microbatches m p = 4 p = 8
1 75% 88%
4 43% 64%
8 27% 47%
16 16% 30%
32 9% 18%
64 4.5% 10%
128 2.3% 5.2%

Read off the design rule: you want m ≫ p.

A common target is m ≈ 4p or more. Note also that m = 1 reproduces the naive inter-layer case exactly — the naive scheme is pipelining with a single microbatch.

But m is bounded above: m microbatches of size B/m must each be large enough to keep a GPU busy (tiny matmuls waste the hardware), so you can't shrink them indefinitely. The bubble is the fundamental tax on pipeline parallelism, and the last decade of schedule research is about reducing it.

Note — the schedules, in the order they were invented

GPipe (all-forward-then-all-backward) — the diagram above. Simple, but every stage must hold the activations of all m microbatches before backward starts, so activation memory grows linearly with m, which fights the very thing you increased m to fix.

1F1B (one-forward-one-backward) — from PipeDream, now the default everywhere. Once the pipeline is full, each stage alternates: one forward, one backward. Same bubble fraction, but the number of in-flight microbatches per stage is capped at p instead of m:

   1F1B, p=4, m=8   (steady state alternates F and B)

   GPU0  F1 F2 F3 F4 B1 F5 B2 F6 B3 F7 B4 F8 B5 B6 B7 B8
   GPU1     F1 F2 F3 B1 F4 B2 F5 B3 F6 B4 F7 B5 F8 B6 B7 B8
   GPU2        F1 F2 B1 F3 B2 F4 B3 F5 B4 F6 B5 F7 B6 F8 B7 B8
   GPU3           F1 B1 F2 B2 F3 B3 F4 B4 F5 B5 F6 B6 F7 B7 F8 B8
                     ▲
                     backward starts as early as possible
                     → activations freed sooner → memory ∝ p, not m

Activation memory independent of m is the whole point. It's what lets you raise m enough to shrink the bubble.

Interleaved 1F1B (virtual stages) — assign each device v non-contiguous chunks of layers instead of one contiguous block (device 0 gets layers 1–2 and 9–10, etc.). Bubble becomes (p−1)/(v·m+p−1), so v = 2 roughly halves it. Cost: v× more P2P communication events. Megatron's default for large runs.

Zero-bubble / DualPipe — exploits the fact that a backward pass is really two computations, gradient-w.r.t.-input (needed immediately by the previous stage) and gradient-w.r.t.-weights (needed only before the optimizer step). Deferring the latter fills the bubble with useful work and can bring it near zero.

the PyTorch API

In 2021 pipeline parallelism in PyTorch meant torch.distributed.pipeline.sync.Pipe (RPC-based) or a third-party library (DeepSpeed, Megatron, FairScale). That module is gone. The current API is torch.distributed.pipelining:

python
from torch.distributed.pipelining import pipeline, SplitPoint, ScheduleGPipe

# 1. Declare where to cut the model into stages
pipe = pipeline(
    module=model,
    mb_args=(example_microbatch,),
    split_spec={"layers.4": SplitPoint.BEGINNING},
)

# 2. Materialize this rank's stage
stage = pipe.build_stage(stage_index=rank, device=device)

# 3. Attach a schedule and run
schedule = ScheduleGPipe(stage, n_microbatches=8)
if rank == 0:
    schedule.step(x)                  # first stage feeds input
elif rank == world_size - 1:
    output = schedule.step(target=y)  # last stage computes loss
else:
    schedule.step()

Available schedules: ScheduleGPipe, Schedule1F1B, ScheduleInterleaved1F1B, ScheduleLoopedBFS, ScheduleInterleavedZeroBubble, ScheduleZBVZeroBubble, ScheduleDualPipeV. Start with ScheduleGPipe to get it working, then switch to Schedule1F1B for memory, then interleaved for throughput.

Note — pipeline parallelism is where chapter 03's P2P section pays off

Stage boundaries are send/recv of activations forward and activation-gradients backward. Three things carry over directly:

  • recv needs a pre-allocated buffer of the correct shape — it doesn't infer shape. Pipeline implementations either fix shapes by construction or exchange shape metadata first. This is why variable sequence lengths are awkward under pipelining.
  • Use batch_isend_irecv, not paired blocking send/recv. Every stage wanting to send downstream and receive upstream simultaneously is the textbook deadlock.
  • P2P over NCCL is fine on modern PyTorch. The chapter-03 comment that "NCCL doesn't support send/recv" was true in 2021 and is not now — which matters enormously here, since pipelining over GLOO would be crippling.
Note — practical gotchas that surprise people
  • Load balancing is on you. The slowest stage sets the pace. Splitting a transformer into equal layer counts isn't equal time: the first stage carries the embedding, the last carries the LM head and loss. Balance by measured time, not layer count.
  • BatchNorm breaks under microbatching (statistics computed over B/m samples). LayerNorm/RMSNorm are fine — one reason transformers pipeline so much more comfortably than CNNs.
  • The loss is computed only on the last stage, so logging and metrics need to be gathered or handled rank-conditionally.
  • Pipeline + activation checkpointing interact. Both trade compute for activation memory; applying both blindly can recompute more than necessary.

4. Multi-dimensional Parallelism

The various parallelization techniques mentioned above can also be applied several at a time, and the number of dimensions increases with the number of parallelization schemes applied. You can perform n-dimensional parallelization in various ways, as below.

  • e.g. 2-D parallelism: data parallelism + inter-layer parallelism
  • e.g. 2-D parallelism: data parallelism + intra-layer parallelism
  • e.g. 3-D parallelism: data parallelism + intra-layer parallelism + pipeline parallelism
        3-D parallelism on 32 GPUs:  TP=4  ×  PP=4  ×  DP=2

        ┌─────────────── data-parallel replica 0 ───────────────┐
        │  pipeline stage 0   stage 1   stage 2   stage 3       │
        │  ┌───────────┐  ┌───────────┐  ┌───────────┐  ┌─────┐ │
        │  │g0 g1 g2 g3│→ │g4 g5 g6 g7│→ │g8 …      │→ │…    │ │
        │  └───────────┘  └───────────┘  └───────────┘  └─────┘ │
        │   └─ tensor-parallel group (all_reduce inside) ─┘     │
        └───────────────────────────────────────────────────────┘
                              ▲
                              │ gradient all_reduce across replicas
                              ▼
        ┌─────────────── data-parallel replica 1 ───────────────┐
        │  … same structure, ranks 16–31 …                      │
        └───────────────────────────────────────────────────────┘

This kind of multi-dimensional parallelism is the most highly regarded approach in large-scale modeling these days. Besides the methods mentioned above there are additional techniques such as ZeRO, but we'll explain those in detail in a later chapter.

Note — the modern axis list

The classic taxonomy names three axes. Six are now in common use, and a large training run may use four or five simultaneously.

Axis Splits Primitive Typical degree Placement
DP — data The batch all_reduce 2 – thousands Outermost, across nodes
FSDP/ZeRO — shard Model state, across the DP ranks all_gather + reduce_scatter = DP degree Layered onto DP
TP — tensor (intra-layer) Weight matrices all_reduce 2 – 8 Inside a node
PP — pipeline (inter-layer) Layers send/recv 2 – 64 Across nodes
CP/SP — context/sequence The sequence dim all_gather/reduce_scatter or all_to_all 1 – 8 Usually with TP
EP — expert MoE experts all_to_all 8 – 64 Across nodes
Note — a worked layout, with the rank arithmetic

64 GPUs = 8 nodes × 8 GPUs. Choose TP=8, PP=4, DP=2 (note 8 × 4 × 2 = 64).

                 world_size = 64

  node0 [g0 … g7]  ──┐
  node1 [g8 … g15] ──┤  replica 0:  4 pipeline stages,
  node2 [g16… g23] ──┤              each stage = 1 node = 1 TP group of 8
  node3 [g24… g31] ──┘
  node4 [g32… g39] ──┐
  node5 [g40… g47] ──┤  replica 1:  same structure
  node6 [g48… g55] ──┤
  node7 [g56… g63] ──┘

  TP groups (8 ranks, node-local, NVLink):   {0..7} {8..15} … {56..63}
  PP groups (4 ranks, one per stage):        {0,8,16,24} {1,9,17,25} …
  DP groups (2 ranks, same stage+tp slot):   {0,32} {1,33} {2,34} …

With TP innermost, DP middle, PP outermost, the mapping is:

python
global_rank = (pp_rank * dp_size + dp_rank) * tp_size + tp_rank

Every collective names its group, and each collective touches only the ranks it should. That is all "3-D parallelism" is, mechanically — three overlapping sets of process groups created with new_group, each rank belonging to one group per axis.

Recall from chapter 03: new_group is a collective call. Every rank must call it, in the same order, with the same arguments — including ranks that won't be members. Building a 3-D layout means many new_group calls, so this is the single most likely place to introduce a silent hang.

Note — the ordering is not arbitrary; it's dictated by bandwidth

Assign the chattiest axis to the fastest link:

   communication volume per step (roughly)
   ───────────────────────────────────────
   TP   ████████████████████████  many collectives per layer  → NVLink   (node-local)
   CP   ████████████              per attention block          → NVLink
   PP   ███                       one activation per boundary  → InfiniBand
   DP   ██                        one gradient reduction       → InfiniBand

Getting this backwards — a TP group spanning nodes — is one of the most common and most catastrophic misconfigurations in multi-node training. The job runs and produces correct numbers; it's just several times slower than it should be, with no error to point at. If a multi-node job is inexplicably slow, check the TP group placement first.

Note — you don't hand-compute these groups any more: DeviceMesh
Note

In 2021 everyone wrote their own rank arithmetic (Megatron's mpu module is exactly this). PyTorch now provides DeviceMesh — an n-dimensional, named view of your ranks that creates the process groups for you:

python
from torch.distributed.device_mesh import init_device_mesh

# shape must multiply to world_size; order = outermost → innermost
mesh = init_device_mesh("cuda", (2, 4, 8), mesh_dim_names=("dp", "pp", "tp"))

tp_group = mesh["tp"].get_group()      # this rank's 8-way TP group
dp_mesh  = mesh["dp"]                  # pass to FSDP / fully_shard

Combined with DTensor (a tensor that knows how it's sharded across a mesh), you annotate what is sharded and PyTorch inserts the collectives. PyTorch's torchtitan repository composes 4-D parallelism this way, and it's the clearest place to see the ideas in this chapter as running code.

Note — a rough budgeting procedure

Given a model and a cluster, in this order:

  1. TP degree — smallest value that makes one pipeline stage fit in memory, capped at GPUs-per-node (usually 8). Prefer smaller; TP has the worst communication profile.
  2. PP degree — enough additional stages to fit the rest of the model. Prefer smaller; the bubble is pure waste.
  3. DP degree — whatever GPUs remain (world / (TP × PP)). Free scaling, mostly.
  4. Microbatches m — as large as you can while keeping per-microbatch work meaningful. Target m ≥ 4p.
  5. FSDP/ZeRO stage on the DP axis — reclaim memory without touching the other axes.
  6. Activation checkpointing — the last lever; trades ~33% extra compute for a large activation-memory reduction.

Sanity check that TP × PP × DP (× CP × EP) = world_size exactly. Mismatches here produce confusing hangs rather than clean errors.

Section 5 of 8

5. ZeRO and FSDP

The stagesWhy ZeRO-2 is nearly freeZeRO/FSDP vs. tensor parallelism

ZeRO was once a footnote to the three classic axes. It became the default, so it belongs in the overview.

The observation ZeRO starts from: in plain data parallelism, every replica stores an identical copy of all 16 bytes/param of model state. Across N GPUs that's N redundant copies. But at any given moment, a rank only needs the parameters of the layer it is currently computing.

So: shard the state across the data-parallel ranks, and reconstruct each layer just in time.

   Plain DDP (N=4)                     ZeRO-3 / FSDP (N=4)
   ┌────┬────┬────┬────┐               ┌────┬────┬────┬────┐
   │ALL │ALL │ALL │ALL │               │ 1/4│ 1/4│ 1/4│ 1/4│  ← each rank holds a shard
   │ 16Ψ│ 16Ψ│ 16Ψ│ 16Ψ│               │ 4Ψ │ 4Ψ │ 4Ψ │ 4Ψ │
   └────┴────┴────┴────┘               └────┴────┴────┴────┘
   4× redundancy                       no redundancy
                                          │
                                          ▼  before layer k's forward:
                                       all_gather(layer k's params)
                                       compute, then FREE them again

The stages

Let Ψ = number of parameters, N = data-parallel world size.

Stage Shards Memory / GPU Comm vs. DDP
DDP baseline nothing 16Ψ 1×
ZeRO-1 optimizer states 4Ψ + 12Ψ/N 1×
ZeRO-2 + gradients 2Ψ + 14Ψ/N 1×
ZeRO-3 / FSDP + parameters 16Ψ/N ~1.5×

For a 7B model (16Ψ = 112 GB) on 8 GPUs:

Memory per GPU Fits in 80 GB?
DDP 112 GB ✗
ZeRO-1 28 + 10.5 = 38.5 GB ✓
ZeRO-2 14 + 12.25 = 26.3 GB ✓
ZeRO-3 14 GB ✓ with lots of room for activations

The 1/N in stage 3 is the important part: memory per GPU falls as you add GPUs, so there is no model size that's out of reach given enough devices. That is qualitatively different from DDP, where adding GPUs doesn't help capacity at all.

Why ZeRO-2 is nearly free

From chapter 03's cost model: all_reduce = reduce_scatter + all_gather, and it moves exactly twice what either half moves alone. Plain DDP all-reduces gradients. ZeRO-2 needs only the shard of the gradient matching its optimizer shard — so it does a reduce_scatter instead, then all_gathers the updated parameters after the step. Same total volume, less memory. That's the whole trick, and it's why ZeRO-1 and ZeRO-2 are essentially strict improvements over DDP.

ZeRO-3 costs extra because parameters must be gathered in both the forward and backward pass — roughly 1.5× DDP's communication. Usually worth it, and much of it can be prefetched and overlapped with compute.

ZeRO/FSDP vs. tensor parallelism

They solve the same problem — "parameters don't fit" — in very different ways, and the difference determines when to use which:

FSDP / ZeRO-3 Tensor parallelism
What's split Parameters, temporarily (regathered to use) Parameters, permanently (never regathered)
Math changes? No — the layer computes normally on full weights Yes — each rank computes a partial result
Model code changes? Essentially none Every layer must be rewritten as column/row-parallel
Communication all_gather per layer, prefetchable all_reduce per layer, on the critical path
Tolerates slow links Better (can overlap) Poorly
Reduces activation memory No Yes

Rule of thumb: try FSDP first — it's far less invasive. Add tensor parallelism when activations, not parameters, are the binding constraint, or when the per-layer all_gather can no longer be hidden behind compute.

the PyTorch API
  • FairScale FSDP → upstreamed into PyTorch as torch.distributed.fsdp.FullyShardedDataParallel ("FSDP1")
  • Now superseded by fully_shard ("FSDP2"), which is DTensor-based, composes cleanly with the other axes, and shards per-parameter rather than per-flat-buffer:
python
from torch.distributed.fsdp import fully_shard

for layer in model.layers:
    fully_shard(layer, mesh=mesh["dp"])   # shard each block
fully_shard(model, mesh=mesh["dp"])       # then the root

DeepSpeed remains a fine choice and is where ZeRO originated; the concepts are identical and the stage numbers mean the same thing.

Section 6 of 8

6. The newer axes — sequence, context, and expert parallelism

Sequence parallelism (the memory-saving companion to TP)Context parallelism (making long contexts possible at all)Expert parallelism (MoE)

Two axes that barely existed when the classic three-axis taxonomy was fixed are now routine. Both exist because the shape of the problem changed: contexts got much longer, and models got sparse.

Sequence parallelism (the memory-saving companion to TP)

📝 Note — these two axes have a chapter of their own

Sequence and context parallelism split the same dimension and share almost the same name, for reasons that are historical rather than logical. Chapter 11 separates them properly: the naming history, the one test that distinguishes them, ring attention, and the causal load-balance trap. The summaries below are enough to place them on the map.

Recall the gotcha from §3: under vanilla tensor parallelism, LayerNorm and dropout are replicated on every TP rank — each holds the full batch × seq × hidden activation. For long sequences this dominates memory.

Sequence parallelism splits those regions along the sequence dimension, so no activation is ever fully replicated:

   vanilla TP:      [ LayerNorm replicated ] → [ attention/MLP split ] → [ LayerNorm replicated ]
                          ▲ full activation on every rank

   TP + SP:         [ LN sharded by seq ] → all_gather → [ split ] → reduce_scatter → [ LN sharded ]
                          ▲ 1/tp of the activation per rank

The clever part: the all_reduce that TP already needed is replaced by all_gather + reduce_scatter. Same total communication volume (from the cost model: one all-reduce = one of each), strictly less memory. Effectively free. It's on by default in Megatron-style implementations.

Context parallelism (making long contexts possible at all)

Attention memory and compute scale with sequence length, so 128k-token contexts need the sequence split across devices for the attention computation itself. Two main approaches:

  • Ring Attention — each rank holds a contiguous chunk of the sequence; K/V blocks circulate around a ring of devices while each rank accumulates its partial attention. Communication overlaps with the attention compute.
  • DeepSpeed-Ulysses — all_to_all to switch the sharding axis: shard by sequence outside attention, transpose to shard by attention head inside it, transpose back. Exactly the distributed-transpose use of all_to_all from chapter 03.

Expert parallelism (MoE)

In a Mixture-of-Experts layer, each token is routed to a small number of experts (often 1 or 2) out of many. Experts are placed on different devices, so tokens must travel to wherever their expert lives — and come back:

   before:  each GPU holds tokens 0..k        (sharded by token)
              │  route: token → expert id
              ▼
            all_to_all  ──────────────────▶   sharded by expert
              │  each GPU runs ITS experts on whatever arrived
              ▼
            all_to_all  ──────────────────▶   back to sharded by token

Two all_to_alls per MoE layer. This makes all_to_all — the collective most introductions skip — arguably the most important primitive in modern sparse models.

The characteristic difficulty is load imbalance: routing is learned, so some experts get far more tokens than others, and the slowest device gates the step. Hence capacity factors, auxiliary load-balancing losses, and token dropping.

Section 7 of 8

7. How to actually choose

A decision procedure that matches how practitioners actually reason:

                   Does the model state fit on ONE GPU?
                          │                    │
                        YES                   NO
                          │                    │
                    ┌─────▼─────┐              │
                    │    DDP    │              │
                    └───────────┘              │
                                               ▼
                        Does it fit with FSDP / ZeRO-3 across your GPUs?
                                    │                   │
                                  YES                  NO
                                    │                   │
                        ┌───────────▼──────────┐        │
                        │  FSDP (+ activation  │        │
                        │   checkpointing)     │        │
                        └──────────────────────┘        │
                                                        ▼
                                       Add TENSOR parallelism (≤ node size).
                                       Still doesn't fit, or too many nodes?
                                                        │
                                                        ▼
                                       Add PIPELINE parallelism across nodes.
                                       Long contexts? add CONTEXT parallelism.
                                       MoE? add EXPERT parallelism.

Rules of thumb worth internalizing:

Rule Why
Data parallelism first, always Cheapest communication, no model changes
TP degree ≤ GPUs per node TP over inter-node links is the classic silent killer
Keep PP degree as small as it can be The bubble is pure waste
Microbatches m ≥ 4 × pipeline stages Keeps the bubble under ~10%
Activation checkpointing before more parallelism ~33% extra compute is usually cheaper than another axis
Measure before adding an axis Every axis adds failure modes; most people over-parallelize
Profile with torch.profiler, not intuition Comm/compute overlap is impossible to reason about by eye
Note — the failure modes scale with the number of axes

Each axis is a set of process groups, and chapter 03's cardinal rule applies to each of them independently: every rank must call every collective, in the same order, with matching shapes. A 4-D job has four independent chances to violate it. Practical advice: bring the axes up one at a time, verifying loss curves match the single-GPU baseline at each step. Debugging a 4-D configuration that was never correct at 2-D is genuinely miserable.

Exercises

  1. Bubble arithmetic. You have 8 pipeline stages and a global batch of 1,024. Compute the bubble fraction for m = 8, 32, and 128. At m = 128, how large is each microbatch — and is that still big enough to keep an H100 busy? What does that tell you about the real limit on m?
  1. Choose a configuration. You have 4 nodes × 8 H100s (80 GB). Train a 30B-parameter model, mixed precision, Adam. Compute the model state, then propose a TP/PP/DP split. Justify each degree, and verify the product equals 32.
  1. Trace the collectives. For a single training step of a 32-layer transformer under TP=8, PP=4, DP=2, count every collective operation and P2P transfer that occurs. Which axis dominates the count? Does that match where you'd expect the time to go?
  1. Derive the pairing. Show why Megatron splits the first MLP weight column-wise and the second row-wise. Specifically: what goes wrong if you split the first one row-wise instead? (Hint: where does GeLU sit relative to the summation?)
  1. Implement scatter without scatter. Using only chapter 03's primitives, implement a two-stage pipeline: rank 0 runs the first half of an MLP, sends activations to rank 1, which runs the second half and sends gradients back. Use batch_isend_irecv. Then break it deliberately by using blocking send/recv on both ranks in the same order, and observe the deadlock.
  1. Measure the wrong layout. If you have multi-node access, run the same job twice — once with the TP group node-local, once with it spanning nodes — and measure step time. The gap you find is the whole argument of §4 in one number.
