1. Why distributed training needs this

Large models do not fit on one GPU. That is worth making concrete, because the numbers drive every design decision that follows.

For a model trained in mixed precision with Adam, the per-parameter memory cost is roughly:

ItemBytes per parameter
bf16 weights2
bf16 gradients2
fp32 master weights4
Adam momentum (fp32)4
Adam variance (fp32)4
Total~16

So a 7B model needs ~112 GB of state before you have stored a single activation. An 80 GB H100 cannot hold it. A 70B model needs ~1.1 TB. This is why the model must be split across devices — and once it is split, the pieces must talk to each other. That conversation is what this chapter is about.

Distributed processing = spreading a large resource across multiple machines or devices and having them cooperate.

2. Processes, ranks, and launching

Basic terminologyRunning a multi-process app1) Your code forks a function2) The launcher forks your script

Basic terminology

  • Node: one computer. "3 nodes" means 3 machines.
  • Global Rank: a process's index across the whole job. In ML, effectively the GPU's global ID.
  • Local Rank: the same index scoped to one node — the GPU ID within that machine.
  • World Size: the total number of processes.
📝 Note — the full set of identifiers, and why the distinction matters.

Picture 2 nodes with 4 GPUs each:

The single most common beginner bug in multi-node training: using RANK where LOCAL_RANK is required. On node 1, RANK=5, but there is no cuda:5 — the node only has GPUs 0–3. torch.cuda.set_device(rank) crashes or silently misbehaves. Device selection is always LOCAL_RANK. Single-node examples hide this, because there the two coincide — which is why the bug so often shows up only when a job is first scaled out.

Note also that "one process per GPU" is a convention, not a law. It just happens to be the only configuration that performs well, so effectively everyone follows it.

How to run a multi-process application

There are two broad styles:

  1. Your code is the parent, and it forks a specific function into subprocesses.
  2. The PyTorch launcher is the parent, and it forks your entire script.

1) Your code forks a function

Subprocesses start in one of two ways:

  • spawn — does not inherit the parent's resources; allocates fresh. Slow but safe.
  • fork — shares the parent's resources with the child. Fast but dangerous.
⚠️ What "dangerous" means, and why it matters for CUDA.

fork() gives the child a copy-on-write image of the parent's memory. That copy includes locks, open file descriptors, and — critically — CUDA context state that cannot be duplicated. If the parent has already touched CUDA, a forked child that tries to use it typically fails with:

Cannot re-initialize CUDA in forked subprocess.
To use CUDA with multiprocessing, you must use the 'spawn' start method

This is why every CUDA example uses spawn. The cost is that a fresh interpreter starts and re-imports your modules, so arguments must be picklable and module-level side effects run again in each child — hence the mandatory if __name__ == "__main__": guard. Without it, spawn re-executes the launching code in every child and you get infinite process recursion.

forkspawnforkserver

python
"""
multi_process.py
"""
import torch.multiprocessing as mp

# Runs concurrently in the subprocesses
def fn(rank, param1, param2):
    # `rank` is injected automatically as the FIRST positional argument.
    print(f"{param1} {param2} - rank: {rank}")

if __name__ == "__main__":
    mp.spawn(
        fn=fn,
        args=("A0", "B1"),     # everything AFTER rank
        nprocs=4,
        join=True,
        daemon=False,
    )
output
$ python multi_process.py

A0 B1 - rank: 0
A0 B1 - rank: 3
A0 B1 - rank: 2
📝 Note — the output order is scrambled, and that is the whole point.

There is no ordering guarantee between independent processes writing to a shared stdout. Get comfortable with this now: for the rest of your distributed career, log output arrives interleaved. The standard fix is to gate logging on rank:

python
if dist.get_rank() == 0:
    print(...)
📝 Note — two things about mp.spawn worth knowing.

The implicit first argument. mp.spawn always injects the process index as the first positional argument. You never pass rank yourself and you cannot reorder it. Write fn(param1, param2, rank) and you will silently get the index bound to param1.

It surfaces child exceptions; a hand-rolled loop does not. Each child gets an error queue: if it raises, the traceback is pickled back to the parent and re-raised. Roll your own mp.Process loop and a crashed child dies silently while the parent blocks in join() forever.

2) The launcher forks your script

This is what you will use for anything real. torchrun runs your whole script as N subprocesses and sets the environment variables for you.

python

hello_dist.py
"""
import os

rank       = int(os.environ["RANK"])
local_rank = int(os.environ["LOCAL_RANK"])
world_size = int(os.environ["WORLD_SIZE"])
print(f"hello world, rank={rank} local_rank={local_rank} / {world_size}")

$ torchrun --standalone --nproc_per_node=4 hello_dist.py

hello world, rank=2 local_rank=2 / 4
hello world, rank=3 local_rank=3 / 4
Why torchrun, and not torch.distributed.launch

You will meet the older python -m torch.distributed.launch in a lot of material. It is deprecated. torchrun replaces it and ships as a console script with PyTorch:

bash
# Single node, 4 GPUs
torchrun --standalone --nproc_per_node=4 train.py

# Multi-node: run on each node, changing --node_rank
torchrun \
  --nnodes=2 \
  --nproc_per_node=8 \
  --node_rank=0 \
  --rdzv_backend=c10d \
  --rdzv_endpoint=10.0.0.1:29500 \
  train.py

Three practical differences:

  1. No more --local_rank argparse argument. The old launcher passed --local_rank=N as a command-line flag, so every script carried parser.add_argument("--local_rank", type=int). torchrun sets the LOCAL_RANK environment variable instead. If you inherit old code with that argparse line, delete it.
  2. Elasticity and fault tolerance. torchrun can restart failed workers and supports a dynamic node count (--nnodes=1:4) via torch.distributed.elastic.
  3. Rendezvous. --rdzv_backend=c10d --rdzv_endpoint=host:port replaces manually setting MASTER_ADDR/MASTER_PORT. --standalone is shorthand for a single-node rendezvous on a free port. Since PyTorch 2.12, a plain torchrun --nproc_per_node=N script.py with neither flag also picks an OS-assigned free port rather than hard-coding 29500 — which stops two concurrent jobs colliding with "Address already in use".

Message passing

Message passing means several processes that do not share an address space exchange data by passing explicit messages. Process 1 sends, process 2 recvs, and no shared memory is involved. Nearly all distributed communication in large-model training is built on this model.

📝 Note — why message passing rather than shared memory.

Shared memory is faster and simpler, but it only exists within one machine. The moment your job spans two nodes connected by a network, there is no shared address space, and message passing is the only model that works. Standardizing on it means the same code runs on 1 GPU or 1,000 — only the transport underneath changes (NVLink → PCIe → InfiniBand → Ethernet).

The operation names below (scatter, gather, all_reduce, barrier) come from MPI, the 1994 HPC standard. NCCL deliberately mirrors MPI's naming, which is why the vocabulary feels like it arrived from another field — it did.

📝 Note — why NCCL is so much faster.

NCCL is not just "an implementation" — it is topology-aware. At init it discovers the actual interconnect graph (NVLink, NVSwitch, PCIe switches, InfiniBand HCAs) and builds rings or trees that maximize bandwidth over the fastest available links. On an 8-GPU NVLink node, an all-reduce may never touch the PCIe bus or host memory at all. Section 7 opens this up properly.

You can also mix: dist.init_process_group(backend="cpu:gloo,cuda:nccl"), for jobs where some collectives (object/metadata) must run on CPU. The general form is a comma-separated list of device_type:backend pairs.

Process groups

Calling init_process_group creates the default group that all processes belong to. new_group creates a subset.

📝 Note — what a process group actually buys you.

A process group is a communicator: a named subset of ranks plus its own communication channel. Two things follow:

  1. Scoped collectives. dist.all_reduce(t, group=g) only involves ranks in g. This is the mechanism behind multi-dimensional parallelism — one group per tensor-parallel slice, one per pipeline stage, one per data-parallel replica.
  2. Concurrency. Distinct groups can have distinct NCCL communicators, so a tensor-parallel all-reduce and a data-parallel all-reduce can overlap.
                    default_pg  (all 8 ranks)
       +----------------------------------------------+
       |  0    1    2    3    4    5    6    7         |
       +----------------------------------------------+
   tp groups:  [0,1]  [2,3]  [4,5]  [6,7]      <- tensor parallel
   dp groups:  [0,2,4,6]     [1,3,5,7]         <- data parallel

You will rarely build these by hand for long. DeviceMesh declares the same structure as an n-dimensional named grid and creates every group for you — the subject of chapter 09. One ordering requirement carries over from here: since PyTorch 2.11, DeviceMesh resolves its process groups at construction, so init_process_group must be called before you build the mesh.

The cardinal rule, first statement

new_group must be called by every process in the job, in the same order, with the same arguments — including ranks that will not be members of the resulting group.

It is a collective call. Skipping it on non-members is a classic silent hang. Ranks outside the member list get GroupMember.NON_GROUP_MEMBER back rather than a usable handle.

Two more things before you reach for it. Each extra group costs a real NCCL communicator, which costs GPU memory — so new_group over all ranks is pure waste; that is what the default group already is, and you can name it explicitly with group=None. And the communicator is created lazily on first use, not by new_group itself, so a mistake here often surfaces at some later collective rather than at the call site.

init_process_group has to run inside each worker, not in a parent that spawns them. With mp.spawn that means calling it in the spawned function:

python
"""
process_group_spawn.py
"""
import os
import torch
import torch.multiprocessing as mp
import torch.distributed as dist

# Runs concurrently in the subprocesses
def fn(rank, world_size):
    # rank is passed automatically; world_size is supplied by us.
    # Single node, so local_rank == rank. Bind the device BEFORE init,
    # or every rank binds to cuda:0 and the first collective hangs.
    torch.cuda.set_device(rank)
    dist.init_process_group(backend="nccl", rank=rank, world_size=world_size)

    # Actually communicate - otherwise you have not shown the setup works.
    t = torch.ones(1, device="cuda") * rank
    dist.all_reduce(t)
    print(f"rank {dist.get_rank()} of {dist.get_world_size()}: {t.item()}")

    dist.destroy_process_group()

if __name__ == "__main__":
    os.environ["MASTER_ADDR"] = "localhost"
    os.environ["MASTER_PORT"] = "29500"
    # No need to set WORLD_SIZE/RANK in the environment: we pass them to
    # init_process_group explicitly, and explicit arguments win.

    mp.spawn(fn=fn, args=(4,), nprocs=4, join=True, daemon=False)
output
$ python process_group_spawn.py
rank 2 of 4: 6.0
rank 0 of 4: 6.0
rank 3 of 4: 6.0
rank 1 of 4: 6.0
⚠️ Two mistakes this example is written to avoid.

A very common version of this snippet omits torch.cuda.set_device(rank) and adds group = dist.new_group(range(world_size)). It prints a plausible-looking ProcessGroupNCCL object per rank and appears to work — but only because it never runs a collective. Both parts are wrong:

  • Without set_device, all four ranks default to cuda:0. Nothing fails until the first real collective, which then hangs or corrupts.
  • new_group over every rank duplicates the default group. It allocates a second communicator for no benefit; pass group=None instead.

The general lesson is worth keeping: if an example creates a process group and never communicates through it, it has not demonstrated that the setup is correct. That is why the all_reduce is in the code above — it is the assertion.

Under torchrun you do not pass rank or world_size at all — they come from the environment. Here is new_group earning its keep — two subgroups, with a collective scoped to one of them:

python
"""
process_groups.py  -  torchrun --standalone --nproc_per_node=4 process_groups.py
"""
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)          # BEFORE init
dist.init_process_group("nccl")
rank, world_size = dist.get_rank(), dist.get_world_size()

# Every rank creates BOTH groups, in the same order - including the one it
# will not belong to. new_group is a collective call.
evens = dist.new_group([r for r in range(world_size) if r % 2 == 0])
odds  = dist.new_group([r for r in range(world_size) if r % 2 == 1])
my_group = evens if rank % 2 == 0 else odds

tensor = torch.ones(1, device="cuda") * rank
dist.all_reduce(tensor, group=my_group)
# evens reduce among themselves: 0 + 2 = 2
# odds  reduce among themselves: 1 + 3 = 4

print(f"rank {rank}: {tensor.item()}")
dist.destroy_process_group()
output
$ torchrun --standalone --nproc_per_node=4 process_groups.py
rank 0: 2.0
rank 2: 2.0
rank 1: 4.0
rank 3: 4.0

The all-reduce touched only half the ranks each time. That scoping is the entire mechanism behind multi-dimensional parallelism: one set of groups per axis, with every collective naming the group it belongs to.

Rendezvous

📝 Note — what "rendezvous" means and the three ways to do it.

MASTER_ADDR/MASTER_PORT are how ranks find each other. Rank 0 opens a small key-value store (TCPStore) at that address; every other rank connects and exchanges the metadata needed to build NCCL communicators. It is used only for bootstrap — the actual tensor traffic does not flow through it.

  • MASTER_ADDR must be reachable from every node — localhost only works single-node.
  • Port collisions are a real and confusing failure mode. torchrun --standalone picks a free port for you.
  • Always tear down: call dist.destroy_process_group() before exit. Skipping it leaves NCCL communicators dangling and produces warnings or hangs at shutdown.
  • Pass device_id=torch.device(f"cuda:{local_rank}") to init_process_group to make NCCL initialize eagerly rather than lazily on first collective. Init failures then surface immediately instead of much later at a confusing call site.
📝 Note — the boilerplate worth memorizing.
python
import os
import torch
import torch.distributed as dist

def setup():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)                  # BEFORE init
    dist.init_process_group(
        backend="nccl",
        device_id=torch.device(f"cuda:{local_rank}"),  # eager init, clearer errors
    )
    return local_rank, dist.get_rank(), dist.get_world_size()

def cleanup():
    dist.barrier()
    dist.destroy_process_group()

if __name__ == "__main__":
    local_rank, rank, world_size = setup()
    try:
        ...   # training
    finally:
        cleanup()

Two details that matter: call torch.cuda.set_device() before init_process_group (otherwise every rank may bind to device 0, and you get a hang or an OOM on GPU 0), and put teardown in a finally so a crashing rank does not leave the others waiting.

4. Point-to-point communication

Blocking: send / recvNon-blocking: isend / irecvWho has to participate?

P2P communication sends data from one specific process to another, with send and recv.

Blocking: send and recv

python
"""
p2p.py  -  torchrun --standalone --nproc_per_node=2 p2p.py
"""
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group("nccl")
rank = dist.get_rank()

if rank == 0:
    tensor = torch.randn(2, 2, device="cuda")
    dist.send(tensor, dst=1)
elif rank == 1:
    tensor = torch.zeros(2, 2, device="cuda")   # pre-allocated, right shape
    print(f"rank 1 before: {tensor}")
    dist.recv(tensor, src=0)
    print(f"rank 1 after: {tensor}")

dist.destroy_process_group()
📝 Note — P2P is what pipeline parallelism runs on.

Every activation handed from one pipeline stage to the next is a send/recv pair. That is why native NCCL support matters so much: doing it over GLOO would stage every activation through host memory.

⚠️ recv needs a pre-allocated tensor of exactly the right shape.

Notice rank 1 creates torch.zeros(2, 2) first. recv fills an existing buffer; it does not allocate or infer shape. If the shapes disagree between sender and receiver you get corruption or a hang, not a friendly error.

This is a live constraint in pipeline parallelism, where activation shapes vary with sequence length. Implementations either exchange shape metadata first or pad to fixed shapes by construction — which is why pipeline examples so often pad every sequence to max_length.

Non-blocking: isend and irecv

send and recv are synchronous. For non-blocking communication use isend/irecv, and wait() before touching the data.

python
if rank == 0:
    tensor = torch.randn(2, 2, device="cuda")
    request = dist.isend(tensor, dst=1)
elif rank == 1:
    tensor = torch.zeros(2, 2, device="cuda")
    request = dist.irecv(tensor, src=0)

request.wait()
📝 Note — "asynchronous" means something different on GPU than on CPU.

This is subtle and worth internalizing:

  • GLOO (CPU): wait() genuinely blocks the calling thread until the transfer completes. Straightforward.
  • NCCL (GPU): collectives are enqueued onto a CUDA stream, so the Python call returns almost immediately regardless of async_op. work.wait() does not block the CPU — it inserts a wait on the CUDA stream so subsequent kernels are ordered after the communication. The CPU races ahead.

Consequence: with NCCL the CPU can be many iterations ahead of the GPU, so when something goes wrong the Python traceback often points at a line unrelated to the real fault. Set CUDA_LAUNCH_BLOCKING=1 when debugging to force synchronous behaviour and get honest stack traces — at a large performance cost, so never leave it on.

The real payoff of async_op=True is overlapping communication with computation:

python
work = dist.all_reduce(grad_bucket, async_op=True)
compute_something_unrelated()   # GPU does useful work while the network is busy
work.wait()                     # now safe to read grad_bucket

This is exactly what DDP does under the hood: it buckets gradients and launches all-reduce for early buckets while later layers are still computing their backward pass. Chapter 05 covers it in detail.

Scaling past two ranks: who has to participate?

Both examples above are written for exactly two processes. Run either with --nproc_per_node=4 and it breaks in two places — and only one of them is the wait():

  1. An else: raise branch, if you wrote one — ranks 2 and 3 fall straight into it.
  2. request.wait() at module level — a rank that took no branch never bound request, so it dies with NameError.

Say you want only ranks 1 and 2 to exchange a tensor while ranks 0 and 3 sit the round out. The rule for wait() is not about where you put it, but about who calls it: only a rank that actually issued an operation may wait on the handle it got back. That admits two idioms — wait inside each branch, or initialise the handle to None and guard the call afterwards.

python
"""
p2p_selective.py - only ranks 1 and 2 talk; 0 and 3 sit it out.
"""
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group("nccl")     # ALL four ranks call this
rank = dist.get_rank()

SRC, DST = 1, 2
request, tensor = None, None

if rank == SRC:
    tensor = torch.randn(2, 2, device="cuda")
    request = dist.isend(tensor, dst=DST)
elif rank == DST:
    tensor = torch.zeros(2, 2, device="cuda")
    request = dist.irecv(tensor, src=SRC)
# ranks 0 and 3: nothing at all. No matching call, no barrier,
# no placeholder - and that is correct, not an omission.

if request is not None:
    request.wait()
    print(f"rank {rank}: {tensor}")
else:
    print(f"rank {rank}: not involved")

dist.destroy_process_group()        # ALL four ranks again
output
$ torchrun --standalone --nproc_per_node=4 p2p_selective.py
rank 0: not involved
rank 3: not involved
rank 1: tensor([[-0.7049,  0.8836],
        [-0.4996,  0.4550]], device='cuda:1')
rank 2: tensor([[-0.7049,  0.8836],
        [-0.4996,  0.4550]], device='cuda:2')

Hoisting the wait out of the branch is the better habit, because it leaves somewhere to put real work between issuing the operation and waiting on it — which is the entire point of isend/irecv. Waiting inside the branch collapses straight back to synchronous behaviour.

With NCCL the difference is smaller than it looks, though, for the reason given just above: wait() inserts a stream dependency rather than blocking the CPU. On GLOO, where it genuinely blocks the calling thread, placement matters a great deal.

The distinction that makes this work

Point-to-point is not a collective. Ranks 0 and 3 do nothing, and that is complete and correct — not a gap to paper over with a barrier or a no-op.

This is the exact inverse of the cardinal rule in section 9. That rule governs all_reduce, broadcast, barrier, new_group — operations every rank must enter together. send/recv bind only the two ranks named in the call.

What all four ranks do still share is init_process_group and destroy_process_group. Under the hood PyTorch builds a dedicated two-rank NCCL communicator for the (1, 2) pair, lazily, on first use; ranks 0 and 3 take no part in creating it.

⚠️ Two follow-on traps.

Do not reach for new_group([1, 2]) here. A subgroup buys you nothing for P2P and costs a communicator. And if you do have one for other reasons, note the signature carefully: dst is a global rank regardless of the group argument. The group-relative form is a separate keyword, and passing both is an error:

python
dist.isend(tensor, dst=2)                    # global rank 2
dist.isend(tensor, group=g, group_dst=1)     # rank 1 *within* g
dist.isend(tensor, group=g, dst=2)           # also fine - dst stays global
# dist.isend(tensor, dst=2, group_dst=1)     # invalid: pick one

Two pairs at once need subgroups, not tags. If you want 0↔1 and 2↔3 exchanging in the same phase, you cannot disambiguate them with the tag argument — tag is not supported by the NCCL backend. Use a separate process group per pair, or batch the operations as below.

⚠️ batch_isend_irecv prevents a classic deadlock.

If every rank in a ring does send(right) then recv(left) synchronously, and the transport buffers are full, everyone blocks on send and nobody reaches recv. Deadlock. Use:

python
ops = [
    dist.P2POp(dist.isend, send_buf, dst=(rank + 1) % world_size),
    dist.P2POp(dist.irecv, recv_buf, src=(rank - 1) % world_size),
]
for req in dist.batch_isend_irecv(ops):
    req.wait()

NCCL groups these into a single operation so ordering cannot deadlock. Pipeline-parallel implementations rely on this heavily.

5. Collective communication

Collective communication involves multiple processes. Four are fundamental — broadcast, scatter, gather, reduce — and the rest are built from them.

📝 Note — the two axes that organize all of them.

Rather than memorizing unrelated functions, note they are generated by two independent choices:

One → ManyMany → One

Data split/combinedscatterreduce

Then:

  • Prefix all- = "…and then everyone gets the result" (i.e. append a broadcast).
  • reduce-scatter = reduce, then hand each rank one slice instead of giving one rank everything.
  • all-to-all = every rank sends a distinct piece to every other rank (a distributed transpose).
  • barrier = no data, pure synchronization.

That is the entire vocabulary.

1) Broadcast

Copies data from one process to all processes in the group.

python
tensor = torch.randn(2, 2, device="cuda") if rank == 0 else torch.zeros(2, 2, device="cuda")
dist.broadcast(tensor, src=0)
# every rank now holds rank 0's values
⚠️ Broadcast is in-place, and every rank must call it.

Non-source ranks must pass a tensor of the same shape and dtype; it gets overwritten. The torch.zeros on other ranks is a buffer, not data.

Note that all ranks call dist.broadcast — the source and the destinations run the same line. Never write if rank == 0: dist.broadcast(...); that hangs. This is the cardinal rule from §3 in its simplest form.

📝 Note — where you will actually use it.

Broadcasting model weights from rank 0 at startup so all replicas begin identically. DDP does this for you at construction, which is why you can initialize the model with a different seed per rank and still end up consistent.

2) Reduce

Combines data from all processes with an operation, collecting the output on one device.

python
tensor = torch.ones(2, 2, device="cuda") * rank
dist.reduce(tensor, op=dist.ReduceOp.SUM, dst=0)
# rank 0 holds [[6,6],[6,6]]  since 0+1+2+3 = 6
📝 Note — the full ReduceOp menu.

📝 Note — what the tensor holds on non-dst ranks.

reduce is in-place: PyTorch hands the backend the same buffer as both source and destination. On rank dst that buffer comes back holding the result. What happens on every other rank is backend-specific, and PyTorch deliberately declines to promise anything — its API contract is only that "only the process with rank dst is going to receive the final result."

The two backends really do differ:

ncclUntouched — still ones(2,2) * rankncclReduce specifies that recvbuff may be NULL on every call except the root's, so it cannot be writing there

So on NCCL your own contribution really is still sitting there afterwards. Leaning on that is still a bad habit: it is a property of the backend rather than of torch.distributed, and the same code quietly changes meaning the moment you fall back to gloo to isolate a NCCL hang — exactly the moment you can least afford a second mystery.

If you need your contribution after the call, say so in the code:

python
mine = tensor.clone()                          # survives on every rank
dist.reduce(tensor, dst=0, op=dist.ReduceOp.SUM)
# `tensor` now holds the sum on rank 0, and nothing you should read elsewhere

Or reach for all_reduce instead and let every rank keep a usable result — usually the better answer if you found yourself wanting one.

⚠️ Reduce is not bitwise-deterministic.

Floating-point addition is not associative, so (a+b)+c ≠ a+(b+c) in general. NCCL may choose different reduction orders across runs depending on topology and message size. Two "identical" runs will diverge after a few thousand steps. For ordinary training this is harmless; if you need run-to-run reproducibility it is a real obstacle, requiring deterministic algorithms and a fixed communication schedule — and you will pay for it in speed.

3) Scatter

Splits a tensor and distributes the pieces.

python
output = torch.zeros(1, device="cuda")

if rank == 0:
    inputs = torch.tensor([10.0, 20.0, 30.0, 40.0], device="cuda")
    chunks = torch.split(inputs, 1)
    # torch.split returns VIEWS; NCCL needs contiguous buffers
    dist.scatter(output, scatter_list=[c.contiguous() for c in chunks], src=0)
else:
    dist.scatter(output, src=0)
# rank i receives element i
📝 Note — the rules the signature doesn't show you.

Several things about scatter are enforced at runtime rather than being conventions you could deviate from:

RuleWhat happens if you break it
scatter_list on the source rank and only thereValueError: Argument scatter_list must NOT be specified on non-source ranks, and the mirror-image error if you omit it on the source
len(scatter_list) == world_sizeValueError from ProcessGroupNCCL::scatter
every element matches the output tensor's size and dtypeValueError — this is the docs' "all Tensors in scatter_list must have the same size"
every element is contiguousnothing at all — see below

So the asymmetry in the code — source provides the list, everyone provides an output — is checked, not merely idiomatic; gather_list carries the identical pair of errors, inverted. Note also that src is a global rank regardless of the group argument, with group_src as the group-relative alternative, exactly as with send/recv. Pass neither and src defaults to global rank 0.

Contiguity is the one that bites, precisely because it is the one nobody checks. ProcessGroupNCCL::scatter validates list length, dtype and shape, then hands each element straight to ncclSend as a raw data_ptr() plus a numel() count. Strides are never consulted. A non-contiguous view therefore transmits whatever happens to sit beside it in storage — no error, wrong numbers.

Whether torch.split hands you that hazard depends entirely on which dimension you split along:

a = torch.tensor([10., 20., 30., 40.])     # 1-D
torch.split(a, 1, dim=0)[0]                # shape (1,)   stride (1,)   contiguous OK
                                           #   -> .contiguous() is a no-op

b = torch.arange(16.).reshape(4, 4)        # 2-D
torch.split(b, 1, dim=-1)[0]               # shape (4, 1) stride (4, 1) NOT contiguous
                                           #   -> would send  [0, 1, 2,  3]
                                           #      instead of  [0, 4, 8, 12]

The example above is the harmless first case, so its .contiguous() costs nothing and does nothing. Megatron's split_tensor_along_last_dim, further down this section, is the second case — which is why its source carries the terse warning "torch.split does not create contiguous tensors by default." There the call is load-bearing. Since .contiguous() returns self when the tensor already qualifies, calling it unconditionally before any collective is free insurance.

📝 Note — on NCCL there is a faster way, involving no communication at all.
python
inputs = torch.tensor([10.0, 20.0, 30.0, 40.0], device="cuda")
output = torch.split(inputs, 1)[rank].contiguous()

Every rank already has the full tensor (it was computed identically, or replicated earlier), so "scattering" is just each rank slicing out its own piece locally. Zero bytes cross the wire. When the data is already replicated, a local slice beats a real scatter every time — and this trick is everywhere in tensor-parallel code.

Megatron-LM does exactly this, wrapped in an autograd.Function so gradients flow correctly:

python
class _ScatterToModelParallelRegion(torch.autograd.Function):
    """Split the input and keep only the chunk belonging to this rank."""

    @staticmethod
    def forward(ctx, input_):
        return _split(input_)

    @staticmethod
    def backward(ctx, grad_output):
        return _gather(grad_output)
The most conceptually important idea in this chapter

Look at that forward/backward pair:

forward:  _split          backward:  _gather

Communication operations come in adjoint pairs. If the forward pass scatters, the backward must gather, because gradients flow the opposite direction through the same data movement. Megatron defines four such functions, conventionally called f and g:

ForwardBackward
_split (scatter)_gather
_gather_split
identityall_reduce
all_reduceidentity

Once you see this, tensor parallelism (chapter 07) stops being mysterious: you split a weight matrix column-wise or row-wise, and insert whichever f/g pair makes the math work out. Everything else is bookkeeping.

Note that the third row is a no-op in the forward pass whose only job is to install an all-reduce on the backward — so half of tensor parallelism's communication is invisible when you read the forward code. Since PyTorch 2.11 there are also native differentiable collectives, which give you this behaviour without writing the wrapper class yourself.

4) Gather

Collects tensors from all devices onto one.

python
inp = torch.ones(1, device="cuda") * rank

if rank == 0:
    buf = [torch.zeros(1, device="cuda") for _ in range(world_size)]
    dist.gather(inp, gather_list=buf, dst=0)
    print(buf)     # [tensor([0.]), tensor([1.]), tensor([2.]), tensor([3.])]
else:
    dist.gather(inp, dst=0)
📝 Note — the gather list is ordered by rank.

buf[i] always holds rank i's contribution. That ordering guarantee is what makes gather/all-gather useful for reassembling a sharded tensor: torch.cat(buf, dim=0) reconstructs the original. The destination must pre-allocate exactly world_size correctly-shaped tensors.

If you are ever on a backend that lacks gather, the standard fallback is all_gather — supported nearly everywhere — followed by discarding the result on non-destination ranks. More bandwidth, but it always works.

5) All-reduce

Reduce, then give the result to every device.

python
tensor = torch.ones(2, 2, device="cuda") * rank
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)
# EVERY rank now holds [[6,6],[6,6]]
The single most important operation in distributed training

Every step of data-parallel training ends with an all-reduce of gradients:

Each rank computes grad L on its own minibatch shard
        |
all_reduce(grads, op=SUM)   <- every rank now has the summed gradient
        |
divide by world_size (or use ReduceOp.AVG)
        |
Every rank applies the IDENTICAL optimizer update -> weights stay in sync

Because the update is identical everywhere, replicas never drift. That invariant — all ranks hold identical weights at the start of every step — is what data parallelism rests on, and all-reduce is what maintains it.

📝 Note — all-reduce is not implemented as reduce-then-broadcast.

The naive version would push all data through one rank, making it a bandwidth bottleneck that gets worse with scale. Real implementations use ring all-reduce = reduce_scatter followed by all_gather.

It is easy to overstate what that buys you, because two different costs scale differently and the ring only tames one of them:

N ranksRing bytes per rank 2(N-1)D/NNaive bytes at the root (N-1)DRing steps 2(N-1)

The volume each rank moves is bounded: it climbs from D at two ranks and never reaches 2D however many GPUs you add. Note the careful word — it does still vary with N; it is simply capped instead of growing with the job. What makes that worth remarking on is the column beside it, where the naive root is moving 511 tensors' worth at the same scale.

That bound is also what bandwidth-optimal means here, in the strict sense: 2(N-1)D/N is the known lower bound for all-reduce, and the ring achieves it exactly rather than merely approaching it.

The latency is another matter — 2(N-1) sequential steps, growing without limit. Total time runs roughly 2(N-1)α + 2(N-1)D/(Nβ): the second term saturates at 2D/β while the first keeps climbing, so nothing here is independent of world size in wall-clock terms. That surviving latency term is precisely why NCCL keeps trees in reserve. Section 6 derives both costs and then works through the tree tradeoff.

6) All-gather

Gather, then give the collected result to everyone.

python
buf = [torch.zeros(1, device="cuda") for _ in range(world_size)]
dist.all_gather(buf, torch.ones(1, device="cuda") * rank)
# every rank holds [0., 1., 2., 3.]
📝 Note — prefer the flat-tensor form in new code.

The list-of-tensors form requires the backend to handle world_size separate buffers. The flat variant is faster and cleaner:

python
output = torch.empty(world_size * inp.numel(), dtype=inp.dtype, device=inp.device)
dist.all_gather_single(output, inp)            # PyTorch >= 2.13
# dist.all_gather_into_tensor(output, inp)     # the 1.13 - 2.12 name
output = output.view(world_size, *inp.shape)

These have been renamed twice. They began as private _all_gather_base/_reduce_scatter_base, became public as all_gather_into_tensor/reduce_scatter_tensor in PyTorch 1.13, and were renamed again in 2.13 to all_gather_single/reduce_scatter_single to align with torchcomms. Older names still resolve for now. You will meet all three spellings in the wild.

📝 Note — where all-gather shows up.

FSDP/ZeRO-3: each rank stores only a shard of each layer's parameters, and all-gathers the full layer just before using it in forward, then frees it. This trades communication for memory — the reason a 70B model can train on GPUs that could never hold it whole. Chapter 08 covers it.

There is also all_gather_object, which pickles arbitrary Python objects. Convenient for metrics and metadata, but slow (CPU-side serialization) — never put it in your training inner loop.

7) Reduce-scatter

Reduce, then give each rank one slice of the result.

python
chunks = torch.split(torch.tensor([1, 10, 100, 1000], device="cuda") * rank, 1)
output = torch.zeros(1, dtype=torch.int64, device="cuda")
dist.reduce_scatter(output, [c.contiguous() for c in chunks], op=dist.ReduceOp.SUM)
# rank0: 6   rank1: 60   rank2: 600   rank3: 6000
📝 Note — reading the arithmetic.

Line up the inputs as a matrix, rows = ranks, columns = slices:

            slice0  slice1  slice2  slice3
  rank0        0       0       0       0
  rank1        1      10     100    1000
  rank2        2      20     200    2000
  rank3        3      30     300    3000
            ------  ------  ------  ------
  column sum:    6      60     600    6000
                 |       |       |       |
                 v       v       v       v
              rank0   rank1   rank2   rank3

Reduce-scatter sums down the columns and gives column i to rank i. Each rank ends up with 1/world_size of the reduced result — which is precisely why it is the memory-saving alternative to all-reduce.

Flat form: dist.reduce_scatter_single(out, flat_in, op=dist.ReduceOp.SUM).

📝 Note — where reduce-scatter matters.

ZeRO stage 2 and FSDP replace the gradient all-reduce with a gradient reduce-scatter: each rank keeps only the gradient slice matching its optimizer-state shard. Half the volume of the gradient all-reduce it replaces, and a 1/N reduction in gradient memory — paid back later by an all-gather of the updated parameters, so total volume matches DDP. The memory saving is what makes ZeRO-2 worth the complexity.

8) Barrier

Pure synchronization — early arrivals wait until everyone reaches the same point.

python
dist.barrier(device_ids=[local_rank])
⚠️ Pass device_ids, and do not sprinkle barriers "to be safe".

Why device_ids: on NCCL, barrier() is implemented as an all-reduce on a dummy tensor, so it must pick a device. If the current device is not what you expect, ranks can pick different devices and the barrier hangs.

Good use: letting one rank do something exclusive while others wait.

python
if rank == 0:
    download_dataset()      # only one process should do this
dist.barrier()              # everyone waits
data = load_dataset()       # now safe for all ranks

Misuse: adding barriers around collectives. Every barrier forces the fastest rank to idle until the slowest arrives, converting straggler variance into wall-clock loss. Collectives are already synchronizing — an all-reduce cannot complete until every rank participates. A barrier next to one buys nothing and costs real time.

Genuinely useful: barriers for localizing a hang. Insert them between phases and see which is the last one reached; the deadlock is between that barrier and the next.

9) All-to-all

Every rank sends a different chunk to every other rank — effectively a distributed transpose:

before:  rank0:[A0 A1 A2 A3]   rank1:[B0 B1 B2 B3]   rank2:[C0 ...]   rank3:[D0 ...]
after:   rank0:[A0 B0 C0 D0]   rank1:[A1 B1 C1 D1]   rank2:[A2 ...]   rank3:[A3 ...]
python
dist.all_to_all_single(output, input)   # flat version, most common

This is the backbone of Mixture-of-Experts training: tokens are routed to whichever expert lives on whichever GPU, which is exactly an all-to-all. It also appears in sequence and context parallelism (DeepSpeed-Ulysses) to switch between sharding over sequence and sharding over attention heads. Given how central MoE has become, it belongs alongside the other eight rather than as a footnote.

Summary: the whole vocabulary

                 ONE rank has it          ALL ranks have it
                 -----------------        ------------------
  whole copy     broadcast  -------->     (source -> everyone)
                 gather     <--------     all_gather
  split pieces   scatter    -------->     (one -> slices)
                 reduce     <--------     all_reduce
                                          reduce_scatter  (reduce, keep 1/N each)
                                          all_to_all      (everyone <-> everyone)
  no data                                 barrier

Two identities worth remembering:

all_reduce      =  reduce_scatter  +  all_gather
all_gather      =  gather          +  broadcast

The first is not a curiosity — it is how all-reduce is actually implemented, and it is the reason ZeRO-2 can halve the gradient step specifically — though not total volume, since the parameter all-gather is added back after the update. It reappears in chapters 07 and 08.

When async_op actually helps

Every collective above takes async_op=True. It is worth being precise about what that flag does, because the obvious reading — "it makes the call return without blocking" — is wrong on NCCL. As section 4 explains, the call returns almost immediately either way; the CPU is never the thing being blocked.

What the flag actually selects is which CUDA stream the collective runs on. From ProcessGroupNCCL.cpp:

// in asyncOp=false [default] mode, we use currentStream as ncclStream
// otherwise, we use separate ncclStream and let it sync on currentStream
auto ncclStream = asyncOp ? ncclStreams_.at(key)
                          : at::cuda::getCurrentCUDAStream(device.index());

So the two modes differ in a way that has nothing to do with blocking:

async_op=Falseasync_op=True
Runs onyour current compute streama separate NCCL stream
Overlap with computeimpossible — same stream, so kernels are strictly orderedpossible — two streams progress concurrently
ReturnsNone — there is no handle, and none neededa Work handle you must wait() on

That reframes the whole feature. async_op=True does not make anything faster by itself; it moves the collective off the critical path so that something else can occupy the GPU while it runs. If nothing else is queued, you have added an extra stream and a synchronisation event for no gain.

The rule that follows from this

The gap between issuing and waiting must contain GPU work — kernels queued on the compute stream. Python statements do not count.

The CPU already runs far ahead of the GPU, so filling the gap with host-side code buys nothing. It is queued kernels that overlap, not lines of source.

Which collectives are worth the trouble, and what real systems overlap them with:

CollectiveOverlapped withWhere you have seen it

all_gather_singlethe current layer's computeFSDP / ZeRO-3 prefetch. Layer N+1's parameters are gathered while layer N is still running

A worked shape, the pattern all of the above reduce to:

python
# NO overlap: the collective sits on the compute stream,
#             so `more_compute` cannot start until it finishes
dist.all_reduce(grad_bucket)
more_compute(activations)

# OVERLAP: collective on its own stream, compute proceeds beside it
work = dist.all_reduce(grad_bucket, async_op=True)
more_compute(activations)          # real GPU kernels - this is what hides the latency
work.wait()                        # compute stream now waits on the NCCL event
optimizer_step(grad_bucket)        # safe to read only after wait()

Four ways to get it wrong

  • Reading the buffer before wait(). You get a partially reduced tensor and no error whatsoever. This is the most common async bug and it corrupts results silently.
  • Letting the tensor die before wait(). NCCL is still reading that memory from another stream. PyTorch stashes tensors to mitigate this, but keeping a reference is your job.
  • Expecting two collectives on the same group to overlap each other. One process group means one NCCL stream, so its collectives serialise in issue order. They overlap with compute, not with one another. To overlap two collectives, put them on separate process groups.
  • Forgetting wait() entirely. Nothing raises. The dependency is simply never inserted, and results are non-deterministically wrong.

Finally, overlap is not free even when it works. NCCL's kernels occupy SMs and consume HBM bandwidth while they run, so a collective hidden behind compute still slows that compute down — it is cheaper than serialising, not costless. This is part of why switch-side reduction is attractive: it hands those SMs back.

6. How ring all-reduce actually works

Section 5 described what each collective does. All-reduce is worth opening up to see how, because the algorithm explains the performance numbers you will measure, and it explains the design of every memory-saving strategy in chapter 08.

The goal

Four GPUs have just finished a backward pass, each on its own slice of the batch. Each holds a different gradient tensor. To keep the arithmetic readable, say the tensor is four numbers long:

rank 0:  [ 1,  2,  3,  4 ]
rank 1:  [10, 20, 30, 40 ]
rank 2:  [ 5,  5,  5,  5 ]
rank 3:  [ 2,  2,  2,  2 ]

We want every rank to end up holding the elementwise sum [18, 29, 40, 51]. That is all-reduce: add up four tensors, give the answer to all four ranks.

The obvious way, and why it fails

Rank 0 could collect the other three tensors, add them, and send the answer back out. But then rank 0 receives 3 tensors and sends 3 tensors, while every other rank sends 1 and receives 1. One link does all the work while the rest sit idle, and it gets worse as you add GPUs — on 64 GPUs, rank 0 would move 63 tensors' worth of data through a single port.

What we want instead: every link busy at every moment, and no rank doing more work than any other.

Why split into N chunks

Here is the move that makes it possible. The sum of element 0 does not depend on elements 1, 2, or 3 at all. Laid out as a grid, the four column-sums are four completely independent problems:

        col 0    col 1    col 2    col 3
r0        1        2        3        4
r1       10       20       30       40
r2        5        5        5        5
r3        2        2        2        2
        -----    -----    -----    -----
sum      18       29       40       51

So instead of one big job there are N independent small jobs — and there happen to be N ranks. Give each rank responsibility for one column and everybody has something to do. That is the entire reason for chunking: it converts one contended job into N parallel ones.

Phase 1 — reduce-scatter, step by step

Each step, every rank sends one number to its right neighbour, receives one from its left, and adds it in. The column a rank works on rotates every step — this is the part that is easy to get wrong. Nothing stays put, which is exactly what lets rank 2's contribution eventually reach rank 0.

Three steps, and each rank owns exactly one finished value — 29, 40, 51, 18. Between them they hold the whole answer, but nobody has all of it. That is reduce-scatter: the result exists, scattered one piece per rank.

Note the offset: rank i ends up owning column i+1, not column i. That is the rotation showing up in the final state.

📝 Note — "reduce-scatter" is one operation, not a reduce followed by a scatter.

The name misleads almost everyone once. Nothing here performs a scatter; no such call exists anywhere in ring all-reduce. The word describes where the answer lands — scattered, one piece per rank. Phase 1 is the reduce-scatter, in a single pass.

Which raises the obvious question: if the ring is set up properly, why don't all the workers simply end up with the full reduced tensor, making phase 2 unnecessary? Look at what each rank holds after phase 1, annotated with how many of the four contributions each cell has absorbed:

            col0        col1        col2        col3
  rank 0      1(1/4)    29(4/4)    10(3/4)     6(2/4)
  rank 1     11(2/4)    20(1/4)    40(4/4)    46(3/4)
  rank 2     16(3/4)    25(2/4)     5(1/4)    51(4/4)
  rank 3     18(4/4)    27(3/4)     7(2/4)     2(1/4)
                ^
      rank 0 holds only its OWN value here - 1 of 4

Every rank finishes with exactly one complete column. Take rank 0 and col0: it still holds 1, its own contribution and nothing else. The answer for that column, 18, was assembled somewhere else entirely:

rank 0  ->  rank 1  ->  rank 2  ->  rank 3
   1          11          16          18  OK

It travelled away from rank 0, which never received a single byte of col0 data. No amount of clever setup changes that, because the diagonal staircase in the matrix above is forced by the budget: a rank sends one chunk per step, and that is the whole reason the ring is cheap. For every rank to fully reduce every column locally, each would have to receive (N-1) contributions across all N columns — (N-1)D bytes, the naive cost, N/2 times worse. Dividing the reduction work is what makes it affordable, and a divided answer is the shadow of that division.

Formally there is no way around it: all-reduce has a lower bound of 2D(N-1)/N bytes per rank, while reduce-scatter alone costs D(N-1)/N. You cannot buy all-reduce at reduce-scatter's price, so phase 2 is not a wart in the design — it is the other half of a proven minimum.

Two footnotes. NCCL does not literally call two APIs here; it is one fused schedule, and the two-phase decomposition is the algorithm's structure rather than a sequence of operations. And there is a real case where you should stop after phase 1: if a rank only needs its own shard of the result, the second half is wasted work. That is exactly ZeRO-2 and FSDP — each rank owns 1/N of the optimizer state, so it only wants 1/N of the gradient. Half the traffic, and gradient memory down by a factor of N.

Why 2(N−1) steps

Six steps for four GPUs. In general it is (N-1) to accumulate plus (N-1) to distribute:

  • N−1 to accumulate (reduce-scatter) — each step adds the incoming partial into what you have.
  • N−1 to distribute (all-gather) — each step copies a finished value onward.

The two phases differ only in whether incoming data is added or stored. Both are N−1 for the same reason: a value moves exactly one rank per step, and it has to reach the N−1 ranks that are not itself. Algebraically, after k steps a chunk carries k+1 contributions; you want all N, so k = N-1.

An N-th step would carry each value back to where it started — pure waste. N−1 is exactly the ring's diameter.

One thing worth keeping straight: it is not that a single chunk is passed around three times in phase 2. All four finished values move simultaneously, each needing three hops. Every link stays busy on every step of both phases, which was the point.

What it costs

The formula below uses four symbols, so it is worth pinning them down before deriving anything:

SymbolMeaning
NNumber of ranks — the GPUs in the ring. The world size.
DSize of the tensor being all-reduced, in bytes. In training this is the gradient buffer. Just "data".
D/NOne chunk — the tensor cut into N pieces, one per rank, exactly as in the section above.
2(N-1)Number of steps: N-1 to accumulate, then N-1 to distribute.

Each step, a rank sends exactly one chunk — D/N bytes, never the whole tensor. That is the entire trick, and the cost is just those two quantities multiplied:

bytes per rank = steps x bytes per step
               = 2(N-1) x D/N
               = 2(N-1)D/N

The step count and the byte count are the same calculation read twice. The shape of the formula decodes cleanly: the 2 is the two phases, the (N-1) is the ring diameter, the /N is chunking.

As N grows, 2(N-1)D/N climbs toward 2D but never reaches it — bounded however many GPUs you add, rather than growing with them. Read that as a statement about volume only: the 2(N-1) step count in the very same formula still grows linearly, which is the subject of the end of this section.

The line that explains ZeRO

All-reduce costs exactly twice reduce-scatter or all-gather alone — because it is those two operations run back to back.

That single fact is the design basis of ZeRO. By keeping only a shard of the gradients, ZeRO stage 2 replaces the gradient all-reduce with a reduce-scatter, halving that step and cutting gradient memory by 1/N. Total per-step volume is unchanged: the updated parameters must then be all-gathered, so the two halves of the all-reduce simply move to either side of the optimizer step. Chapter 08 works through the consequences.

Two worked examples

Before trusting the formula on real hardware, check it against the toy walkthrough above, where D = 4 numbers and N = 4, so a chunk is a single number:

steps  = 2(N-1)     = 2(4-1) = 6        <- the walkthrough has exactly 6 steps
volume = 2(N-1)D/N  = 6 x 1  = 6 numbers
                             = 1.5 x D  <- the N=4 row of the table above

Example A — a 1B-parameter model on one 8-GPU NVLink node. Gradients in bf16, so two bytes per parameter:

D      = 1e9 params x 2 bytes  = 2 GB
chunk  = D/N = 2 GB / 8        = 250 MB
steps  = 2(8-1)                = 14
volume = 14 x 250 MB           = 3.5 GB      = 1.75 x D  OK

transfer   3.5 GB / 450 GB/s   ~ 7.8 ms
latency    14 x ~5 us          ~ 0.07 ms     <- under 1% of the total

Squarely bandwidth-bound, which is the regime the ring is built for. The naive alternative pushes (N-1)D = 14 GB through the root's single link, about 31 ms — four times slower. That ratio is not a coincidence of these numbers: dividing (N-1)D by 2(N-1)D/N leaves N/2 exactly, whatever the tensor size. At 512 ranks the ring wins by 256×.

Example B — one small 100 KB gradient bucket across 512 GPUs. Same formula, opposite outcome:

chunk  = 100 KB / 512   ~ 200 bytes   <- smaller than a network packet
steps  = 2(511)         = 1022
volume ~ 200 KB         = 1.996 x D   <- the bound still holds perfectly

transfer   ~0.4 us
latency    1022 x ~5 us ~ 5.1 ms      <- essentially 100% of the total

The volume bound did everything it promised and bought nothing at all, because you are paying 1,022 round trips to move 200 KB. This is the concrete version of the warning that the 2(N-1) term never stops growing. A tree needs roughly 2·log₂(512) = 18 steps, about 0.09 ms — 57× faster on identical hardware, which is what the next part of this section is about, and why DDP batches gradients into ~25 MiB buckets to push you back toward Example A.

When the ring loses: trees

The ring's weakness is latency: 2(N-1) sequential steps. On 512 GPUs that is 1,022 steps. For a small tensor, where D/N is tiny and per-step overhead dominates, that is terrible. So NCCL keeps a second shape in reserve:

Ring   -  bandwidth-optimal, 2(N-1) steps
          +---+   +---+   +---+   +---+   +---+   +---+
          | 0 |-->| 1 |-->| 2 |-->| 3 |-->| 4 |-->| 5 |
          +---+   +---+   +---+   +---+   +---+   +---+
            ^                                       |
            +---------------------------------------+

Tree   -  latency-optimal, ~log N steps
                        +---+
                        | 0 |        reduce ^ up the tree
                        +---+        bcast  v down the tree
                     +----+----+
                   +---+     +---+
                   | 1 |     | 2 |
                   +---+     +---+
                  +--+--+   +--+--+
               +---+ +---+ +---+ +---+
               | 3 | | 4 | | 5 | | 6 |
               +---+ +---+ +---+ +---+

Total time for either is roughly steps x (alpha + bytes_per_step / beta), where alpha is per-step latency and beta is link bandwidth. For the ring the bandwidth term settles at 2D/beta but the latency term 2(N-1)alpha grows linearly. The tree flips the tradeoff: O(log N) depth, slightly worse bandwidth efficiency. NCCL chooses per call based on message size and world size. At large scale it uses a double binary tree — two overlapping trees where each rank is a leaf in one and an interior node in the other, so no link sits idle.

This is also why DDP buckets gradients rather than all-reducing each parameter separately: many small collectives are latency-bound, so it batches them into roughly 25 MiB buckets first. Chapter 05 covers bucketing properly.

📝 Note — these are logical orderings, not physical wiring.

On an 8-GPU NVSwitch node every GPU is physically connected to every other. The ring is only the order NCCL decided to pass data around, chosen so consecutive ranks are neighbours on the fastest available link. We said NCCL is "topology-aware," and that on an NVLink node an all-reduce "may never touch the PCIe bus or host memory." Both claims deserve unpacking, because together they explain why the backend choice is a performance regime rather than a preference.

Two networks in one box

The single most useful thing to understand about a GPU server is that the GPUs sit between two separate networks. One exists only to move tensors between GPUs and is very fast. The other is the ordinary general-purpose bus shared with every other device in the machine, and is much slower.

HBM is the memory on the GPU card itself — the "80 GB" in an 80 GB A100. It sits next to the compute die and is the fastest memory in the machine by a wide margin. Your tensors live here.

PCIe is the general-purpose expansion bus every server has — how the CPU talks to any plug-in device: GPUs, NICs, NVMe drives. Note the ratio: PCIe is roughly 50× slower than the HBM it feeds. That gap is the whole reason NVLink exists.

NVLink is NVIDIA's GPU-to-GPU link — physically a separate set of wires with its own pins and protocol, not part of the PCIe tree. An A100 has 12 links (~600 GB/s bidirectional total), an H100 has 18 (~900 GB/s), and a Blackwell B200 reaches ~1.8 TB/s on NVLink 5. So NVLink is roughly 10–30× faster than PCIe for the same GPU-to-GPU copy, and the gap has widened with every generation.

NVSwitch solves a problem NVLink alone has. Each GPU has a fixed number of links, so in an 8-GPU box you cannot give every pair a full-width direct connection — that would need 7 links fanning out of every GPU, and each would sit idle whenever that pair was not talking. Without a switch you get a partial mesh where achievable bandwidth depends on which two GPUs are talking. NVSwitch is a physical crossbar: every GPU plugs its links into the switch, and any GPU reaches any other at full speed, simultaneously. A DGX H100 contains four of these chips; Blackwell systems use 5th-generation NVSwitch, and GB200 NVL72 extends the same fabric across 72 GPUs in a rack, so an all-reduce that once had to cross the network can stay on NVLink.

⚠️ The units trap.

Networking is quoted in gigabits per second; interconnects in gigabytes per second. A 400 Gb/s InfiniBand link is 50 GB/s. Divide by eight before comparing a NIC to NVLink, or you will overestimate your network by an order of magnitude.

What "discovering the topology" actually means

When you call dist.init_process_group("nccl"), before a single byte of your data moves, NCCL reads the machine's wiring diagram:

  • It walks the PCI device tree in /sys to see which GPUs hang off which PCIe switch, and which CPU socket each is attached to.
  • It queries NVML to ask each GPU which peers it has NVLink connections to, and how many links.
  • It detects whether NVSwitch is present.
  • It enumerates network cards and works out which NIC is physically closest to which GPU.

From that it builds a weighted graph — nodes are GPUs, edges are links, weights are bandwidth and latency — and then searches over candidate communication schedules for the one that keeps the most links busy. That search is the real work: not "which library am I," but "given this specific machine, what is the fastest arrangement?"

You can watch it happen. Run with NCCL_DEBUG=INFO and you will see:

NCCL INFO Channel 00/12 :    0   1   2   3   4   5   6   7
NCCL INFO Channel 01/12 :    0   3   2   1   4   7   6   5

That is NCCL reporting the exact ring orderings it chose, and that it is running twelve of them in parallel.

The three routes a GPU-to-GPU copy can take

Route 1 - staged through host memory   (no peer-to-peer support)
  GPU0 HBM --PCIe--> host DRAM --PCIe--> GPU1 HBM        ~10-15 GB/s

Route 2 - PCIe peer-to-peer            (GPUDirect P2P)
  GPU0 HBM --------PCIe switch--------> GPU1 HBM         ~20-25 GB/s

Route 3 - NVLink
  GPU0 HBM ------NVLink / NVSwitch----> GPU1 HBM         ~450 GB/s

Route 1 crosses PCIe twice, consumes host memory bandwidth, and requires the CPU to manage a pinned staging buffer. Route 2 hops across the PCIe switch directly between the two cards — host memory is skipped and the CPU is out of the data path, but the ceiling is still PCIe. Route 3 leaves GPU 0 on the NVLink pins, crosses the NVSwitch, and lands in GPU 1's HBM, never entering the PCIe tree at all.

So "an all-reduce may never touch the PCIe bus or host memory" means: for the entire collective, the payload bytes travel exclusively on route 3. The gradients are never copied into system RAM, never cross the PCIe complex, and the CPU never sees them.

📝 Note — PCIe is still involved, just not for the data.

The CPU issues kernel launches and small control descriptors over PCIe throughout. What stays off it is the bulk payload — the gigabytes of gradients. That is the distinction that matters for throughput.

When the switch does the arithmetic

Everything in section 6 assumes the addition happens on GPUs. That assumption is worth questioning: if all eight GPUs are wired into a switch, why not have everyone send once, let the switch add it up, and have the switch send the answer back? That would be one step instead of 2(N-1).

NVIDIA built exactly that: SHARP (Scalable Hierarchical Aggregation and Reduction Protocol). The in-node NVLink version is NVLink SHARP, which NCCL exposes as the NVLS algorithm.

⚠️ A crossbar alone does not help — the trap in the idea.

NVSwitch as described above is a dumb crossbar: it routes traffic, it has no arithmetic units. If you tried "everyone sends to GPU 0, GPU 0 adds and sends the answer back," the switch would deliver the traffic happily, but GPU 0 still has to receive N−1 full tensors through its own single link. On 8 GPUs that is 7×D arriving at one port. The switch is not the bottleneck; the endpoint is. This is the naive algorithm from section 6 wearing a different hat.

A full crossbar solves connectivity, not aggregation. The addition has to happen somewhere, and if that somewhere is a GPU, that GPU becomes the choke point. The ring's whole trick is spreading the reduction so no endpoint ever handles more than D/N at a time.

For the idea to work the switch must actually do arithmetic — and on Hopper-generation NVSwitch (3rd gen, as in DGX H100) it does. The switch silicon has reduction units and multicast support:

  1. Each GPU sends its tensor into the fabric — D bytes out, once.
  2. The switch sums the incoming streams as they pass through.
  3. The switch multicasts the result back — each GPU receives D bytes in, once.
RingNVLS (switch reduction)
Steps2(N-1)constant, independent of N
Bytes sent per GPU≈ 2D≈ D

Where the addition happensGPU SMsswitch ASIC

Two separate wins. The latency win is obvious — constant rather than growing with N, which matters enormously for small tensors at large scale.

The bandwidth win is the one people miss. Ring is bandwidth-optimal among endpoint-only algorithms: if all arithmetic happens on GPUs, you cannot beat ~2D per GPU, because the data must traverse the ring twice. Multicast breaks that floor — the switch replicates the result to all ports itself, so no GPU re-sends anything. Roughly a 2× reduction in wire traffic.

There is a third, quieter benefit: NCCL's ring kernels occupy GPU SMs and consume HBM bandwidth doing read-add-write. Push the arithmetic into the switch and those resources go back to your model.

So why does the ring still exist?

  • Hardware. NVLS needs 3rd-gen NVSwitch or newer. A DGX A100's NVSwitch is a pure crossbar with no reduction units, and plenty of machines have no NVSwitch at all. Ring works everywhere.
  • Scope. NVSwitch spans one node. Across nodes you are on InfiniBand, where SHARP can do the same trick in the IB switches — but only if the fabric is SHARP-capable and the aggregation manager is configured. Hence NCCL's hybrid NVLSTree: switch reduction inside the node, tree between nodes.
  • Constraints. Switch ALUs support a fixed menu of operations and dtypes, and the multicast path needs specially registered memory with alignment requirements. Anything outside that falls back to ring or tree.

NCCL picks automatically per call. NCCL_DEBUG=INFO shows which algorithm it chose, and NCCL_ALGO=NVLS (or Ring, Tree) forces it if you want to measure the difference yourself.

Why GLOO over TCP is so much slower

With the routes above in mind, the comparison is no longer mysterious. For GPU tensors, GLOO over TCP takes route 1 and then adds more:

  1. Copy GPU → host memory (one PCIe crossing).
  2. Hand the buffer to the kernel's TCP/IP stack — syscalls, socket buffers, another memory copy, checksums, congestion control.
  3. Out through the NIC and across the wire.
  4. Reverse the entire sequence on the receiving side.

Every step involves the CPU, and none of it is topology-aware — GLOO does not know NVLink exists, so two GPUs six inches apart in the same chassis communicate as though they were in different buildings. Meanwhile NCCL with GPUDirect RDMA lets the NIC read GPU memory directly, skipping host memory even for cross-node traffic.

Within a single node the gap is closer to two orders of magnitude than one.

What this buys you in practice

  • On GPUs, use nccl. Not as a default to be justified, but because gloo puts you in a different performance regime entirely.
  • Keep tensor parallelism inside a node. It all-reduces several times per layer and needs NVLink; across nodes it will be network-bound. This is the placement rule chapters 07 and 09 keep returning to.
  • If a job is slower than expected, NCCL_DEBUG=INFO will tell you which algorithm and ring ordering it picked. A ring that zig-zags across a PCIe boundary is a topology problem, not a code problem.
  • On multi-NIC machines, NCCL_SOCKET_IFNAME matters. NCCL may otherwise pick a management interface or a Docker bridge and quietly run your job at 1 Gb/s.

The cardinal rule

Every rank must call every collective, in the same order, with matching shapes and dtypes.

Violating this hangs the job — usually with no error, just silence until the NCCL watchdog timeout fires (default 10 minutes; long enough that people assume the job is merely slow).

Common ways to violate it:

python
# Rank-conditional collective - ranks 1..N-1 wait forever
if rank == 0:
    dist.all_reduce(x)

# Data-dependent control flow that differs per rank
if loss.item() > threshold:        # crossed on some ranks only
    dist.all_reduce(x)

# Uneven dataloader lengths - some ranks exit the loop early
for batch in my_loader:            # different len() per rank
    dist.all_reduce(grad)

# Shape mismatch - last batch is smaller on one rank
dist.all_gather(out_list, features)

# new_group called only by prospective members
if rank in [0, 1]:
    g = dist.new_group([0, 1])     # ranks 2,3 must call this too

Fixes: use DistributedSampler with drop_last=True for even batches; make control flow rank-independent, or all-reduce the condition first so every rank agrees; call new_group unconditionally on all ranks.

A debugging checklist for "my job hangs"

  1. Is every rank actually alive? (nvidia-smi on each node, or check for a crashed rank whose peers are now waiting.)
  2. Insert dist.barrier() between phases to bisect where it hangs.
  3. Turn on TORCH_DISTRIBUTED_DEBUG=DETAIL — it will often name the mismatched collective directly.
  4. Try the same script with backend="gloo" on CPU tensors. If it works, the bug is NCCL/topology; if it still hangs, your program logic is asymmetric across ranks.
  5. Multi-node only: check NCCL_SOCKET_IFNAME, and that MASTER_ADDR resolves and the port is reachable from all nodes.
  6. Before requesting a cluster at all: LocalTensor (PyTorch 2.10+) simulates many SPMD ranks inside a single process, applying operations per-shard and faking collectives locally. It carries real overhead and is a debugging tool rather than a training path — but "did I get the rank arithmetic right" is exactly the question it answers cheaply. Useful before a chapter-09 multi-axis job.

Correctness gotchas

  • Device binding. Every rank must call torch.cuda.set_device(local_rank) before init_process_group. Skip it and all ranks on a node default to cuda:0; the symptom is an OOM on GPU 0, or a hang at the first collective, long after the actual mistake.
  • Seeds. For data-parallel training you want different data order per rank but identical weight init. DistributedSampler handles the former; DDP broadcasts params at construction for the latter. If you roll your own, be deliberate.
  • Checkpointing. Save from rank 0 only, and dist.barrier() afterwards so other ranks do not race ahead into a partially written file. Better still, use torch.distributed.checkpoint for sharded state — it also handles resharding to a different world size on load.
  • Logging metrics. Loss printed by rank 0 is that rank's local loss, not the global one. all_reduce with ReduceOp.AVG before logging if you want the true value.
  • Synchronizing calls in the loop. A .item() or print(loss) every step forces a device sync, which stops the CPU running ahead to enqueue the next iteration's kernels — and that destroys the compute/communication overlap the whole design depends on.
  • BatchNorm. Per-rank batch statistics differ. Use nn.SyncBatchNorm if it matters for your model (it rarely does for transformers, which use LayerNorm or RMSNorm).
