   THE WHOLE DOCUMENT IN NINE LINES

   sampling turns logits into a token       <- temperature, top-k, top-p
   decode is memory-bound                   <- one full weight read per token
   so cache K and V                         <- O(T) instead of O(T^2)
   contiguous cache reserves max_len        <- 60-80% of it sits unused
   so page it: fixed blocks + a map         <- waste < 1 block per sequence
   more free blocks = bigger batch          <- the throughput lever
   schedule per ITERATION, not per request  <- continuous batching
   OR get more tokens per weight read       <- speculation, exact output
   measure TTFT and ITL separately          <- they trade against each other
The one sentence

Prefill is compute-bound and sets TTFT; decode is memory-bound and sets inter-token latency. Everything else in a serving stack is either fitting more sequences into KV memory so decode stops wasting the GPU, or extracting more tokens per weight read so it stops needing to.

1. Sampling and tokenization

The pipelineThe filtersTokenizationIncremental detokenization

The pipeline

Every decode step ends with the same funnel from a logit vector to one token id. Order matters — applying top-k before temperature gives different results than after.

   logits (V,)
     |
     v  penalties        repetition / presence / frequency
     v  temperature      logits / T          (T -> 0 means greedy)
     v  top-k            keep k largest, rest -> -inf
     v  top-p            keep smallest set with cumulative prob >= p
     v  softmax          stable: subtract max first
     v  sample           multinomial draw, or argmax if greedy
   token id

The filters

python
import numpy as np

def apply_temperature(logits, t):
    return logits if t == 0 else logits / t      # t == 0 -> use greedy_select

def top_k_filter(logits, k):
    if k <= 0 or k >= logits.size:
        return logits
    kth = np.partition(logits, -k)[-k]           # k-th largest value
    return np.where(logits < kth, -np.inf, logits)

def top_p_filter(logits, p):
    idx = np.argsort(logits)[::-1]               # descending
    probs = softmax(logits[idx])
    cum = np.cumsum(probs)
    keep = (cum - probs) < p                     # include the crossing token
    out = np.full_like(logits, -np.inf)
    out[idx[keep]] = logits[idx[keep]]
    return out

def sample_from_probs(probs, rng):
    return int(rng.choice(probs.size, p=probs))

def greedy_select(logits):
    return int(np.argmax(logits))
⚠️ Two traps in top_p

Off-by-one: testing cum >= p excludes the token that crosses the threshold, which leaves an empty set whenever one token already has probability above p. Compare the cumulative before each token, as above.

Filter on logits, not probs: mask to -inf and softmax once at the end. Zeroing probabilities and renormalising twice accumulates error and breaks the relationship with temperature.

In vLLM

All of this is one batched GPU pass in Sampler, driven by a per-request SamplingParams. Requests in the same batch can have different temperatures and top-p values, so the filters are vectorised masks over a (batch, vocab) tensor rather than a per-sequence loop. Each request carries its own seeded generator, which is what makes seed= reproducible even under continuous batching where batch composition changes every step.

Tokenization

Strings in, ids out, and back. The toy version is a dict in both directions.

python
def build_vocab(texts, specials=("<pad>", "<eos>", "<unk>")):
    toks = sorted({t for s in texts for t in s.split()})
    itos = list(specials) + toks
    return {"stoi": {t: i for i, t in enumerate(itos)}, "itos": itos}

def encode_prompt(vocab, text):
    unk = vocab["stoi"]["<unk>"]
    return [vocab["stoi"].get(t, unk) for t in text.split()]

def decode_tokens(vocab, ids):
    return " ".join(vocab["itos"][i] for i in ids)

Incremental detokenization

This is the part that surprises people. Streaming means emitting text after every token, but you cannot decode tokens one at a time — real tokenizers are stateful across token boundaries. In BPE and SentencePiece a token may be half a UTF-8 character, or carry a leading space that only makes sense in context. Decoding [464] alone and [464, 995] together do not concatenate.

python
def incremental_detokenize(tok, all_ids, prev_len):
    text = tok.decode(all_ids)            # decode the whole prefix, every time
    return text[prev_len:], len(text)     # emit only what is new
⚠️ Never call tok.decode([new_id]) per step

It produces mojibake on multi-byte characters (CJK, emoji) and drops or duplicates spaces. Decode the prefix and diff. Production keeps a sliding window of the last few tokens rather than re-decoding everything, but the principle is the same: the unit of decoding is a prefix, not a token.

In vLLM

Handled by an incremental detokenizer that keeps the last few tokens plus the character offsets already emitted, and re-decodes only that window. In the V1 architecture detokenization runs in the frontend process, not the engine core — it is pure CPU work and would otherwise sit on the critical path of the GPU loop.

Why decode is memory-bound

A decode step reads every weight in the model to produce one token. For an N-parameter model at batch size B you move 2N bytes (fp16) and do about 2NB FLOPs, so arithmetic intensity is roughly B.

intensity ≈ B  ·  H100 needs ≈ 300 to be compute-bound

At B = 1 the GPU runs at well under 1% of peak FLOPs — a very expensive memory copier. Two ways out, and this document is both:

  • Raise the batch size — the same weight read serves more sequences. Capped by KV memory: §3–5.
  • Get more than one token per weight read — speculation: §8.

What the cache holds

At step t, attention needs the keys and values of all previous tokens, and those never change once computed. Recomputing them each step costs O(T²) over a generation; caching makes it O(T). Only K and V are cached — the query is new every step and never re-read.

python
def init_kv_cache(n_layers, max_tokens, n_kv_heads, d_head):
    shape = (n_layers, max_tokens, n_kv_heads, d_head)
    return {"k": np.zeros(shape, np.float16),
            "v": np.zeros(shape, np.float16), "length": 0}

def append_kv(cache, layer, k, v):
    t = cache["length"]
    cache["k"][layer, t] = k
    cache["v"][layer, t] = v
    if layer == cache["k"].shape[0] - 1:       # advance once per full pass
        cache["length"] = t + 1

def causal_attention(q, k, v, mask=None):
    scores = (q @ k.transpose(0, 2, 1)) / np.sqrt(q.shape[-1])
    if mask is not None:                       # prefill only
        scores = np.where(mask, scores, -np.inf)
    return softmax(scores, axis=-1) @ v

def model_decode_step(model, token, cache):
    x = embed_tokens(model, [token])
    for layer in range(model.n_layers):
        q, k, v = linear_projection(model, layer, x)
        append_kv(cache, layer, k, v)
        n = cache["length"]
        x = x + causal_attention(q, cache["k"][layer, :n], cache["v"][layer, :n])
        x = x + mlp(model, layer, x)           # no mask: cache holds only the past
    return model.lm_head(x)
Note — no causal mask during decode

The single query is the newest token and the cache contains only tokens preceding it, so causality is enforced by what is in the cache. Masking is a prefill-only concern.

Note — the budget that actually matters

Whatever is left after weights and activations is the KV budget, and that budget divided by bytes-per-token divided by average sequence length is your maximum concurrency. Since concurrency is what makes decode compute-efficient, serving throughput is a memory-allocation question before it is anything else.

The reservation problem

That cache takes max_tokens up front, and it has to: the tensor is contiguous, the sequence grows one token at a time, and you cannot know how long the answer will be. So you allocate for the worst case and rarely reach it.

   seq B |########----------------------------------------|  reserved 2048, used 96
   seq C |##################################--------------|  reserved 2048, used 1503

⚠️ The number worth remembering

The vLLM paper measured 60–80% of KV memory wasted in contiguous systems. Since KV memory caps concurrency, that waste is a direct multiplier on cost per token. Paging is not a micro-optimisation — it roughly doubles to quadruples achievable batch size.

3. Paging the cache

The ideaAllocatorBounded wastePaged attentionSharing blocks

The idea

Exactly virtual memory. Split KV storage into fixed-size blocks of B tokens (16 is the default). Each sequence gets a block table mapping logical block index to physical block index. Logical order stays contiguous; physical placement does not have to be.

   PHYSICAL BLOCK POOL  (B = 4 tokens per block)

   blk:   0      1      2      3      4      5      6
        [A0]   [B0]   [A1]   [C0]   [B1]   [A2]   [free]

   block tables
     seq A : [0, 2, 5]        logical 0,1,2 -> physical 0,2,5
     seq B : [1, 4]
     seq C : [3]

   a sequence grows by appending ONE block, from anywhere in the pool

Allocator

python
import math

def blocks_needed(n_tokens, block_size):
    return math.ceil(n_tokens / block_size)

class BlockAllocator:
    def __init__(self, num_blocks):
        self.total = num_blocks
        self.free = list(range(num_blocks))
        self.refcount = [0] * num_blocks

    def allocate(self):
        if not self.free:
            raise MemoryError("no free KV blocks")
        b = self.free.pop()
        self.refcount[b] = 1
        return b

    def free_block(self, b):
        self.refcount[b] -= 1
        if self.refcount[b] == 0:              # only when nobody shares it
            self.free.append(b)

    def blocks_in_use(self):
        return self.total - len(self.free)

def append_to_paged_cache(seq, layer, k, v, pool, allocator, block_size):
    pos = seq["length"]
    logical = pos // block_size
    if logical == len(seq["block_table"]):     # crossed a block boundary
        seq["block_table"].append(allocator.allocate())
    phys = seq["block_table"][logical]
    pool["k"][layer, phys, pos % block_size] = k
    pool["v"][layer, phys, pos % block_size] = v

def free_sequence_blocks(seq, allocator):
    for b in seq["block_table"]:
        allocator.free_block(b)
    seq["block_table"] = []

Bounded waste

A sequence only wastes space in its last, partially filled block — at most B - 1 token slots. With B = 16 that is under 7% worst case and about 3% on average, independent of max_len. External fragmentation disappears entirely, because every free block is interchangeable.

Rule

Contiguous KV wastes proportional to max_len. Paged KV wastes at most one block per sequence. That is the whole trade: you accept an indirection on every attention read to make waste independent of how long the answer might have been.

Paged attention

Standard attention assumes K and V are one contiguous tensor it can stride through. After paging they are scattered, so the kernel must consult the block table for every read. That is the cost paging charges, and why paged attention is a custom kernel rather than a layout change.

python
def gather_kv_from_blocks(pool, layer, block_table, length, block_size):
    ks, vs = [], []
    for i, phys in enumerate(block_table):
        n = min(block_size, length - i * block_size)     # last block partial
        ks.append(pool["k"][layer, phys, :n])
        vs.append(pool["v"][layer, phys, :n])
    return np.concatenate(ks), np.concatenate(vs)

def paged_attention_step(q, pool, layer, block_table, length, block_size):
    k, v = gather_kv_from_blocks(pool, layer, block_table, length, block_size)
    scores = (q @ k.T) / np.sqrt(q.shape[-1])
    return softmax(scores, axis=-1) @ v

That reference version materialises the gather; production kernels never do. They walk block by block accumulating with online softmax (the FlashAttention trick), load the block table into shared memory once per sequence, and assign one CUDA block per (sequence, head, KV block) — which is why B is a multiple of the warp size.

⚠️ Block size is a real tuning knob

Small B means less internal waste but a longer block table and more indirection per step. Large B means fewer lookups and better coalescing but more waste per sequence, cutting concurrency. 16 is the usual default; 32 can win for long-context workloads.

Sharing blocks

Once KV lives behind a block table, two sequences can point at the same physical block. This is the second payoff of paging, often the larger one in production. Requests sharing a system prompt or few-shot preamble share those blocks: a 2000-token prefix across 50 concurrent requests goes from 50 copies to 1.

   seq A : [ 7, 9, 12, 15 ]      blocks 7 and 9 are the shared system prompt
   seq B : [ 7, 9, 21 ]          refcount[7] = refcount[9] = 2
                ^--- same physical blocks, stored once

Parallel sampling and beam search fork one prompt into several continuations. They share prompt blocks; when a branch writes into a shared block, that block is copied first and the writer gets the private copy.

python
def write_block(seq, logical, allocator, pool):
    phys = seq["block_table"][logical]
    if allocator.refcount[phys] > 1:          # shared -> fork before writing
        new = allocator.allocate()
        pool["k"][:, new] = pool["k"][:, phys]
        pool["v"][:, new] = pool["v"][:, phys]
        allocator.free_block(phys)
        seq["block_table"][logical] = new
        phys = new
    return phys
In vLLM

The pool is sized by a profiling run at startup: vLLM runs a synthetic max-size batch, measures peak activation memory, then hands everything up to gpu_memory_utilization (default 0.9) of the card to KV blocks. That is why the reported number of GPU blocks changes when you change max_model_len or dtype.

Prefix sharing is hash-based rather than declared: each full block is keyed by a hash of its token ids plus the hash of the preceding block, so identical prefixes deduplicate automatically across unrelated requests with no shared-prompt API. Evicted-but-unmodified blocks stay in a cache and can be re-adopted on a later hit. Prefix caching is on by default in V1.

4. Sequences and static batching

Per-request stateStoppingStatic batching

Per-request state

A request carries everything the scheduler and the model runner will ask for: its ids, its sampling settings, where its KV lives, and how far along it is.

python
def make_request(rid, prompt, sampling, arrival):
    return {"id": rid, "prompt": prompt, "sampling": sampling, "arrival": arrival}

def init_sequence_state(req, prompt_ids):
    return {"id": req["id"], "prompt_ids": prompt_ids, "output_ids": [],
            "block_table": [], "length": 0, "status": "waiting",
            "sampling": req["sampling"], "t_first": None}

def sequence_decode_step(model, seq, pool, allocator, block_size, rng):
    logits = model_decode_step_paged(model, seq, pool, allocator, block_size)
    sp = seq["sampling"]
    if sp["temperature"] == 0:
        tok = greedy_select(logits)
    else:
        logits = apply_temperature(logits, sp["temperature"])
        logits = top_k_filter(logits, sp["top_k"])
        logits = top_p_filter(logits, sp["top_p"])
        tok = sample_from_probs(softmax(logits), rng)
    seq["output_ids"].append(tok)
    seq["length"] += 1
    return tok

Stopping

Four independent stop conditions, each mapping to a different finish_reason in the response. A server has to check all of them.

python
def is_sequence_done(seq, eos_id, max_tokens, stop_strings=(), text=""):
    if seq["output_ids"] and seq["output_ids"][-1] == eos_id:
        return "stop"                                  # model chose to stop
    if len(seq["output_ids"]) >= max_tokens:
        return "length"                                # hit the cap
    if any(s in text for s in stop_strings):
        return "stop"                                  # user-supplied stop string
    if seq.get("aborted"):
        return "abort"                                 # client disconnected
    return None
⚠️ Stop strings are a text-level test, not a token-level one

A stop string can straddle a token boundary, so it must be checked against detokenized text rather than ids — and the emitted text must then be truncated before the stop string. This is also why stop strings interact badly with streaming: you may have already sent bytes you now need to retract, which is why servers buffer the last few characters before emitting.

Static batching

Collect N requests, pad to the longest, run them together, return when all finish. Every sequence that finishes early leaves its slot idle, and no new request can start until the whole batch drains. With generation lengths varying 10×, utilisation collapses.

python
def build_batch_step_input(seqs):
    return {"tokens":       [s["output_ids"][-1] if s["output_ids"]
                             else s["prompt_ids"][-1] for s in seqs],
            "positions":    [s["length"] - 1 for s in seqs],
            "block_tables": [s["block_table"] for s in seqs],
            "lengths":      [s["length"] for s in seqs]}

def batched_decode_step(model, seqs, pool, block_size, rng):
    batch = build_batch_step_input(seqs)          # ONE forward pass for all of them
    logits = model.decode_batch(batch, pool, block_size)
    return [sample_for(s, logits[i], rng) for i, s in enumerate(seqs)]

def static_batch_generate(model, seqs, **kw):
    while not all(s["done"] for s in seqs):       # everyone waits for the slowest
        batched_decode_step(model, seqs, **kw)
    return seqs
Note — the decode batch is ragged, and that is fine

Sequences in one decode batch have different lengths, but each contributes exactly one query row. Only the KV side differs in length, and that is handled by per-sequence block tables and lengths — no padding of the query. This is why decode batching is cheap and prefill batching is not.

5. Continuous batching and scheduling

Iteration-level schedulingQueues and admissionPreemptionChunked prefill

Iteration-level scheduling

The one idea: make the batch a per-step decision instead of a per-request one. After every forward pass, evict finished sequences and admit waiting ones. New requests wait one iteration, not one batch. This is the Orca paper's contribution and the reason it is called continuous batching.

   STATIC                              CONTINUOUS

   A ####------ done, slot idle        A ####
   B ##########                        B ##########
   C ###----- done, slot idle          C ###
   D (waits for the whole batch)       D    #######   <- admitted mid-flight
                                       E     ######   <- and again
   |--- batch time = max(len) ---|

Queues and admission

Three states: waiting (queued, no KV yet), running (has blocks, decoding), swapped (preempted, KV parked on CPU). Admission is bounded by free blocks, not by a slot count — which only works because paging made blocks fungible.

python
import heapq

def priority_queue_push(q, seq, key):
    heapq.heappush(q, (key(seq), seq["arrival"], seq["id"], seq))   # stable tie-break

def priority_queue_pop(q):
    return heapq.heappop(q)[-1]

def has_free_capacity(n_tokens, allocator, block_size, reserve=1):
    return len(allocator.free) >= blocks_needed(n_tokens, block_size) + reserve

def select_admissions(waiting, allocator, block_size, max_seqs, n_running):
    admitted, budget = [], len(allocator.free)
    while waiting and n_running + len(admitted) < max_seqs:
        need = blocks_needed(len(waiting[0]["prompt_ids"]), block_size) + 1
        if need > budget:
            break                                   # head-of-line: do NOT skip ahead
        budget -= need
        admitted.append(waiting.pop(0))
    return admitted

def schedule_step(waiting, running, allocator, block_size, max_seqs):
    for s in [s for s in running if s["done"]]:     # 1. reclaim
        free_sequence_blocks(s, allocator)
    running = [s for s in running if not s["done"]]

    while running and not has_free_capacity(0, allocator, block_size):
        preempt_sequence(running.pop(), allocator, waiting)         # 2. make room

    running += select_admissions(waiting, allocator, block_size,
                                 max_seqs, len(running))            # 3. admit
    return waiting, running
Note — why admission does not skip ahead

Letting a small request jump a large one that does not fit looks like a free win and starves long prompts indefinitely under load. Blocking at the head bounds waiting time. If you want small-request priority, do it explicitly with a priority key — not as an accident of the fitting logic.

Preemption

Sequences grow, so a batch that fit at admission can stop fitting later. Something must be evicted mid-generation:

StrategyWhat happensCost to resume
Recomputefree blocks, re-prefill laterone prefill pass — cheap and parallel; the default
Swapcopy blocks to pinned CPU RAM and backPCIe round trip — no FLOPs, but serial and slow
python
def preempt_sequence(seq, allocator, waiting, mode="recompute"):
    if mode == "recompute":
        free_sequence_blocks(seq, allocator)        # KV is derivable, so drop it
        seq["prompt_ids"] = seq["prompt_ids"] + seq["output_ids"]
        seq["output_ids"], seq["length"] = [], 0
    else:
        seq["cpu_blocks"] = [copy_to_host(b) for b in seq["block_table"]]
        free_sequence_blocks(seq, allocator)
    seq["status"] = "waiting"
    waiting.insert(0, seq)                          # front: it already waited once
⚠️ Preempt the newest, and re-queue it at the front

Evicting the sequence that has generated the most tokens throws away the most work and hurts the request that has already waited longest. Evict the most recently admitted one — same reasoning as LIFO under overload. Then put it at the front of the waiting queue, or you get preemption loops where the same sequence is admitted and evicted forever without progressing.

Chunked prefill

A 4000-token prefill in one step blocks every decoding sequence for its duration — a visible stutter in every open stream. Chunked prefill splits it across iterations and mixes the pieces into decode batches, trading a little TTFT for much steadier ITL.

   WITHOUT CHUNKING     step: [ 4000-token prefill ]        <- all decodes stall
                        step: [ 32 decodes ]
                        step: [ 32 decodes ]

   WITH CHUNKING        step: [ 512 prefill + 28 decodes ]
   (budget 512)         step: [ 512 prefill + 28 decodes ]   <- smooth ITL
                        ...
In vLLM

The knobs are --max-num-seqs (batch width) and --max-num-batched-tokens (token budget per iteration). Each iteration batches all pending decodes first, then fills whatever budget is left with prefill chunks — the opposite of V0, which prioritised prefills and so optimised TTFT at the cost of ITL. In V1 the prefill/decode distinction is gone from the scheduler entirely: a scheduling decision is just {request_id: num_tokens}, which is why chunked prefill is on by default and no longer a separate mode.

Two admission details that match the reserve parameter above. There is a watermark — a fraction of KV blocks kept free when admitting — and an option to check that the full input length fits before admitting rather than just the first chunk, which prevents over-admission and KV thrashing under chunked prefill. Repeated preemption messages in the logs mean your KV budget is too small for your --max-num-seqs: lower the concurrency or raise gpu_memory_utilization.

The driver loop

Everything above is synchronous machinery. The API layer wraps it in something requests can arrive at and stream out of, independently of the step loop.

   HTTP request
     |
     v  submit_request      -> tokenize, make_request, push to waiting queue
     |
     |     +--------------------------------------------------+
     |     |  engine loop (runs continuously)                  |
     +---->|    schedule_step -> forward -> sample -> outputs  |

python
def submit_request(engine, prompt, sampling):
    rid = str(uuid.uuid4())
    ids = encode_prompt(engine.vocab, prompt)
    req = make_request(rid, prompt, sampling, time.time())
    engine.waiting.append(init_sequence_state(req, ids))
    engine.streams[rid] = asyncio.Queue()
    return rid

def drive_until_complete(engine):
    while engine.waiting or engine.running:
        for rid, token, finish in engine.step():   # one scheduled iteration
            engine.streams[rid].put_nowait((token, finish))

def collect_request_output(engine, rid):
    seq = engine.finished[rid]
    return {"id": rid, "text": decode_tokens(engine.vocab, seq["output_ids"]),
            "token_ids": seq["output_ids"], "finish_reason": seq["finish_reason"]}

Server-sent events: one data: line per chunk, a blank line between, a literal [DONE] sentinel at the end. The delta is text, not tokens — see the incremental detokenization trap in §1.

def format_stream_chunk(rid, text, index=0, finish_reason=None):

            "choices": [{"index": index, "text": text,

async def stream(engine, rid):
    prev_len, ids = 0, []
    while True:
        token, finish = await engine.streams[rid].get()
        ids.append(token)
        delta, prev_len = incremental_detokenize(engine.tok, ids, prev_len)
        chunk = format_stream_chunk(rid, delta, 0, finish)
        yield "data: " + json.dumps(chunk) + "\n\n"
        if finish:
            break
    yield "data: [DONE]\n\n"

⚠️ Handle client disconnects

A disconnected client whose sequence keeps generating burns KV blocks and batch slots for nothing. The stream generator must abort the request on cancellation — mark it aborted, free its blocks at the next scheduler pass. Under load, missing this is the difference between graceful degradation and a wedged server.

In vLLM

AsyncLLMEngine wraps the synchronous engine and hands each request an async generator. The OpenAI-compatible server exposes /v1/completions, /v1/chat/completions, /v1/embeddings and /metrics on top of it.

In V1 the engine core runs in its own process, connected to the API frontend over ZeroMQ. Tokenization, detokenization and HTTP handling sit in the frontend, so Python overhead on those cannot stall the GPU loop — the biggest structural change from V0, and the reason V1 holds throughput at high request rates where V0 became CPU-bound.

def time_to_first_token(t_submit, t_first):
    return t_first - t_submit

def inter_token_latency(token_times):
    return float(np.mean(np.diff(token_times))) if len(token_times) > 1 else 0.0

def aggregate_throughput(total_output_tokens, wall_seconds):
    return total_output_tokens / wall_seconds         # OUTPUT tokens only

def latency_percentiles(values, ps=(50, 90, 95, 99)):
    return {"p%d" % p: float(np.percentile(values, p)) for p in ps}

def run_throughput_latency_benchmark(engine, requests, rate=None):
    t0 = time.time()
    for req in requests:
        if rate:
            time.sleep(np.random.exponential(1 / rate))   # Poisson arrivals
        submit_request(engine, req["prompt"], req["sampling"])
    drive_until_complete(engine)

    ttfts = [time_to_first_token(r["t_submit"], r["t_first"])
             for r in engine.finished.values()]
    itls = [inter_token_latency(r["token_times"]) for r in engine.finished.values()]
    n_out = sum(len(r["output_ids"]) for r in engine.finished.values())
    return {"ttft": latency_percentiles(ttfts),
            "itl": latency_percentiles(itls),
            "throughput": aggregate_throughput(n_out, time.time() - t0)}
⚠️ Three ways benchmarks lie

Sending everything at once measures a queue drain, not serving. Use Poisson arrivals at a target rate, and sweep the rate.

Reporting means hides the tail users actually feel. Report p50/p90/p99 — preemption and scheduling artefacts live entirely in the tail.

Counting prompt tokens in throughput makes a long-prompt workload look fast. Report output tokens/sec, and prompt throughput separately if you need it.

The trade

TTFT and throughput pull against each other, and the scheduler is where you choose. Bigger batches raise throughput and raise queueing delay; chunked prefill smooths ITL and slightly worsens TTFT; speculation cuts ITL at low load and costs throughput at high.

   request rate ->

   throughput   ______/------------   saturates when the GPU is full
                     /
   TTFT         ____/                 flat, then a knee, then linear (queueing)
                    ^
                    |  the knee is your capacity. Report it, not peak throughput.

8. Speculative decoding

The slackThe algorithmSpeedupOn a paged cacheDraft sources

The slack

Back to §2: decode is memory-bound, so nearly all its time goes to streaming weights. Feed the model K positions instead of 1 and the weight read is unchanged — those extra positions are close to free. The catch is causal: to evaluate position t+2 you need the token at t+1. Speculation breaks the circle by getting a guess from somewhere cheap, then using the free parallelism to check it.

   PLAIN DECODE                  SPECULATIVE

   [target] -> 1 token           [draft] x4  -> 4 guesses   (cheap, serial)
   [target] -> 1 token           [target] x1 -> checks all 4 + 1 bonus
   [target] -> 1 token                          |
   [target] -> 1 token                          v
                                 accept "the cat" , fix "ran"->"sat" , drop rest
   4 target passes = 4 tokens    1 target pass  = 3 tokens
The guarantee

The tokens that come out are distributed exactly as if the target model had run alone. Not approximately — identically. The draft affects only your speed, never your output distribution. Bolt on a bad draft, a random one, an adversarial one: you lose speed and nothing else.

The algorithm

p is the target distribution, q the draft's, both already temperature- and top-p-adjusted.

  1. Draft K tokens autoregressively from q, keeping q at each step.
  2. Run the target once over all K drafted positions → K+1 distributions.
  3. Walk left to right; accept x̃i if r < min(1, pi(x̃i)/qi(x̃i)), r ~ U[0,1].
  4. On first rejection, emit from the residual norm(max(0, pi − qi)) and stop.
  5. If all K accepted, emit a free bonus token from pK.
python
def speculative_round(target, draft, ids, K, rng):
    drafted, q_list, cur = [], [], list(ids)
    for _ in range(K):                        # 1. draft, remembering q
        q = draft(cur)
        t = sample_from_probs(q, rng)
        drafted.append(t); q_list.append(q); cur.append(t)

    p_list = target(list(ids) + drafted)      # 2. ONE pass scores K+1 positions

    out = []
    for i, t in enumerate(drafted):           # 3. accept longest surviving prefix
        if rng.random() < min(1.0, p_list[i][t] / q_list[i][t]):
            out.append(t)
        else:
            resid = np.maximum(p_list[i] - q_list[i], 0)
            out.append(sample_from_probs(resid / resid.sum(), rng))
            return out                        # 4. fix and stop
    out.append(sample_from_probs(p_list[K], rng))     # 5. bonus token
    return out

Two bits that look arbitrary and are not:

  • Why the residual, not just p? The accept branch already emitted min(p, q) worth of mass at this position — it fills the target's quota wherever the draft over-proposed and falls short only where it under-proposed. p − min(p,q) = max(0, p−q) is exactly the shortfall. Resampling from p would double-count and skew output toward whatever the draft likes.
  • Why discard drafts after a rejection? Not distributional — those drafts were conditioned on the token you just replaced, so their target logits are stale.
⚠️ Sample the draft, do not argmax it

The test divides by qi(x̃i), so the draft must expose the distribution it sampled from. Both models must also use the same temperature and top-p, applied before the ratio.

Acceptance rate and speedup

α is the probability a drafted token survives — the overlap α = ∑x min(p(x), q(x)), not accuracy. With c the draft's cost as a fraction of a target pass:

speedup =   (1 − αK+1) / (1 − α)   /   (K·c + 1)

Note — a worked number

70B target, 7B draft (c ≈ 0.1), α = 0.8, K = 5: tokens 3.7, cost 1.5, speedup ≈ 2.5×. Drop to a 1B draft (c ≈ 0.02) and α falls to ~0.7: 2.9 / 1.1 ≈ 2.7× — faster despite the worse draft. The optimum draft is usually smaller than people guess. K has an interior optimum too: the numerator saturates at 1/(1−α) while cost grows linearly. Practical range 3–7.

⚠️ The batch-size trap — the most common follow-up

Speculation monetises idle FLOPs. At batch 1 they are nearly free. As batch size rises, continuous batching (§5) has already filled the machine and the GPU is compute-bound — now the draft passes and the K× wider verify cost real time. Above roughly batch 32–64 speedup shrinks and can go below 1×.

§5 and §8 compete for the same slack: speculation is a latency optimisation, continuous batching a throughput one. Enable speculation adaptively — on when the batch is small, off when the machine is full.

python
def rollback(seq, n_reject, allocator, block_size):
    seq["length"] -= n_reject                        # stale entries are simply
    keep = blocks_needed(seq["length"], block_size)  # overwritten next round
    for blk in seq["block_table"][keep:]:
        allocator.free_block(blk)
    seq["block_table"] = seq["block_table"][:keep]

def has_capacity_for_round(seq, K, allocator, block_size):
    need = blocks_needed(seq["length"] + K + 1, block_size) - len(seq["block_table"])
    return len(allocator.free) >= need               # reserve the WHOLE round
Note — rollback is where paging pays off

Attention reads only up to length, so entries past it are unreachable and never need zeroing. Rollback is metadata-only: an O(tokens) correction becomes O(1). Contiguously this is a memmove or a bookkeeping mess. Prefix caching (§3) is untouched — the target pool behaves exactly as before.

⚠️ EOS inside an accepted run

If EOS is accepted at position 2 of 5, positions 3–5 still pass the sampling test but must never be emitted. Truncate at EOS and roll back the remaining KV. Missing this produces text after the stop token — a bug that survives every distributional test you might write.

The whole thing in eight sentences
  • Sampling is a funnel: penalties, temperature, top-k, top-p, softmax, draw.
  • Prefill is compute-bound and sets TTFT; decode is memory-bound and sets ITL.
  • Cache K and V to make generation O(T); the cache is large and grows.
  • Contiguous cache reserves max_len and wastes most of it; paging bounds waste at one block per sequence.
  • More free blocks means a bigger batch, which is what makes decode efficient.
  • Schedule per iteration, not per request; preempt the newest and re-queue it at the front.
  • Speculation buys extra tokens per weight read with the output distribution provably unchanged.
  • Batching and speculation compete for the same idle FLOPs — measure TTFT and ITL separately or you will not see the trade.

Build order that works

   sampling + tokenizer            <- testable with no model at all
        v

        v
   paged cache + block allocator   <- test: paged == contiguous logits, bitwise
        v

        v

        v

⚠️ The equivalence tests are the whole game

Every stage above has a version of the same test: the optimised path must produce bitwise identical output to the naive path it replaces. Paging bugs (off-by-one in the partial last block, stale block table after preemption, missed copy-on-write) and speculation bugs (resampling from p instead of the residual) both produce perfectly fluent text and show up nowhere else.
