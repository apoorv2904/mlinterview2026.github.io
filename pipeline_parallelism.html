1. Inter-layer model parallelism

Pipeline parallelism is an improvement on inter-layer model parallelism. Inter-layer model parallelism was the model-parallel method that assigns particular layers to particular GPUs, as shown below. In the figure below, layers 1, 2, 3 are assigned to GPU 1 and layers 4, 5 to GPU 2 — and one such split-off piece is called a stage. In the example below the model is divided into 2 stages.

         ┌──────── GPU 1 ────────┐   ┌──────── GPU 2 ────────┐
   x ──▶ │ layer1 → layer2 → l3  │──▶│ layer4 → layer5       │──▶ ŷ
         └───────────────────────┘   └───────────────────────┘
              ▲ stage 0                    ▲ stage 1
                                       activations cross the boundary
                                       via send/recv  (P2P)

However, due to the nature of neural networks — where the output of the previous layer is the input of the next — another GPU can only begin its computation once a particular GPU has finished. In other words, as in the figure below, inter-layer model parallelism has the fatal limitation that only one GPU can be used at a time.

(diagrams: ../images/inter_layer_2.png, ../images/inter_layer_3.gif)

   time ──────────────────────────────────────────────────────────────▶

   GPU0  ███████                                            ███████
   GPU1         ███████                              ███████
   GPU2                ███████               ███████
   GPU3                       ███████ ███████
         └──────── forward ──────────┘└──────── backward ───────────┘

         ███ = computing        (blank) = IDLE

   Utilization = 1/4. You bought four GPUs and are using one at a time.
Note — the term "stage" is worth pinning down now

, because the rest of the chapter counts in stages. A stage is one contiguous chunk of layers assigned to one device. p = number of stages = pipeline-parallel degree. Stage 0 owns the embedding; the last stage owns the LM head and computes the loss. Everything else in this chapter is about scheduling work through these stages — the partitioning itself doesn't change.

2. GPipe

Micro-batchPipeliningGPipe in code

GPipe is a pipeline-parallelism technique developed at Google. It appeared in order to reduce the idle time of GPUs during inter-layer model parallelism, and it works by splitting the mini-batch once more into micro-batches and pipelining the training process.

(diagrams: ../images/gpipe_1.png, ../images/pipeline_parallelism2.png)

Micro-batch

  • A mini-batch is a subsample set obtained by dividing the whole dataset into n pieces.
  • A micro-batch is a subsample set obtained by dividing a mini-batch once more into m pieces.
   dataset  ─────────────────────────────────────────────────────────
                │ split into n
                ▼
   mini-batch   ┌───────────────────────────────────┐   e.g. 32 examples
                │ split into m                      │
                ▼                                   │
   micro-batch  ┌──────┬──────┬──────┬──────┐       │   e.g. 4 × 8 examples
                │  μ1  │  μ2  │  μ3  │  μ4  │       │
                └──────┴──────┴──────┴──────┘       │
                                                    │
   ONE optimizer step happens per mini-batch ───────┘
   (the micro-batches' gradients accumulate)
Note — the crucial semantic point: micro-batching does not change the math

All m micro-batches contribute gradients to the same optimizer step; they simply accumulate. So GPipe with m=8 produces exactly the gradient that one un-split batch would have produced (up to floating-point ordering). Pipelining is a pure scheduling transformation — same loss curve, better hardware utilization.

The one place it does bite: any layer whose output depends on the whole batch. BatchNorm computes statistics over B/m samples instead of B, which changes the model. LayerNorm and RMSNorm are per-example and therefore fine — one of several reasons transformers pipeline far more comfortably than CNNs.

Pipelining

GPipe splits the mini-batch into micro-batches and pipelines the computation. The red parts (where the GPU is idle) are called bubble time, and you can see that the larger the micro-batch count, the smaller the bubble time becomes.

   GPipe schedule — all forwards, then all backwards.  p=4, m=4

   time ────────────────────────────────────────────────────────────▶
   GPU0  F1 F2 F3 F4  ·  ·  ·                    B4 B3 B2 B1
   GPU1   ·  F1 F2 F3 F4  ·  ·               B4 B3 B2 B1
   GPU2   ·  ·  F1 F2 F3 F4  ·           B4 B3 B2 B1
   GPU3   ·  ·  ·  F1 F2 F3 F4       B4 B3 B2 B1
         └─ fill ─┘                              └─ drain ─┘
              ▲                                       ▲
              └──────────── bubble (idle) ────────────┘

   Fk = forward of micro-batch k    Bk = backward of micro-batch k
Note — the bubble, quantified

With p stages and m micro-batches, the pipeline needs m + p − 1 slots instead of the ideal m:

bubble fraction = (p−1) / (m+p−1)

Fraction of total time idle:

micro-batches m p = 2 p = 4 p = 8 p = 16
1 50% 75% 88% 94%
4 20% 43% 64% 79%
8 11% 27% 47% 65%
16 6% 16% 30% 48%
32 3% 9% 18% 32%
64 1.5% 4.5% 10% 19%
128 0.8% 2.3% 5.2% 11%

Read the m = 1 row: it is the naive inter-layer case from §1. Naive inter-layer parallelism is just pipelining with a single micro-batch. Everything GPipe adds is in the other rows.

The design rule that follows: you want `m ≫ p`

A common target is m ≥ 4p. But m cannot grow without limit — each micro-batch of size B/m must still be large enough to keep a GPU's SMs busy, and (for GPipe specifically) activation memory grows linearly with m. That tension is what the next two sections are about.

GPipe in code

ScheduleGPipe implements exactly the schedule above. The only two numbers that matter are the ones from the bubble formula — p, set by how you split the model, and m, which you choose.

python
"""
gpipe_demo.py  —  torchrun --standalone --nproc_per_node=4 gpipe_demo.py
"""
import os

import torch
import torch.distributed as dist
import torch.nn.functional as F
from torch.distributed.pipelining import pipeline, SplitPoint, ScheduleGPipe
from transformers import AutoModelForCausalLM, AutoTokenizer

def main():
    rank       = int(os.environ["RANK"])
    local_rank = int(os.environ["LOCAL_RANK"])
    world_size = int(os.environ["WORLD_SIZE"])          # = p, the stage count
    torch.cuda.set_device(local_rank)
    dist.init_process_group("nccl", device_id=torch.device(f"cuda:{local_rank}"))
    device = torch.device(f"cuda:{local_rank}")

    model = AutoModelForCausalLM.from_pretrained("gpt2")
    tok = AutoTokenizer.from_pretrained("gpt2")
    tok.pad_token = tok.eos_token

    # A representative MICRO-batch drives the trace — not the full mini-batch.
    example = tok(["hello world"] * 2, return_tensors="pt",
                  padding="max_length", max_length=128).input_ids

    # GPT-2 small has 12 blocks; three cuts give four stages of three blocks each.
    pipe = pipeline(
        module=model,
        mb_args=(example,),
        split_spec={f"transformer.h.{i}": SplitPoint.BEGINNING for i in (3, 6, 9)},
    )
    stage = pipe.build_stage(rank, device=device)

    def loss_fn(logits, labels):
        return F.cross_entropy(
            logits[..., :-1, :].reshape(-1, logits.size(-1)),
            labels[..., 1:].reshape(-1),
        )

    # m = 16, p = 4  ->  bubble = 3/19 ~ 16%.  Setting m = p would give 43%.
    schedule = ScheduleGPipe(stage, n_microbatches=16, loss_fn=loss_fn,
                             scale_grads=True)   # True because loss_fn AVERAGES

    optimizer = torch.optim.AdamW(stage.submod.parameters(), lr=3e-5, fused=True)

    try:
        for batch in loader:                     # mini-batch of 16 x micro-batch
            optimizer.zero_grad(set_to_none=True)
            ids = batch.to(device)
            if rank == 0:
                schedule.step(ids)               # first stage feeds input
            elif rank == world_size - 1:
                losses = []
                schedule.step(target=ids, losses=losses)   # last stage owns the loss
            else:
                schedule.step()                  # middle stages just relay
            optimizer.step()
    finally:
        dist.destroy_process_group()

if __name__ == "__main__":
    main()
Note — the two numbers, and the mistake almost everyone makes once

n_microbatches is m. world_size is p. They are unrelated, and setting them equal is a common reflex that quietly costs you most of the benefit:

   m = p = 4   ->  bubble = 3/7  ~ 43%     <- barely better than not pipelining
   m = 16, p=4 ->  bubble = 3/19 ~ 16%
   m = 64, p=4 ->  bubble = 3/67 ~  4.5%

If a pipeline run is disappointing, check m before anything else.

Note — the three-branch if rank == is structural, not boilerplate

Data enters at stage 0; labels are only needed at stage p−1, because that is the only stage that can compute a loss; the middle stages have neither. Every pipeline API has this shape in some form. It is also why loss_fn is handed to the schedule rather than called by you — the framework has to own it, since only one rank can run it.

Note — where the point-to-point communication is hiding

Nothing in this script calls send or recv, but every stage boundary is exactly that: activations forward, activation-gradients backward. Two consequences worth carrying:

  • Shapes must be known in advance. recv needs a pre-allocated buffer, which is why the traced example uses padding="max_length". Ragged batches need either padding to a fixed length or an API that exchanges shape metadata first.
  • The transfers must not be issued in an order that deadlocks. The framework uses batch_isend_irecv for you. If you hand-roll a pipeline with blocking send/recv in the same order on both ranks, you get a hang with no error.
Note — historical, and it explains why this API looks the way it does

The first widely-used PyTorch GPipe implementation was torchgpipe (kakaobrain), later upstreamed as torch.distributed.pipeline.sync.Pipe. Both are gone. Both required the model to be an nn.Sequential whose every module took and returned bare tensors — so using them on a Hugging Face model meant rebuilding it: pulling the embedding and LM head out into custom modules, monkeypatching each transformer block to return a tensor instead of a tuple, and hand-specifying a balance=[4, 3, 3, 4] list of module counts per stage.

That balance list is worth one more look before you forget it, because the modern API does not solve the problem it was solving. [4, 3, 3, 4] is not uniform: stage 0 carries the embedding and stage 3 carries the LM head, both heavy for a 50k vocabulary, so those stages get fewer transformer blocks to compensate. You still have to make that judgment — it just moves into split_spec. §3.2 is about how to make it well.

3. 1F1B Pipelining (PipeDream)

PipeDream, released by Microsoft, performs pipelining in a slightly different way from GPipe. This method is commonly called 1F1B: unlike GPipe, which does all the forwards and only then the backwards, PipeDream alternates forward and backward.

   1F1B — p=4, m=8.  After the fill, each stage alternates F and B.

   GPU0  F1 F2 F3 F4 B1 F5 B2 F6 B3 F7 B4 F8 B5 B6 B7 B8
   GPU1   · F1 F2 F3 B1 F4 B2 F5 B3 F6 B4 F7 B5 F8 B6 B7 B8
   GPU2   ·  · F1 F2 B1 F3 B2 F4 B3 F5 B4 F6 B5 F7 B6 F8 B7 B8
   GPU3   ·  ·  · F1 B1 F2 B2 F3 B3 F4 B4 F5 B5 F6 B6 F7 B7 F8 B8
                     ▲
                     backward begins as early as possible
                     → each activation is freed sooner

There are two challenges in 1F1B pipelining:

  1. Weight version managing
  2. Work partitioning

1) Weight version managing

In the case of GPipe, only one weight version is maintained, but a pipeline flush happens periodically. A pipeline flush is the process of updating the parameters using the computed gradients. During this flush no forward or backward computation happens at all, so processing efficiency drops.

   GPipe: flush between mini-batches — everything drains, then updates

   GPU0  FFFF········BBBB │ FFFF········BBBB │ ...
   GPU1  ·FFFF·····BBBB·  │ ·FFFF·····BBBB·  │
   GPU2  ··FFFF··BBBB··   │ ··FFFF··BBBB··   │
   GPU3  ···FFFFBBBB···   │ ···FFFFBBBB···   │
                       ▲
                    flush: update, pipeline empty, everyone idle

PipeDream keeps updating parameters continuously without such a flush. So the idle time in both forward and backward disappears. But to do this, it must continuously manage several versions of the parameter state. If it stored only the latest version of the parameters, then when the output of a previous layer is transmitted to the next layer, the next layer's portion might already have been updated.

To prevent this problem it stores and manages several versions of the weights — but storing weights takes up a lot of memory space. So a trade-off arises here.

  • GPipe: memory-efficient, processing-inefficient
  • PipeDream: memory-inefficient, processing-efficient
Note — what "several weight versions" actually means, and why correctness demands it

The rule that makes backpropagation valid is: the backward pass of micro-batch k must use the same weights its forward pass used. In a flush-free pipeline, other micro-batches' updates land in between, so those weights have moved on.

   time ─────────────────────────────────────────────▶
   stage 1:  F(μ1)                     B(μ1)
             uses W⁽¹⁾                 needs W⁽¹⁾ again
                      ↑                     ↑
                      └── but μ2, μ3 updated the weights to W⁽³⁾ meanwhile
                          → must have STASHED W⁽¹⁾

This is called weight stashing. The cost is real: a stage may need to keep up to p versions of its parameters, so parameter memory is multiplied by roughly the pipeline depth. For a big model that is exactly the memory you were trying to save by pipelining in the first place.

There's a second, subtler cost: even with stashing, vanilla PipeDream's update is stale — the gradient computed from W⁽¹⁾ gets applied to a newer weight vector. That is a genuinely different optimization algorithm from synchronous SGD, with its own convergence behaviour. This is why the two variants in §4 exist, and why almost nobody runs vanilla PipeDream today: the community chose to keep exact synchronous semantics and attack the bubble in other ways.

2) Work Partitioning

The second problem is how to split the neural network. Simply giving each layer group the same number of layers is not always the best solution. What matters most to us is minimizing idle time. For that, the running time of each partition needs to be similar. Beyond that you also have to consider parameter size, activation memory, and so on.

   Balance by TIME, not by layer count.

   naive (equal layer count)          balanced (equal time)
   ┌──────┬──────┬──────┬──────┐      ┌────────┬─────┬─────┬────────┐
   │ emb  │ 4 blk│ 4 blk│ head │      │emb+2blk│4 blk│4 blk│2blk+head│
   │ +4blk│      │      │+4blk │      │        │     │     │        │
   └──────┴──────┴──────┴──────┘      └────────┴─────┴─────┴────────┘
     slow   fast   fast   slow          ~equal   ~equal ~equal ~equal
       ▲                    ▲
       └─ these two gate the whole pipeline

PipeDream finds an optimal partitioning strategy through profiling and optimization.

Note — the slowest stage sets the pace, so imbalance is a multiplier on everything

If one stage is 20% slower than the rest, every other stage idles 20% of the time, on top of the bubble. The three things that make transformer stages unequal:

Cause Effect
Embedding on stage 0 Large parameter table, cheap compute
LM head + loss on stage p−1 [B, S, V] logits — often the single biggest tensor in the model
Uneven layer counts Direct

Practical advice: profile one step, then partition by measured time. DeepSpeed's partition_method="parameters" balances parameter counts, which is a decent proxy but not the same thing. balance=[4,3,3,4] in the GPipe script above is this same reasoning applied by hand.

4. Variations of 1F1B Pipelining

1) PipeDream 2BW (2-buffered weight update)2) PipeDream FlushHold on… what is Activation Memory?The same thing in DeepSpeed, and a trap worth knowing

We introduce two versions of pipeline strategies that improve on PipeDream's 1F1B pipelining.

1) PipeDream 2BW (2-buffered weight update)

PipeDream-2BW appeared in order to improve PipeDream's memory inefficiency. The core idea is to perform gradient accumulation during pipelining. It solves the memory-inefficiency problem by collecting several gradients and performing the update all at once. Unlike before, 2BW only needs to maintain two weight versions.

   PipeDream-2BW: accumulate gradients, update every m micro-batches

   weight versions kept:  W(old)  and  W(new)     ← exactly 2, not p

   μ1 μ2 μ3 μ4 │ μ5 μ6 μ7 μ8 │ μ9 …
   └─ accumulate ┘└─ accumulate ┘
        update        update

2) PipeDream Flush

PipeDream-Flush is a pipelining method that combines 1F1B with a pipeline flush. Because a flush happens, the idle time is similar to GPipe, but the activation memory that must be maintained during the forward-backward process is reduced. Because PipeDream-Flush flushes, there is no need to manage multiple parameter versions. So only a single weight needs to be maintained, making it even more memory-efficient than PipeDream-2BW. (It is the most memory-efficient of the techniques introduced so far.)

(diagrams: ../images/pipe_dream_flush.png, ../images/pipe_dream_flush_2.png)

   GPipe vs PipeDream-Flush — SAME bubble, very different memory

   GPipe        F1 F2 F3 F4 F5 F6 F7 F8 B8 B7 B6 B5 B4 B3 B2 B1
   in flight →  1  2  3  4  5  6  7  8  ← peak = m activations stored

   1F1B-Flush   F1 F2 F3 F4 B1 F5 B2 F6 B3 F7 B4 F8 B5 B6 B7 B8
   in flight →  1  2  3  4  3  4  3  4  ← peak = p activations stored
                                          (independent of m!)
Note — this is the most important table in the chapter

All three schedules have the same bubble; what separates them is memory.

Weight versions Peak activation memory Update semantics
GPipe 1 ∝ m exact, synchronous
PipeDream up to p ∝ p stale/async
PipeDream-2BW 2 ∝ p delayed by 1 step
PipeDream-Flush (1F1B) 1 ∝ p exact, synchronous

The last row is why 1F1B won. It gives you GPipe's exact semantics and single weight copy, and PipeDream's flat activation memory. There is essentially no reason to run GPipe in production.

And the consequence is the one that matters: because activation memory no longer grows with m, you can finally raise m enough to make the bubble small. GPipe couldn't — increasing m to shrink the bubble inflated the activation memory that motivated pipelining. 1F1B breaks that circle.

Hold on… what is Activation Memory?

Most layers store the output values produced in the forward pass before backward is called. Anyone who has used torch.autograd.Function knows this well — the forward layer's outputs are saved in the ctx variable.

python
"""
Reference: https://pytorch.org/tutorials/beginner/examples_autograd/two_layer_net_custom_function.html
"""

import torch

class ReLU(torch.autograd.Function):

    @staticmethod
    def forward(ctx, input):
        ctx.save_for_backward(input)
        # storing the input value

        return input.clamp(min=0)

    @staticmethod
    def backward(ctx, grad_output):
        input, = ctx.saved_tensors
        grad_input = grad_output.clone()
        grad_input[input < 0] = 0
        return grad_input

This is because the values used in the forward pass are needed when computing the gradient. Look at the following example.

   forward: max-pool 4×4 → 2×2            backward: 2×2 grad → 4×4 grad

   ┌────┬────┬────┬────┐                  ┌────┬────┬────┬────┐
   │ 1  │ 3  │ 2  │ 1  │                  │ 0  │ 0  │ 0  │ 0  │
   ├────┼────┼────┼────┤    ┌────┬────┐   ├────┼────┼────┼────┤
   │ 4  │ 2  │ 0  │ 5  │ →  │ 4  │ 5  │   │0.8 │ 0  │ 0  │1.2 │
   ├────┼────┼────┼────┤    ├────┼────┤   ├────┼────┼────┼────┤
   │ 2  │ 1  │ 7  │ 3  │    │ 6  │ 7  │   │ 0  │ 0  │0.5 │ 0  │
   ├────┼────┼────┼────┤    └────┴────┘   ├────┼────┼────┼────┤
   │ 6  │ 0  │ 1  │ 2  │   grad in:       │0.9 │ 0  │ 0  │ 0  │
   └────┴────┴────┴────┘   [[0.8,1.2],    └────┴────┴────┴────┘
                            [0.9,0.5]]
                                    ▲
        To route each gradient to the RIGHT cell you must know
        WHICH cell held the max — i.e. you need the original 4×4.
        So the 4×4 stays in memory until backward runs.

The above shows the max-pooling operation and the computation of its gradient. When performing backward, a (2, 2) tensor like [[0.8, 1.2], [0.9, 0.5]] comes in as input. From this you have to find the gradient matrix on the right, and to do that you absolutely need the (4, 4) tensor received in the forward pass. So that tensor is kept in memory. The memory needed to store the tensors used during forward in order to perform backward is called activation memory.

Note — why activation memory, not parameter memory, is usually the real constraint

Parameter memory is fixed by the model. Activation memory scales with batch size × sequence length × hidden size × number of layers, so it is the term that explodes as you scale your inputs. For a transformer, a useful rough shape is:

   activations per layer  ≈  c · batch · seq_len · hidden      (c ≈ 10–20 without
                                                                fused attention)
   total  ≈  layers × that

Concretely: a 40-layer model, batch 8, sequence 2048, hidden 5120 can run to tens of GB of activations — often more than the parameters, gradients, and optimizer states put together.

Two standard countermeasures, both of which interact with pipelining:

  • Activation checkpointing (gradient checkpointing). Don't store intermediates; store only the stage boundaries and recompute the forward during backward. Typically ~30% more compute for a large memory reduction. This is why torch.utils.checkpoint exists.
  • 1F1B scheduling. Exactly what §4.2 described — cap the number of in-flight micro-batches at p instead of m.

They compose, but apply both carelessly and you can recompute more than necessary.

Now that we know what activation memory is, shall we try PipeDream? PipeDream-Flush is implemented in Microsoft's distributed-processing library DeepSpeed. (Reference: https://github.com/microsoft/DeepSpeed/issues/1110) So let's use DeepSpeed.

The same thing in DeepSpeed, and a trap worth knowing

DeepSpeed's PipelineModule implements 1F1B-with-flush and is still in wide use. It ships its own launcher — deepspeed --num_gpus=n script.py, or the shorter alias ds — which is equivalent to torchrun for single-node jobs.

The example below is worth walking through less for the API than for the configuration trap that follows it.

python
"""
src/pipe_dream.py
"""
import deepspeed
import torch
import torch.nn as nn
from datasets import load_dataset
from deepspeed import PipelineModule
from torch.optim import Adam
from torch.utils.data import DataLoader
from tqdm import tqdm
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch.distributed as dist

# PipelineModule needs an nn.Sequential of tensor-in/tensor-out modules, so a
# Hugging Face model still has to be rebuilt into that shape here — the same
# surgery the historical note in §2 describes. Omitted for brevity.

def collate_fn(batch):
    batch_encoding = tokenizer.pad(
        {"input_ids": batch}, padding="max_length", max_length=1024
    )
    return batch_encoding.input_ids

def batch_fn(data):
    input_ids = data
    labels = data
    return input_ids, labels

def loss_fn(logits, labels):
    logits = logits[..., :-1, :].contiguous()
    labels = labels[..., 1:].contiguous()

    return nn.CrossEntropyLoss()(
        logits.view(-1, logits.size(-1)),
        labels.view(-1),
    )

if __name__ == "__main__":
    dist.init_process_group("nccl")
    world_size, rank = dist.get_world_size(), dist.get_rank()
    batch_size, train_steps = 16, 300
    train_samples = batch_size * train_steps

    tokenizer = AutoTokenizer.from_pretrained("gpt2")
    tokenizer.pad_token = tokenizer.eos_token

    model = PipelineModule(
        create_model_from_pretrained(model_name="gpt2"),
        loss_fn=loss_fn,
        num_stages=world_size,
        partition_method="type:GPT2Block"
        # partition_method lets you choose which layers to parallelize.
    )
    engine, optimizer, _, _ = deepspeed.initialize(
        model=model,
        optimizer=Adam(model.parameters(), lr=3e-5),
        config={
            "train_batch_size": batch_size,
            "steps_per_print": 9999999,
            # turn off: https://github.com/microsoft/DeepSpeed/issues/1119
        },
    )
    engine.set_batch_fn(batch_fn)

    datasets = load_dataset("rajpurkar/squad")["train"]["context"][:train_samples]
    datasets = [
        tokenizer(data, return_tensors="pt", max_length=1024).input_ids[0]
        for data in tqdm(datasets)
    ]
    data_loader = iter(
        DataLoader(
            sorted(datasets, key=len, reverse=True),
            # uniform length batching
            # https://mccormickml.com/2020/07/29/smart-batching-tutorial/
            batch_size=batch_size,
            num_workers=8,
            collate_fn=collate_fn,
            shuffle=False,
        )
    )

    for i in range(train_steps):
        loss = engine.train_batch(data_loader)

        if i % 10 == 0 and rank == 0:
            print(f"step: {i}, loss: {loss}")
bash
$ ds --num_gpus=4 ../src/pipe_dream.py
[INFO] [engine.py:77:__init__] CONFIG: micro_batches=1 micro_batch_size=16
Read that log line carefully: `micro_batches=1`. This example is not actually pipelining

DeepSpeed derives the micro-batch count from an identity:

train_batch_size = train_micro_batch_size_per_gpu
                 × gradient_accumulation_steps
                 × data_parallel_world_size

Here all 4 GPUs are pipeline stages, so data_parallel_world_size = 1. With only train_batch_size: 16 specified, DeepSpeed solves the identity as 16 = 16 × 1 × 1 — giving one micro-batch, i.e. m = 1.

From the bubble table in §2, m=1, p=4 is a 75% bubble. This run is the naive inter-layer schedule of §1, with all of pipelining's machinery and none of its benefit.

The fix is to pin the micro-batch size so accumulation steps become the micro-batch count:

python
config={
    "train_batch_size": 16,
    "train_micro_batch_size_per_gpu": 1,   # → gradient_accumulation_steps = 16
    "steps_per_print": 9999999,
}

That gives m = 16, p = 4, bubble ≈ 16%. Always check the micro_batches= value DeepSpeed prints at startup — it is the single number that determines whether your pipeline is working.

Note — three other things this script quietly teaches
  1. engine.train_batch() replaces the whole loop. No forward, no loss.backward(), no optimizer.step() — the engine drives the schedule, pulling micro-batches from the iterator itself. This is characteristic of pipeline APIs: the schedule owns control flow, and you hand it a data source rather than a batch.
  2. loss_fn is passed to PipelineModule, not called by you. The loss can only be computed on the last stage, so the framework needs to own it. Same reason batch_fn exists — it tells the engine how to derive (inputs, labels) from one dataset item.
  3. padding="max_length", max_length=1024 — every sequence padded to full length. This looks wasteful, and for ordinary training it would be. Here it's deliberate: recv needs a pre-allocated buffer of known shape, so pipelines strongly prefer fixed shapes. Combined with the sort-by-length "uniform length batching" trick, this is the script working around the shape-rigidity of P2P transfer that notebook 03 warned about.
Note — partition_method options

"type:GPT2Block" splits so that each stage gets an equal number of modules of that class — i.e. balance by transformer block. Alternatives: "parameters" (balance parameter counts, the usual default choice) and "uniform" (equal module counts). None of them balance by measured time, which is what you actually want; for serious runs, profile and specify the partition explicitly.

5. Interleaved Scheduling

Previously, one stage (a set of contiguous layers) was computed sequentially to produce the result. For example, if there are 8 layers and 2 devices, normally layers 1–4 would be assigned to device 1 and layers 5–8 to device 2. Then device 1 would process layers 1 through 4 sequentially and emit the output. (Both GPipe and 1F1B work this way.)

   contiguous (standard)                interleaved (v = 2 chunks/device)

   GPU0 │ layers 1 2 3 4 │             GPU0 │ layers 1 2 │ … │ layers 5 6 │
   GPU1 │ layers 5 6 7 8 │             GPU1 │ layers 3 4 │ … │ layers 7 8 │

   each device = 1 contiguous block     each device = v non-contiguous chunks

However, interleaved scheduling overlaps a single stage in order to reduce bubble time to the extreme. For example, if device 1 is assigned layers 1–4, it performs layers 1–2 and layers 3–4 concurrently. This reduces bubble time, but communication cost increases, so it needs to be tuned carefully. (A trade-off exists.)

Note — what interleaving actually does to the numbers

Each device holds v "virtual stages" instead of one. The pipeline is effectively v times deeper in scheduling terms while using the same devices, so micro-batches flow through more, smaller steps and the fill/drain overlap much better:

bubble fraction = (p−1) / (v · m + p − 1)
v=1 (standard) v=2 v=4
p=8, m=32 18% 10% 5.2%
p=8, m=64 10% 5.2% 2.7%
p=16, m=64 19% 10% 5.5%

The cost: v times as many P2P transfers, because activations now cross a device boundary at every chunk edge instead of every stage edge. On NVLink that's usually a good trade; over slower inter-node links it can wipe out the gain. Megatron-LM uses interleaved 1F1B by default for large runs, with v = 2 being the common choice.

Note the naming: this is "virtual pipeline stages" or "looped" scheduling in the literature. In PyTorch it's ScheduleInterleaved1F1B.

6. The schedule zoo, compared

Every schedule discussed above, plus the zero-bubble family, in one place.

Schedule Year Bubble Activation memory Weight versions Semantics
Naive inter-layer — (p−1)/p (75% at p=4) ∝ 1 1 exact
GPipe 2018 (p−1)/(m+p−1) ∝ m 1 exact
PipeDream (1F1B async) 2019 ~0 (no flush) ∝ p up to p stale
PipeDream-2BW 2020 ~0 ∝ p 2 delayed
PipeDream-Flush (1F1B) 2020 (p−1)/(m+p−1) ∝ p 1 exact
Interleaved 1F1B 2021 (p−1)/(vm+p−1) ∝ p 1 exact
Zero-bubble (ZB-H1/H2) 2023 → ~0 ∝ p 1 exact
DualPipe 2024 → ~0 higher 1 exact
Note — the zero-bubble idea, which is genuinely clever

Everything above treats "backward" as one atomic block. It isn't. A backward pass is really two computations:

   B  =  B_input  (∂L/∂x, gradient w.r.t. the layer INPUT)
      +  B_weight (∂L/∂W, gradient w.r.t. the WEIGHTS)

Only B_input is on the critical path — the previous stage is blocked waiting for it. B_weight is needed only before the optimizer step, which is at the very end of the mini-batch. So you can defer B_weight and use it to fill the bubble:

   1F1B          F F F F  B B B B          ← bubble at fill and drain
   zero-bubble   F F F F  Bi Bi Bi Bi
                          Bw Bw Bw Bw      ← Bw slotted into the idle slots
                 └── the drain is now doing useful work ──┘

The schedules that do this (ScheduleInterleavedZeroBubble, ScheduleZBVZeroBubble) can drive the bubble close to zero while keeping exact synchronous semantics. ScheduleDualPipeV (from DeepSeek's training stack) goes further by running two pipelines in opposite directions and overlapping their bubbles with each other's communication.

Choosing, in one line each:

  • Learning / debugging → GPipe. Simplest to reason about.
  • Default production choice → 1F1B.
  • Deep pipeline (p ≥ 8) with fast interconnect → Interleaved 1F1B.
  • Squeezing the last few percent, willing to accept complexity → zero-bubble family.
Note — DualPipeV, in one paragraph, since PyTorch now ships it

ScheduleDualPipeV implements the schedule DeepSeek published alongside V3. It runs two pipelines in opposite directions over the same devices and overlaps each one's bubble against the other's communication. In practice the gain over interleaved 1F1B comes mostly from hiding expert-parallel all_to_all traffic in MoE models — which is why it shows up in MoE training stacks rather than dense ones. torchtitan's implementation dispatches the overlapped forward and backward on separate threads to two CUDA streams, one for compute and one for EP communication. If you are not training an MoE over a slow interconnect, interleaved 1F1B is very likely enough.

  • Never → vanilla async PipeDream. Stale gradients aren't worth it.

7. Pipeline parallelism in PyTorch today

§2 showed ScheduleGPipe. Here is the full picture: the same setup, with any schedule from §6 swappable on one line, and the pieces you need once you compose pipelining with the other axes in chapter 09.

python
"""
torchrun --standalone --nproc_per_node=4 pipe_modern.py
"""

import os

import torch
import torch.distributed as dist
from torch.distributed.pipelining import pipeline, SplitPoint, Schedule1F1B
from transformers import AutoModelForCausalLM, AutoTokenizer

def main():
    rank = int(os.environ["RANK"])
    local_rank = int(os.environ["LOCAL_RANK"])
    world_size = int(os.environ["WORLD_SIZE"])
    torch.cuda.set_device(local_rank)
    dist.init_process_group("nccl")
    device = torch.device(f"cuda:{local_rank}")

    model = AutoModelForCausalLM.from_pretrained("gpt2")
    tok = AutoTokenizer.from_pretrained("gpt2")
    tok.pad_token = tok.eos_token

    # a representative MICRO-batch drives the trace
    example = tok(["hello world"] * 2, return_tensors="pt",
                  padding="max_length", max_length=128).input_ids

    # 1. declare the cut points — no nn.Sequential rewrite needed
    pipe = pipeline(
        module=model,
        mb_args=(example,),
        split_spec={
            "transformer.h.3": SplitPoint.BEGINNING,
            "transformer.h.6": SplitPoint.BEGINNING,
            "transformer.h.9": SplitPoint.BEGINNING,
        },
    )

    # 2. materialize only THIS rank's stage
    #    build_stage(stage_index, device, group) — pass the PP group explicitly
    #    once you are composing PP with other axes (chapter 09)
    stage = pipe.build_stage(rank, device=device)

    # 3. attach a schedule.  n_microbatches is `m` — keep it >> p
    def loss_fn(logits, labels):
        return torch.nn.functional.cross_entropy(
            logits[..., :-1, :].reshape(-1, logits.size(-1)),
            labels[..., 1:].reshape(-1),
        )

    schedule = Schedule1F1B(
        stage,
        n_microbatches=16,
        loss_fn=loss_fn,
        scale_grads=True,    # must match your loss_fn: True if it AVERAGES, False if it SUMS
    )

    optimizer = torch.optim.AdamW(stage.submod.parameters(), lr=3e-5)

    try:
        for batch in loader:                       # batch of 16 × micro-batch size
            optimizer.zero_grad(set_to_none=True)
            ids = batch.to(device)
            if rank == 0:
                schedule.step(ids)                 # first stage feeds input
            elif rank == world_size - 1:
                losses = []
                schedule.step(target=ids, losses=losses)   # last stage owns the loss
            else:
                schedule.step()                    # middle stages just relay
            optimizer.step()
    finally:
        dist.destroy_process_group()

if __name__ == "__main__":
    main()
Note — what to notice about this API
Older APIs (torchgpipe, pipeline.sync) torch.distributed.pipelining
Model shape must be nn.Sequential, tensors only any nn.Module; traced
Splitting balance=[4,3,3,4] by module count split_spec by module name
Processes one process, many devices one process per stage
Multi-node no yes
Schedules GPipe only GPipe, 1F1B, interleaved, zero-bubble, DualPipe
Loss you compute it loss_fn passed to the schedule
Composes with DP/TP awkward via DeviceMesh
Gradient scaling manual scale_grads= on the schedule

The three-branch if rank == 0 / elif last / else is characteristic and worth internalizing: the first stage has data, the last stage has labels, the middle has neither. It's the same asymmetry as input_ids.to(0) / labels.to(world_size-1) in the 2021 script, just made explicit.

Swap Schedule1F1B for ScheduleGPipe to reproduce §2, or ScheduleInterleaved1F1B for §5. Only that one line changes.

Two live caveats, as of PyTorch 2.13
  1. torch.distributed.pipelining is still labelled alpha. It has been stable enough that torchtitan builds on it and it is the recommended path, but the docs continue to warn that API changes are possible. Pin your PyTorch version for a long run.
  2. scale_grads must match your loss function. It defaults to True, which divides gradients by n_microbatches — correct if your loss_fn averages over the micro-batch. If your loss sums, set scale_grads=False. Getting this wrong silently scales your effective learning rate by m, which is exactly the class of bug §4's DeepSpeed micro_batches=1 finding belongs to: no error, just a different training run.

8. Making it actually work

Note — the failure modes, roughly in order of how often they occur
Symptom Cause Fix
Barely faster than 1 GPU m too small — check the printed micro-batch count Raise m to ≥ 4p
One GPU pegged, others idle Stage imbalance Profile per-stage time; repartition
Hang at a stage boundary Shape mismatch between send and recv Fix shapes; pad to a constant length
Deadlock during the fill Blocking send/recv in the same order on both sides batch_isend_irecv (frameworks do this for you)
OOM on the first stage under GPipe Activation memory ∝ m Switch to 1F1B; add activation checkpointing
OOM on the last stage The [B, S, V] logits tensor Fuse loss with the projection; shrink m's micro-batch
Loss is None on most ranks Loss exists only on the last stage Gather it, or log from the last rank
Accuracy differs from single-GPU BatchNorm under micro-batching Use LayerNorm/RMSNorm, or SyncBatchNorm
Note — how pipeline parallelism combines with the other axes

Pipelining is rarely used alone. The standard 3-D layout from chapter 04:

   TP inside a node (NVLink, chatty)
   PP across nodes  (InfiniBand, one activation per boundary)
   DP on top        (one gradient reduction per step)

   64 GPUs = 8 nodes × 8:   TP=8, PP=4, DP=2
   → each pipeline stage is one whole node
   → each of the 4 stages talks to the next over the network
   → the two pipeline replicas all-reduce gradients with each other

Pipelining tolerates slow links better than tensor parallelism because it moves one activation tensor per stage boundary per micro-batch, versus TP's several collectives per layer. That is precisely why PP goes across nodes and TP stays inside one.

Note — the memory/bubble trade-off, stated as a procedure
  1. Pick p = the smallest number of stages that makes the model fit. Every extra stage costs bubble.
  2. Pick m ≥ 4p, as large as you can while each micro-batch still saturates a GPU.
  3. Use 1F1B so step 2 doesn't blow up activation memory.
  4. If the bubble is still hurting and your interconnect is fast, go interleaved (v=2).
  5. Only then consider zero-bubble.
Note — a sanity check that catches most misconfigurations

Before trusting a pipeline run:

   expected step time  ≈  (single-GPU step time for the whole model)
                          × (1 + bubble fraction)
                          / 1                     ← PP gives no compute speedup!

Pipeline parallelism does not make a fixed amount of work finish faster in the way data parallelism does — it makes a model fit that otherwise wouldn't, and keeps the devices busy while doing so. If you're benchmarking PP expecting linear speedup, you're measuring the wrong thing.
