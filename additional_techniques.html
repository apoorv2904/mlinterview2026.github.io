Section 1 of 7

1. Kernel Fusion

What is a kernel?What is fusion?But…

Kernel fusion is a method of improving computation speed using custom code implemented in CUDA.

What is a kernel?

Think of a kernel as code that runs directly on the GPU device. CUDA has the following syntax:

__device__ void func(){...}

__global__ void func(){...}

__host__ void func(){...}

Functions with a prefix like __global__ or __device__ run on the GPU, while functions with __host__ or with nothing attached run on the CPU. Code that includes a prefix like __global__ or __device__ and runs on the GPU is what we usually call a "kernel."

Note — the one distinction that matters:

__global__ is callable from the host, runs on the device — it's the entry point you launch (kernel<<<blocks, threads>>>(...)). __device__ is callable from the device only — a helper. So the thing you "launch" is always a __global__ function, and each launch has a fixed overhead of a few microseconds. That overhead is half of what fusion eliminates.

What is fusion?

Generally we build models by combining the small operations PyTorch provides. For example we combine torch.matmul and torch.add to make an operation like y = torch.matmul(x, w) + b. Likewise we combine torch.split, torch.permute and so on to implement Transformer head split & merge. This approach is easy to implement and clean, but analyzing it internally it's quite inefficient.

Suppose we ran an operation like torch.matmul(x, w) * b. First, torch's host code loads tensors x and w in order to run the kernel corresponding to torch.matmul (cuBLAS). Then it stores the computed result. Second, to compute * b, it loads the just-stored result of matmul(x, w) and b, computes, and stores the result again.

Something seems inefficient. Couldn't we load x, w, b all at once, finish all the computation, and store once? Unfortunately torch needs to provide operations in as small units as possible for the user's freedom. So, apart from a few operations, this load/store process is repeated unnecessarily. But if we know how to write CUDA code we don't need to use torch's kernels — we can just implement a kernel that loads x, w, b at once, computes, and stores. So many CUDA programmers implement things by fetching all needed parameters, computing, and storing once, in order to reduce unnecessary load/store and function-call overhead.

   UNFUSED:  three kernels, three round trips to HBM

   HBM ──load x,w──▶ [matmul kernel] ──store──▶ HBM
   HBM ──load t,b──▶ [mul kernel]    ──store──▶ HBM
   HBM ──load u  ──▶ [gelu kernel]   ──store──▶ HBM
                          ▲
              6 HBM traversals + 3 launch overheads

   FUSED:    one kernel, one round trip

   HBM ──load x,w,b──▶ [ matmul → mul → gelu ]  ──store──▶ HBM
                        ▲ intermediates stay in registers/SRAM
              2 HBM traversals + 1 launch overhead
Note — why this matters so much: almost nothing in a transformer is compute-bound

The relevant number is arithmetic intensity — FLOPs performed per byte moved. An A100 does ~312 TFLOPS bf16 but only ~2 TB/s of HBM bandwidth, a ratio of roughly 150 FLOPs per byte. Any operation doing less arithmetic than that per byte it touches is memory-bound: the GPU's compute units sit idle waiting on memory.

Operation FLOPs per byte Bound by
Large matmul hundreds compute ✓
LayerNorm ~2 memory
GeLU / activation ~1 memory
Dropout <1 memory
Elementwise add ~0.3 memory
Softmax ~2 memory

So the majority of the operations in a transformer are memory-bound. For those, the only thing that matters is how many times you traverse HBM — and fusion is precisely the technique that reduces that count. This is why fusion often yields 1.5–3× on real models: you are not making the arithmetic faster, you are removing trips to memory that were never necessary.

But…

Writing CUDA from scratch is beyond this chapter's scope. What follows instead is the set of transformer kernels that were the standard recommendations, and then what replaced them.

the idea won; the list didn't

Every project above is either archived, absorbed, or superseded. Apex is unmaintained, LightSeq is inactive, FasterTransformer was folded into TensorRT-LLM. But the principle — fuse to reduce HBM traffic — became one of the central ideas of modern ML systems. Four things replaced them:

1. FlashAttention — fusion applied to attention, and the single biggest win of the era.

Standard attention materializes the [batch, heads, seq, seq] score matrix in HBM. At seq=8192 that's ~1 GB per head per layer, and writing/reading it dominates the cost. FlashAttention tiles the computation so the score matrix is never written out at all — it uses an online-softmax reformulation to accumulate the result in SRAM:

   standard:   Q,K ──▶ S = QKᵀ ──store──▶ HBM ──load──▶ softmax ──store──▶ HBM ──▶ ·V
                                 ▲ O(seq²) memory traffic

   FlashAttn:  Q,K,V ──▶ [ tiled: QKᵀ → online softmax → ·V, all in SRAM ] ──▶ O
                                 ▲ O(seq) memory traffic, exact same result

It is exact, not an approximation. Memory drops from O(seq²) to O(seq), which is what made long contexts practical at all. You get it for free:

python
# PyTorch dispatches to a Flash kernel automatically
out = torch.nn.functional.scaled_dot_product_attention(q, k, v, is_causal=True)

# packed / ragged batches without padding (PyTorch >= 2.10)
from torch.nn.attention import varlen_attn
out = varlen_attn(q, k, v, cu_seq_q, cu_seq_k, max_q, max_k,
                  window_size=(-1, 0))    # causal; is_causal was removed in 2.11

The lineage now runs to FlashAttention-4, which PyTorch 2.11 exposes as a FlexAttention backend on Hopper and Blackwell. If you use scaled_dot_product_attention or FlexAttention you get whichever generation your hardware and version support, without changing code — which is the point.

2. torch.compile — fusion without writing CUDA.

The compiler traces your model, fuses memory-bound operation chains, and generates Triton kernels automatically. One line:

python
model = torch.compile(model)

Typically 1.1–1.5× on transformers, more on models with many small elementwise ops. You no longer need to write CUDA to get fusion.

3. Triton — writing kernels in Python.

When the compiler isn't enough, you write the kernel yourself in Python-like Triton rather than CUDA C++. Most custom kernels published today (including FlashAttention variants) are Triton.

4. Transformer Engine — fused transformer layers with fp8.

NVIDIA's current answer for Hopper and later: pre-fused attention and MLP blocks plus automatic fp8 scaling. It's what Megatron Core uses now, and it's the direct successor to the Apex kernels listed above.

5. nn.LinearCrossEntropyLoss — fusion applied to the loss.

The last layer of a language model produces [batch, seq, vocab] logits purely so cross-entropy can consume them. For a 128k vocabulary that tensor, plus its fp32 softmax intermediate, is routinely the largest allocation in the model. PyTorch 2.13 fuses the projection and the loss so it is never materialized:

python
# functional form: use when the projection weight already exists (a tied lm_head)
loss = torch.nn.functional.linear_cross_entropy(
    hidden_states, lm_head.weight, targets)

# module form: owns its own weight, so it is built with the shapes instead
loss_fn = torch.nn.LinearCrossEntropyLoss(hidden_size, vocab_size)
loss    = loss_fn(hidden_states, targets)

Reported at up to 4× lower peak memory for large-vocabulary LM training. This is the same insight as §1 — don't write an intermediate to HBM if you can consume it in place — applied to the one tensor where it pays most.

Also fused, and easy to forget: optimizers. torch.optim.AdamW(..., fused=True) collapses the entire per-parameter update into one kernel instead of dozens of small elementwise launches. Free, and worth a few percent. As of 2.12, Adagrad joined Adam, AdamW, and SGD in having a fused implementation.

2. Progressive Layer Dropping (PLD)

Progressive Layer Dropping is a method that randomly skips layers to improve training speed and performance. The paper's authors say they obtained the following two insights from BERT's training process.

  • Early in training, the difference in L2-norm and cosine similarity between a layer's input and output is large, but it gets smaller toward the end of training.
  • That is, early in training many things are newly learned and changed, but late in training it appears to make only fine corrections.
  • For Pre-LN models, the earlier layers have a fairly large difference between input and output, but the later layers produce almost the same output.
  • Toward the later layers it appears to make only very fine corrections without greatly changing the existing result.

Based on this, they implement dropping of some layers during training to improve training speed and performance. Based on the insights from experiments, they report good performance from dropping relatively less in the parts considered important for training (early in training / earlier layers) and dropping frequently in the parts considered less important (late in training / later layers).

Dropping decides whether or not to drop a layer using a gate function G = {0, 1}.

When the gate function points to 0, it is implemented so that only an identity mapping is passed to the next layer.

   G = 1                              G = 0
   x ──▶ [ Attention + MLP ] ──▶ y    x ──────────────────────▶ x
              (computed)                    (identity — skipped)

This is a feature currently included in DeepSpeed, but it isn't yet compatible with ZeRO and so on, so it is hard to use when actually developing large-scale models. For more detail see the paper https://arxiv.org/abs/2010.13369.

Note — why this only works with Pre-LN, which is worth understanding

The insight depends on the residual structure:

   Post-LN:  x → LayerNorm(x + Sublayer(x))     removing Sublayer changes what LN sees
   Pre-LN:   x → x + Sublayer(LayerNorm(x))     removing Sublayer leaves exactly x
                  ▲ the residual path is a clean identity

Under Pre-LN, G=0 is a genuine no-op — the signal passes through untouched. Under Post-LN it isn't, because the normalization would be applied to a different quantity. This is one of several reasons essentially every modern transformer is Pre-LN.

PLD faded, and the reason it faded is instructive

It is not in any mainstream recipe now. Three reasons:

  1. The ZeRO incompatibility was never resolved, and stochastic-depth-style tricks compose badly with pipeline parallelism too (a dropped layer changes stage timing, which breaks the pipeline balance).
  2. Compute stopped being the binding constraint in the way it was for BERT-era models. For LLM pre-training the constraints are memory, bandwidth, and data, and PLD doesn't help with any of them.
  3. Scaling-law thinking took over. If you have a compute budget, the literature says spend it on more tokens through the full model rather than fewer FLOPs per token. Skipping layers means training a slightly different, weaker model.

The closely related idea that did survive is layer dropout / stochastic depth as a regularizer for fine-tuning smaller models, where it's about generalization rather than speed. And the underlying observation — later layers change their input less — turned out to be robust and now motivates entirely different work: layer pruning, early-exit inference, and speculative decoding with a truncated draft model.

3. 1-Bit Compressive Optimizers

  • 1-bit Adam
  • 1-bit LAMB

1-bit compressive optimizers are a technique that compresses the momentum of optimizers like Adam to 1 bit. Gradients and optimizer states are data that distributed devices exchange frequently and that can become a communication bottleneck. So for SGD, a technique was applied of compressing the momentum term to 1 bit for communication and then correcting the error in post-processing, improving communication speed. For Adam it was hard to apply this technique because the variance term has a nonlinearity — but 1-bit Adam solved this problem with one trick, and showed good performance even with compressed data.

The method was: run uncompressed for the first several steps, and once it reaches a certain stage, transmit the variance term as simply a fixed constant and compress only the momentum term properly, transmitting it like SGD. This technique shows the same convergence rate as uncompressed Adam and, as a result, can reduce communication volume by up to 5×. For more detail see the paper https://arxiv.org/abs/2102.02888.

   phase 1: warm-up          phase 2: compressed
   ────────────────          ───────────────────
   full-precision Adam       variance v ← FROZEN at its warm-up value
   collect v until it        momentum m ← compressed to 1 bit/element
   stabilizes                             + error feedback
Note — the "one trick" is worth stating precisely, because it's a nice observation

Adam's update is

   w ← w − lr · m / (√v + ε)

m is a linear accumulation of gradients, so compressing it and correcting the residual afterwards works — errors accumulate additively and can be fed back. v accumulates g² and appears under a square root in a denominator, so compression error passes through a nonlinearity and cannot be corrected the same way.

The trick: v stops changing much after early training. So freeze it. Once frozen, Adam's update becomes linear in m, and the whole SGD-with-error-feedback compression machinery applies unchanged.

Note — what "error feedback" means

Naively transmitting sign(m) loses everything. Error feedback keeps the residual locally and adds it into the next step's value:

   e ← 0
   each step:
       to_send  = compress(m + e)      # 1 bit per element
       e        = (m + e) − to_send    # remember what compression discarded
       transmit to_send

Nothing is permanently lost; it's only delayed. That's why convergence is preserved. The same idea underpins PowerSGD and most other gradient-compression schemes.

still valid, rarely needed, and largely displaced

1-bit Adam remains in DeepSpeed and still works. But it addresses communication volume, and three things changed:

  1. Interconnects got much faster. NVLink 4/5 and 400 Gb/s InfiniBand mean most jobs are not network-bound. Compressing what wasn't the bottleneck buys nothing.
  2. bf16 gradient reduction halved the traffic for free, with no algorithmic risk. model.register_comm_hook(state=None, hook=hooks.bf16_compress_hook) is one line and needs no warm-up phase or frozen variance.
  3. The pressing problem turned out to be optimizer memory, not optimizer communication. The techniques that won there are different:
Goal 2021 Today
Less optimizer communication 1-bit Adam bf16 comm hook; PowerSGD if truly network-bound
Less optimizer memory — 8-bit optimizers (bitsandbytes): 12Ψ → ~3Ψ
Less optimizer memory (extreme) — paged optimizers; or LoRA — no optimizer state for frozen weights at all
python
import bitsandbytes as bnb
optimizer = bnb.optim.AdamW8bit(model.parameters(), lr=3e-5)

Block-wise quantization of the optimizer states to 8 bits, with reported quality parity. That is the technique from this family that actually became common.

4. Curriculum Learning

Curriculum learning mirrors human learning in neural-network training. Humans learn easy things first when young and gradually learn harder things as they get older. But modern neural-network training has no such tendency. So we train the network similarly — showing easy samples early and hard samples later.

Then how do we distinguish hard samples from easy ones? The paper's authors applied this to GPT model pre-training, and simply considered long samples to be hard and short samples to be easy. In Megatron-LM all samples are trained concatenated together, so early in training they deliberately chunk the input data and feed it in short form, and as training progresses they feed progressively longer samples.

   sequence length over training

   2048 │                                    ┌──────────────
        │                             ┌──────┘
        │                      ┌──────┘
        │               ┌──────┘
    128 │───────┬───────┘
        └───────────────────────────────────────────────▶ steps

It's a very simple method but showed quite surprising performance. Looking at the graph, you can see the loss measured is lower when curriculum learning is applied. Curriculum learning is implemented in DeepSpeed. For details see the paper https://arxiv.org/abs/2108.06084.

Note — there is a second, purely mechanical benefit, and it may be the larger one

Attention costs O(seq²). Training at length 128 instead of 2048 is 256× cheaper per token of attention, and the memory footprint shrinks correspondingly, so you can use a much larger batch. In other words, sequence-length curriculum isn't only pedagogically motivated — the early phase is nearly free:

   early phase:  short seq → cheap attention → big batch → many steps per hour
   late phase:   long seq  → the model already knows the easy structure

Some of the reported gain is likely "you got far more optimizer steps for the same wall-clock time," independent of any curriculum effect. Both effects are real and they point the same direction.

Note — the stability argument, which is why this survived

Early training is where large runs diverge. Short sequences give lower-variance gradients (less positional extrapolation, less long-range signal to fit), which makes the fragile first few thousand steps much better behaved. Practitioners often reach for length warmup specifically as a divergence remedy, not a speed one.

this one aged *well*, and generalized

Of the four techniques in this chapter, curriculum learning is the one that grew rather than faded — but it broadened from "sequence length" to the whole data pipeline:

Form What it schedules
Sequence-length warmup The classic form. Common in large runs, often for stability
Data mixture scheduling Change which corpora you sample from over training — e.g. more web early, more code/math/curated late. Standard in modern pre-training
Annealing / mid-training A final phase on high-quality data at low LR. Now a routine part of the recipe
Quality filtering + dedup Not a curriculum, but the same insight: which tokens you show matters as much as how many
Batch-size ramp Grow the batch as the critical batch size grows during training

The through-line is that data ordering and composition are first-class training decisions, not preprocessing details. In 2021 that was a paper; now it's a standard part of how large models get trained.

DeepSpeed's implementation still exists (data_efficiency config); most large projects implement their own scheduling in the data loader.

5. What actually matters now

The four techniques above were a reasonable shortlist in their day. Here is what a comparable list looks like now, roughly ordered by how much difference each makes on a typical training job.

Tier 1 — do these on every job

Technique Gain Effort
bf16 mixed precision 2–3× one line
FlashAttention (scaled_dot_product_attention / FlexAttention) large; enables long context at all usually automatic
torch.compile 1.1–1.5× one line
Fused loss (nn.LinearCrossEntropyLoss) up to 4× peak memory on large vocab one line
Fused optimizer (AdamW(fused=True)) few % one argument
Fix the data loader often 1.5×+ num_workers, pin_memory, tokenize in collate_fn
Activation checkpointing (selective) large memory saving one line
Sequence packing up to ~30% of wasted tokens recovered preprocessing
Note — "fix the data loader" is on this list for a reason

It's unglamorous and it is very frequently the actual bottleneck. A cluster of 64 H100s starved by single-threaded Python tokenization is a common and expensive sight. Profile the input pipeline before optimizing kernels.

Tier 2 — architecture choices that are now standard

Choice Why it won
RoPE (rotary position embeddings) Extrapolates better than learned absolute; no position table
RMSNorm Cheaper than LayerNorm (no mean subtraction), works as well
SwiGLU Better quality per parameter than GeLU MLP
GQA (grouped-query attention) Shrinks the KV cache ~8× — the dominant inference cost
Pre-LN (+ often QK-norm) Trainability at depth; enables residual tricks like §2
Untied embeddings at scale Weight tying helps small models, hurts large ones

Note that RoPE and RMSNorm appear in chapter 09 as GPT-NeoX novelties. Four years later they're the default in essentially every open model — a good measure of how fast the modelling layer moved while the parallelism layer stood still.

Tier 3 — capacity and memory

Technique What it buys
MoE More parameters at constant FLOPs per token. Costs all_to_all and load-balancing complexity
8-bit optimizers (bitsandbytes) 12Ψ → ~3Ψ of optimizer state
fp8 training (Hopper+, Transformer Engine) ~2× over bf16 on supported hardware; needs per-tensor scaling. FP4 is now available on Blackwell via Transformer Engine and Megatron Core
LoRA / QLoRA Fine-tune 0.1% of parameters. Removes optimizer state for the rest entirely
Context parallelism (Ring Attention) 100k+ token contexts
Note — LoRA deserves emphasis because it reframes the whole memory problem for fine-tuning

Freeze the base weights; train small low-rank adapters ΔW = BA with rank ≪ dim:

   full fine-tune of 7B:   16 bytes/param × 7e9  = 112 GB
   LoRA (r=16) on 7B:      base in 4-bit ≈ 3.5 GB
                         + adapters ~20M params × 16 bytes ≈ 0.3 GB
                         ≈ 4 GB total

Chapters 07–09 exist because 112 GB doesn't fit. If your task is fine-tuning rather than pre-training, LoRA can make the entire question disappear. It does not help with pre-training, where you genuinely need to move all the weights.

Tier 4 — training dynamics

Technique Why
LR schedule (warmup + cosine or WSD) The single most impactful hyperparameter decision
Batch-size ramp Critical batch size grows during training
muP / spectral scaling Transfer hyperparameters from small proxies to large runs. On the Megatron Core roadmap as first-class support
Muon and other emerging optimizers Active area since 2024; Megatron Core is adding distributed Muon. Muon also halves optimizer-state memory (one moment, not two) on 2-D weights — chapter 04 §2 has the arithmetic. Treat as promising, not settled

Data quality, dedup, mixture Often larger effect than any systems optimization
Note — the honest ranking

If you are trying to make a large training run better and you have limited time, the ordering that tends to hold is:

   1. data quality and mixture          ← largest effect, least discussed
   2. LR schedule and stability
   3. the Tier-1 systems list above
   4. architecture details
   5. exotic optimizers and compression  ← where this chapter's §2 and §3 sit

The 2021 chapter's four techniques are all in tier 5. That's not a criticism of the chapter — it's what the frontier looked like before FlashAttention and torch.compile existed.

Section 6 of 7

6. An ordered tuning checklist

When the job is too slow, in order:

  1. Profile first. torch.profiler with a trace. Are you compute-bound, memory-bound, communication-bound, or data-starved? Guessing wastes days.
  2. Check GPU utilization. Below ~90% and steady → data pipeline. Sawtooth → synchronization stalls (look for .item() in the loop).
  3. bf16 + FlashAttention + torch.compile. Three lines, usually the largest wins available.
  4. Raise micro-batch size until memory-limited; use gradient accumulation for the rest of the global batch.
  5. Fused optimizer, zero_grad(set_to_none=True), remove per-step .item() calls.
  6. Communication: is comm overlapping compute? If not — check overlap_comm (DeepSpeed), bucket sizes, and find_unused_parameters.
  7. Check the parallel layout: is TP spanning nodes? Is the pipeline bubble what you predicted?
  8. Only then consider compression, exotic optimizers, or custom kernels.

When the job doesn't fit, in order:

  1. Smaller micro-batch + gradient accumulation.
  2. Activation checkpointing (selective first, then full).
  3. ZeRO-1 → ZeRO-2 → ZeRO-3 / FSDP.
  4. 8-bit optimizer.
  5. Tensor parallelism (also cuts activation memory).
  6. Pipeline parallelism.
  7. CPU / NVMe offload.
  8. If fine-tuning: LoRA / QLoRA, and skip steps 3–7.

When the loss diverges, in order:

  1. Check the LR against the global batch size (chapter 05's linear scaling rule). Add warmup.
  2. Switch fp16 → bf16.
  3. Gradient clipping (clip_grad_norm_(1.0)), after unscaling.
  4. Sequence-length warmup (§4).
  5. Inspect the data for pathological samples.
  6. Check init, and consider z-loss / QK-norm.

7. Quick reference

   THE FUSION PRINCIPLE
   ────────────────────
   Most transformer ops are MEMORY-bound, not compute-bound.
   A100: ~312 TFLOPS bf16 vs ~2 TB/s HBM  →  ~150 FLOPs per byte to break even.
   LayerNorm ~2, GeLU ~1, dropout <1, softmax ~2  →  all memory-bound.
   ⇒ minimize HBM traversals. That is what every kernel technique does.
python
# ── Tier 1: do these always ────────────────────────────────
with torch.autocast("cuda", dtype=torch.bfloat16):     # 2-3×
    loss = model(**batch).loss

out = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # FlashAttention
# packed batches, no padding (>= 2.10):
# out = varlen_attn(q, k, v, cu_seq_q, cu_seq_k, max_q, max_k, window_size=(-1, 0))

model = torch.compile(model)                            # 1.1-1.5×

optimizer = torch.optim.AdamW(params, lr=3e-5, fused=True)

loss = F.linear_cross_entropy(h, lm_head.weight, tgt)   # 2.13, big vocab

model.gradient_checkpointing_enable()                   # memory

# ── memory, if needed ──────────────────────────────────────
import bitsandbytes as bnb
optimizer = bnb.optim.AdamW8bit(params, lr=3e-5)        # 12Ψ -> ~3Ψ

from torch.distributed.fsdp import fully_shard          # ZeRO-3
for layer in model.layers: fully_shard(layer)
fully_shard(model)

# ── communication, if network-bound ────────────────────────
from torch.distributed.algorithms.ddp_comm_hooks import default_hooks as hooks
model.register_comm_hook(state=None, hook=hooks.bf16_compress_hook)

# ── fine-tuning only ───────────────────────────────────────
# LoRA / QLoRA: base weights frozen (4-bit), train rank-r adapters
#   7B full FT ≈ 112 GB   →   7B QLoRA ≈ 4 GB

# ── profile before any of the above ────────────────────────
with torch.profiler.profile(
    activities=[torch.profiler.ProfilerActivity.CPU,
                torch.profiler.ProfilerActivity.CUDA],
    on_trace_ready=torch.profiler.tensorboard_trace_handler("./log"),
) as prof:
    for _ in range(5):
        train_step(); prof.step()

Appendix

Exercises

  1. Measure fusion. Time y = torch.matmul(x, w) * b then torch.gelu(y) as separate ops, then wrap the whole thing in torch.compile. Compare. Then compute the theoretical HBM traffic for each and see whether the ratio matches.
  1. Find the crossover. For your GPU, look up peak bf16 FLOPS and HBM bandwidth and compute the FLOPs-per-byte break-even point. Then classify LayerNorm, softmax, and a [4096, 4096] @ [4096, 4096] matmul as compute- or memory-bound.
  1. FlashAttention memory. For batch 4, 32 heads, seq 8192, bf16: compute the size of the materialized attention score matrix. Then measure peak memory with and without scaled_dot_product_attention.
  1. Error feedback. Implement 1-bit compression with and without error feedback on a toy quadratic optimization. Plot the loss curves. How many steps before the no-feedback version stalls?
  1. Length curriculum. Train a small GPT with fixed seq=512 and with a curriculum ramping 128 → 512. Match total tokens, not steps. Which reaches a lower loss, and how much of the difference is explained by the extra optimizer steps?
  1. Profile honestly. Take any training script you have and profile it. Before looking at the trace, write down your guess for what's bottlenecking it. Compare.
