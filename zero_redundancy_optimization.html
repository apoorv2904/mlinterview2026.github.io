1. Mixed Precision

As recent GPUs have come to support lower-precision computation, modern neural-network training mostly uses mixed precision, using FP16 (half) and FP32 (single) together. On a V100, if FP32 runs at about 14 TFLOPS, in FP16 you can train the model at 100 TFLOPS. Also, using FP16 shrinks the model size, which is an advantage not only for training but for deployment too.

   FP32   │S│ 8 exponent │        23 mantissa        │   4 bytes
   FP16   │S│5 exponent│  10 mantissa │                2 bytes
   BF16   │S│ 8 exponent │ 7 mantissa │                2 bytes
                ▲            ▲
                range     precision

But why mixed?

A question arises here. Why not just train the model in FP16 — is it really necessary to use FP32 and FP16 together? To give the conclusion first: training with FP16 alone makes the loss diverge badly and training is nearly impossible. Keeping gradients in FP16 throws away most of the decimal places, so precise training becomes impossible. So we use both the fast FP16 and the accurate FP32, trying to take only the advantages of each.

The compute-heavy forward and backward are done with the FP16 model, and the computed gradients are copied into the higher-precision FP32 model to update the weights. But another question arises. How do we apply FP16 gradients to FP32? According to the researchers' experiments, when you backward a loss computed in FP16, some values that were small (on the left of the figure) became 0 during the computation.

Loss Scaling

How can we solve this problem? With a very simple idea: multiply the loss gradient by a very large value to push the distribution to the right. The name of this technique is loss scaling. If you multiply the FP16 loss by a very large value, values that would have vanished when applied to FP32 can be preserved.

   before scaling                    after × 1024
                                                    ┌──── fp16 range ────┐
   ▁▂▄██▆▃▂▁    │◀ fp16 range ▶│         ─────▶      │  ▁▂▄██▆▃▂▁        │
   └─ lost ─┘                                        │  └─ preserved ─┘  │
python
# What loss scaling does, stripped to its essentials:
scale = 1024.0

loss = compute_loss(model(batch))     # fp16/bf16 forward
(loss * scale).backward()             # every gradient in the graph is now scale x larger

for p in model.parameters():          # undo it in fp32, BEFORE the optimizer sees it
    p.grad = p.grad.float() / scale    #   cast first, then divide

optimizer.step()
Note — why scaling the loss works at all

Because differentiation is linear:

   d(c·L)/dw  =  c · dL/dw

Multiplying the loss by c multiplies every gradient in the graph by c, uniformly, with one multiply. There is no need to touch the backward pass at all. The gradients then live in a range fp16 can represent, and you divide by c once at the end, in fp32, before the optimizer step.

The critical detail: you must unscale before the update, or your effective learning rate is c times too large. GradScaler does this inside scaler.step(optimizer). Keep this in mind for the walkthrough below.

Indeed, as in the figure below, multiplying the loss by a large value made training work well without diverging. The grey graph is without scaling; the green is with. Surprisingly, the performance is almost identical to FP32.

For this reason, mixed precision using FP16 and FP32 together has become almost essential to modern neural-network training. Until bfloat16 (Google TPU) — which covers FP32's range with FP16's storage size — is supported on more diverse GPUs and becomes popularized, FP16 + 32 mixed-precision training will remain an essential technique for neural-network training.

bf16 won. Use it, and skip most of this section

Every NVIDIA GPU from Ampere (A100) onward, and every AMD MI-series, supports bf16 natively. It is now the default for large-model training, and this changes the chapter's premise:

3) Backward

Now we need to update the model's parameters with the gradient-descent rule wₙ := wₙ − lr · dL/dwₙ.

So we need gradients like dL/dw₁ and dL/dw₂. They are roughly as follows (obtained by the chain rule):

   dL/dw₂ = dL/dz₂ · dz₂/dw₂
   dL/dw₁ = dL/dz₂ · dz₂/dz₁ · dz₁/dw₁

Concretely:

   dL/dz₂ = y − z₂     (BWD-activation: layer2)
   dz₂/dw₂ = z₁        (BWD-weight:     layer2)
   dz₂/dz₁ = w₂        (BWD-activation: layer1)
   dz₁/dw₁ = x         (BWD-weight:     layer1)

   dL/dw₂ = (y − z₂) · z₁
   dL/dw₁ = (y − z₂) · w₂ · x
python
# loss scaling
L *= 1024

# do backward
L.backward()
Note — the two kinds of backward, which matter again in chapter 06's zero-bubble schedules

Notice the list above separates BWD-activation (dL/dz, the gradient w.r.t. the layer input) from BWD-weight (dL/dw, the gradient w.r.t. the parameters). Only the first is needed by the previous layer; the second is needed only by the optimizer. That is exactly the decomposition zero-bubble pipeline scheduling exploits. Same fact, different chapter.

4) Update Weight

Finally, run optimizer.step() to update the parameters.

   w₁ := w₁ − lr · dL/dw₁
   w₂ := w₂ − lr · dL/dw₂
python
print(f'before: {fp32_model.w1.weight}\n')
optimizer.step()
print(f'after: {fp32_model.w1.weight}\n')

Think about it — the FP32 model never performed a forward or backward. So it doesn't hold gradient tensors. That's why running optimizer.step() didn't change the values. So before running optimizer.step(), we must copy the gradients of the FP16 model that went through backward().

For reference, in PyTorch every parameter (nn.Parameter) with requires_grad=True has a grad attribute. When backward is called on a tensor output by the model, it walks back through the graph performing the derivative computation and stores the results in the space called grad. Because grad is the same size as the corresponding tensor, if the model's capacity is 10 GB then the gradients need 10 GB as well. This is one of the reasons training needs far more memory than inference. So if a tensor won't be used for training, you must set requires_grad to False to prevent unnecessary memory consumption.

python
# copy gradient to FP32 model
fp32_model.w1.weight.grad = fp16_model.w1.weight.grad.float()
fp32_model.w2.weight.grad = fp16_model.w2.weight.grad.float()
python
print(f'before: {fp32_model.w1.weight}\n')
optimizer.step()
print(f'after: {fp32_model.w1.weight}\n')
There is a bug in this walkthrough: the gradients are never unscaled

L *= 1024 multiplied every gradient by 1024. The copy to the fp32 model carries that factor straight through into optimizer.step(), so the effective learning rate is 1024× larger than lr=1e-2. As a demonstration of the mechanics it's fine; as a template it will blow up.

The missing step:

python
SCALE = 1024
fp32_model.w1.weight.grad = fp16_model.w1.weight.grad.float() / SCALE
fp32_model.w2.weight.grad = fp16_model.w2.weight.grad.float() / SCALE

Note the ordering: cast to fp32 first, then divide. Dividing in fp16 would re-introduce the underflow the scaling existed to prevent.

A real implementation also checks for inf/nan before unscaling and skips the step if any are found — an overflowed gradient is garbage, not a small number. That check is what scaler.step(optimizer) does for you, and it's why GradScaler sometimes reports skipped steps early in training.

Doing mixed-precision training in PyTorch

In PyTorch you can perform mixed-precision training easily as follows.

python
# bf16 — the default choice on any GPU from Ampere onward.
# No GradScaler, no overflow handling, no skipped steps.
for batch in loader:
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast("cuda", dtype=torch.bfloat16):
        loss = model(**batch).loss
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()


# fp16 — only if you are on pre-Ampere hardware. Needs the scaler.
scaler = torch.amp.GradScaler("cuda")

for batch in loader:
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast("cuda", dtype=torch.float16):
        loss = model(**batch).loss

    scaler.scale(loss).backward()      # scaled gradients
    scaler.unscale_(optimizer)         # BEFORE clipping — clipping needs true values
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)             # skips the step if any gradient is inf/nan
    scaler.update()                    # adjust the scale for next iteration
Note — what autocast actually does, since "casts operations to mixed precision" is vague

It maintains a per-operation policy:

Category Runs in Examples
Numerically safe, compute-heavy fp16/bf16 matmul, conv, linear, bmm
Numerically sensitive fp32 softmax, layer_norm, log, exp, sum, losses
Promote to widest input fp32 add, cat, elementwise mixes

So "mixed precision" isn't a uniform cast — it's a curated one. The big GEMMs get the tensor-core speedup; reductions and normalizations stay in fp32 where catastrophic cancellation would otherwise bite. Your model weights stay fp32 throughout; only the activations flowing through autocast-ed ops are low precision.

`torch.cuda.amp.*` is deprecated

(since PyTorch 2.4) and emits a FutureWarning. The spellings are torch.amp.GradScaler("cuda") and torch.autocast("cuda", ...). You will see the old ones constantly in blog posts and older repos.

Note the unscale_ placement in the fp16 path above: gradient clipping must see true gradients. Clipping scaled gradients clips at 1024 × your threshold — that is, not at all.

Dynamic Loss Scaling

Loss scaling made mixed-precision training very effective. But it's very hard to know what scale value is best to set. So some open-source projects propose the dynamic loss scaling technique to solve this. It's implemented in NVIDIA's amp and MS's deepspeed.

The idea of dynamic loss scaling is very simple. The goal is to keep the scale value as large as possible without the gradient's decimals overflowing. The larger you make the gradient values the better, but if they get too large overflow occurs, so you grow them as much as possible short of overflow.

So at the start of training you set a very large value as the scale. In deepspeed the default is set to 2³². You backward the loss with this value, and if the gradient overflowed you halve the scale value. Repeating this process many times to find the maximum scale value at which overflow does not occur is exactly dynamic loss scaling.

Note — the algorithm has a second half that is easy to miss: it also grows 
   every step:
       backward with current scale
       if any gradient is inf/nan:
           SKIP the optimizer step        ← the update is discarded entirely
           scale ← scale / 2
           reset the success counter
       else:
           apply the step
           if N consecutive successes (N = loss_scale_window, default 1000):
               scale ← scale × 2          ← creep back up

Without the growth half it would only ever ratchet downward and eventually underflow again. The hysteresis parameter in the config ("hysteresis": 2) means "tolerate this many overflows before reducing," which damps oscillation around the boundary.

Two practical consequences:

  • Early skipped steps are normal. Starting at 2³² essentially guarantees overflow, so the first several steps get discarded while the scale ratchets down. If you see "OVERFLOW! Skipping step" in the first ~20 iterations, that's the algorithm working, not a bug.
  • initial_scale_power: 32 is unusually aggressive. DeepSpeed's own default is 16. Starting at 32 just spends more steps searching. And with bf16 the entire mechanism is unnecessary.
Note — historical, for reading old configs

Before PyTorch had native AMP, mixed precision came from NVIDIA's apex library, which exposed an opt_level knob:

opt_level Meaning Modern equivalent

2. Zero Redundancy Optimization

By using FP16 and FP32 together, training speed became very fast, but a drawback appeared — memory. Because the FP32 master weights, the FP16 parameters, and the gradients are all held on the GPU, more memory is needed than before.

And even though the model parameters exist in FP16, the optimization happens in FP32, so tensors such as the variance and momentum required by adaptive optimizers like AdaGrad and Adam must still be kept in FP32.

The second moment is the hard one: non-negative, heavy-tailed, and in a denominator.

First, what 4Ψ + 12Ψ/N even means. Ψ is the parameter count. The 16 bytes fall into two groups that ZeRO treats completely differently:

    4Ψ   bf16 weights (2) + bf16 gradients (2)   ← ZeRO-1 does NOT touch these
   12Ψ   fp32 master (4) + m (4) + v (4)         ← ZeRO-1 shards these
   ────
   16Ψ   total                                   →  4Ψ + 12Ψ/N
                                                      ↑        ↑
                                          every rank keeps    divided N ways

Consequence 1 — the 12 is not a constant. Only the shardable term depends on your optimizer recipe, so a different recipe changes the 12 and nothing else:

   AdamW textbook   master 4 + m 4 + v 4  =  12Ψ   →   4Ψ + 12Ψ/N
   Muon, fp32       master 4 + momentum 4 =   8Ψ   →   4Ψ +  8Ψ/N
   8-bit AdamW      master 4 + m 1 + v 1  =   6Ψ   →   4Ψ +  6Ψ/N

Breaking that floor means sharding the other two terms, which is exactly what the later stages do: ZeRO-2 shards the gradients (2Ψ), ZeRO-3 shards the weights (2Ψ), giving 16Ψ/N with no floor at all. Low-precision optimizer state is a bounded trick against one term; sharding is an unbounded lever against all three.

Additionally, data tensors and activation tensors are allocated in memory. Data tensors mean the token-state tensors before they enter the model, and activation tensors mean the hidden states and other tensors computed during forward and backward. On top of that, when you do distributed processing you also need bucket space to hold tensors during communication. We already covered buckets as gradient bucketing in the Data Parallelism session. So we need to manage not only the model and the data but also these optimizer states (variance, momentum) and data & activation memory.

Zero Redundancy Optimization (ZeRO) is a collection of memory-optimization techniques that helps manage these parts very efficiently. There are broadly two families of solutions: ZeRO-DP (ZeRO Data Parallelism) and ZeRO-R (ZeRO Residual States). Let's work through them step by step.

Note — the word "redundancy" is the whole thesis, so make it concrete

Under plain DDP, all N GPUs hold byte-identical copies of those 16 bytes/param. Across 8 GPUs, that's 8 identical copies of everything:

   DDP, N=4:
   GPU0 [16Ψ]   GPU1 [16Ψ]   GPU2 [16Ψ]   GPU3 [16Ψ]     ← 4× redundancy
        └────────────┴────────────┴────────────┘
                    all identical, always

Yet at any instant, a rank only needs the parameters of the layer it's computing, and the optimizer state only at step() time. The redundancy buys nothing except convenience. ZeRO removes it, shard by shard, in four escalating stages.

For a 7B model that's 16 × 7e9 = 112 GB of state. On 8×80GB GPUs, DDP needs 112 GB per GPU and fails. ZeRO-3 needs 14 GB per GPU and fits comfortably.

3. ZeRO Data Parallelism

If we first examine the memory state, the left side of the figure above (FP16, FP32, model & optimizer & gradient) takes up the largest space. So we need to split and manage those efficiently. ZeRO-DP helps split and manage these tensors per device, together with data parallelism.

ZeRO-DP is provided in 4 stages and can be applied selectively through the DeepSpeed library.

The redundancy being removed is easy to see. Under DDP every rank holds a bit-identical copy of everything:

   N = 8, 7B model
   rank 0 [16Ψ]  rank 1 [16Ψ]  ...  rank 7 [16Ψ]      112 GB each
          └───────── all identical, all the time ─────────┘

Seven of those eight copies are waste. But you cannot simply delete them, because the ranks need the weights in order to compute. ZeRO’s answer is one idea, applied at three depths:

Give each rank sole ownership of one shard. Gather the rest only for the instant it is needed, then throw it away.

📝 Note — the unit for communication here is bf16 bytes per parameter

The ZeRO paper states communication in elements: an all-reduce moves 2Ψ, a reduce-scatter or an all-gather moves Ψ. This chapter states it in bytes instead, so that it shares a unit with the memory figures. Assuming bf16 gradients and bf16 working weights:

   all_reduce       2Ψ elements  →  4Ψ bytes
   reduce_scatter    Ψ elements  →  2Ψ bytes
   all_gather        Ψ elements  →  2Ψ bytes

                             moved per rank      vs DDP
   DDP        all_reduce             4Ψ B         1.00x
   ZeRO-1/2   RS 2Ψ + AG 2Ψ          4Ψ B         1.00x
   ZeRO-3     AG 2Ψ + AG 2Ψ + RS 2Ψ  6Ψ B         1.50x

Two things this makes visible that the element form hides. First, the fp32 master weights are never communicated, in any stage — only gradients and bf16 working weights move, so fp32 master inflates memory but not comms. Second, if your gradients are fp32 — the PyTorch AMP default, or FSDP with reduce_dtype=torch.float32 — every reduction doubles, and DDP’s all-reduce is 8Ψ bytes rather than 4Ψ. That is precisely what chapter 05’s bf16_compress_hook exists to claw back.

Stage 1 — shard the optimizer states (12Ψ)

Only master, m and v are sharded. Rank i becomes the only rank that updates shard i.

   DDP  ───  all_reduce(grads)  ───  every rank runs the same update

   ZeRO-1
   1.  forward + backward as usual         every rank has FULL gradients
   2.  reduce_scatter(grads)               rank i keeps summed grads for shard i
   3.  rank i updates ONLY its shard       master_i, m_i, v_i  →  new W_i
   4.  all_gather(new bf16 weights)        everyone has full W again

       steps 2 and 4 ARE the all_reduce, split apart,
       with the optimizer step done in the gap

DDP paid one all_reduce = 4Ψ bytes. Stage 1 pays reduce_scatter (2Ψ) + all_gather (2Ψ) = 4Ψ bytes. Identical volume — the all-reduce is simply split, with the optimizer step done in the gap. Rank i also does only 1/N of the optimizer arithmetic. Memory: 4Ψ + 12Ψ/N, or 38.5 GB at N=8.

Stage 2 — also shard the gradients (2Ψ)

Stage 1 still materializes the full gradient buffer before scattering it. Stage 2 refuses to: as each bucket’s gradients become ready during the backward pass, it reduce-scatters that bucket immediately.

   backward, layer by layer:

   layer 12 grads ready ──▶ reduce_scatter ──▶ keep my shard, FREE the rest
   layer 11 grads ready ──▶ reduce_scatter ──▶ keep my shard, FREE the rest
   layer 10 ...
                                ↑
              full gradients never exist anywhere, at any instant
📝 Note — the temporary buffer is what makes stage 2 possible, not a flaw in it

A reduce-scatter has to have something to reduce, so the gradients for a bucket do exist in full, on every rank, for a moment. Stage 2 does not avoid that — it bounds it:

   Let B = parameters in one bucket   (B ≪ Ψ)

   Stage 1 :  full gradients for the WHOLE MODEL held at once   2Ψ bytes
   Stage 2 :  full gradients for ONE BUCKET held at once        2B bytes
              scattered, then freed before the next bucket arrives

   7B model, bf16 gradients, DeepSpeed reduce_bucket_size = 5e8:
     Stage 1 transient   2 x 7e9  =  14 GB
     Stage 2 transient   2 x 5e8  =   1 GB

So at any instant every GPU is holding the gradients of a bucket or two in temporary memory, not of the entire model — implementations keep a second bucket in flight so the reduce-scatter overlaps the next layer’s backward. The peak is set by the bucket size, which is why the bucket is a tuning knob rather than an implementation detail — too large and you lose the saving, too small and the collectives stop amortizing. The collective itself is unchanged, so communication is still 4Ψ bytes.

Memory: 2Ψ + 14Ψ/N, or 26.3 GB at N=8.

Stage 3 — also shard the parameters (2Ψ)

Now rank i stores only W_i. But computing layer L needs all of W_L, so the gather moves inside the layer loop:

   FORWARD                          BACKWARD
   ───────                          ────────
   for L in layers:                 for L in reversed(layers):
     all_gather(W_L)   ◀─ comms      all_gather(W_L)      ◀─ comms again
     compute                          compute grads
     FREE W_L          ◀─ key!       reduce_scatter(dW_L) ◀─ comms
                                      FREE W_L

   DDP moved gradients once. Stage 3 moves parameters twice
   and gradients once — three collectives per layer, not one.

   all_gather (fwd)   2Ψ B
   all_gather (bwd)   2Ψ B    ← needed again because W_L was freed after forward
   reduce_scatter     2Ψ B
   ──────────────────────
   total               6Ψ B   vs DDP's 4Ψ B   →  1.5x
📝 Note — why there is no fourth collective after the optimizer step

Stages 1 and 2 end their step with an all_gather of the updated weights, because in those stages parameters are replicated — the replica has to be rebuilt before the next forward.

Stage 3 does not, and it is worth seeing why the count is 6Ψ bytes rather than 8Ψ. After the reduce_scatter, rank i already holds the correctly summed gradient for exactly the slice it owns. It updates W_i locally and stops there:

   Stage 1 / 2 :  sharded is TEMPORARY  →  must all_gather back to replicated
   Stage 3     :  sharded is the RESTING STATE  →  nothing to rebuild

   rank i after reduce_scatter:  dW_i is final  →  update W_i  →  done
   the other partitions arrive in the NEXT forward's all_gather,
   which is already counted in the 6Ψ above.

In other words the post-update gather is not skipped as an optimization — it would be actively wrong. Parameters are supposed to live sharded between steps, and the forward pass already gathers what it needs, when it needs it.

Memory: 16Ψ/N, or 14 GB at N=8, with no floor underneath it. Add one layer’s gathered weights for the transient peak — which is why wrapping granularity matters: wrap per layer and that term is one layer, wrap the whole model and you have gathered everything and saved nothing.

   Let Ψ = #parameters, N = data-parallel world size

   ┌────────────┬──────────────┬─────────────────────┬───────────────┐
   │  Stage     │ What shards  │ Memory per GPU      │ Comm vs DDP   │
   ├────────────┼──────────────┼─────────────────────┼───────────────┤
   │  DDP       │  nothing     │       16Ψ           │      1×       │
   │  ZeRO-1    │  optimizer   │   4Ψ + 12Ψ/N        │      1×       │
   │  ZeRO-2    │  + gradients │   2Ψ + 14Ψ/N        │      1×       │
   │  ZeRO-3    │  + params    │      16Ψ/N          │     1.5×      │
   └────────────┴──────────────┴─────────────────────┴───────────────┘

   fp16 weights  ██                   ← survives until stage 3
   fp16 grads    ██                   ← sharded at stage 2
   fp32 w,m,v    ████████████         ← sharded at stage 1  (12 of the 16 bytes!)
Note — why the stages are in that order: biggest win first, cheapest first

Stage 1 shards the fp32 master weights, momentum, and variance — 12 of the 16 bytes, three quarters of the total — and costs nothing extra in communication. That's why it's stage 1: it's nearly free.

Note — why stages 1 and 2 are communication-neutral, which sounds too good to be true

Straight from chapter 03's identity:

   all_reduce  =  reduce_scatter  +  all_gather      (and costs exactly 2× either half)

   DDP:      all_reduce(gradients)                       → 4Ψ bytes per rank
   ZeRO-1/2: reduce_scatter(gradients) → each rank gets its shard
             ... local optimizer step on that shard ...
             all_gather(updated params)                  → 2Ψ + 2Ψ = 4Ψ bytes per rank

Identical volume. DDP was already paying for both halves of an all-reduce; ZeRO just declines to reassemble in between, does the update on the shard it holds, and reassembles the parameters instead of the gradients. Same bytes, far less memory. This is why ZeRO-1 and ZeRO-2 are close to strict improvements over DDP and there is rarely a reason not to use them.

Stage 3 is different: parameters are sharded permanently, so every layer must be all_gathered before use in the forward pass and again in the backward pass. That extra gather is the 1.5×.

In conclusion, applying ZeRO-DP lets you train a much larger model on smaller GPUs. DeepSpeed exposes the stages through zero_optimization.stage; PyTorch’s native equivalent is FSDP, which §7 covers with runnable code.

4. Activation Checkpointing

Besides the FP16/32 model, gradients, and optimizer states, another large memory region is the activation memory region. Activations mean the input tensors that get multiplied with the model weights. If there is a neural network like y = w₁ · (w₂ · x), then tensors such as x (multiplied with w₁) and w₂ · x correspond to activation memory.

python
"""
Reference: https://pytorch.org/tutorials/beginner/examples_autograd/two_layer_net_custom_function.html
"""

import torch

class ReLU(torch.autograd.Function):

    @staticmethod
    def forward(ctx, input):
        ctx.save_for_backward(input)
        # storing the input value

        return input.clamp(min=0)

    @staticmethod
    def backward(ctx, grad_output):
        input, = ctx.saved_tensors
        grad_input = grad_output.clone()
        grad_input[input < 0] = 0
        return grad_input

In the Pipeline Parallelism session we mentioned that the activation tensors used during forward are stored for the backward pass. As above, to compute the derivative of a max-pooling layer you need the original positions of the pooled values, so the tensor input during forward is absolutely required. Also, looking at the ReLU implementation above, you can see the input tensor being saved via ctx.save_for_backward.

That is, to perform the backward step you must store the inputs from the forward step. But if you store activations everywhere like this, memory consumption becomes very large.

   (a) store everything  — the default
   layers:  1─2─3─4─5─6─7─8
   stored:  ●─●─●─●─●─●─●─●        memory: O(L)   recompute: none

So if you don't store the activation tensors you can save far more memory. But if you don't store them, you have to run forward once more at backward time to obtain the activation tensors.

   (b) store nothing
   layers:  1─2─3─4─5─6─7─8
   stored:  ○─○─○─○─○─○─○─○        memory: O(1)   recompute: O(L²) — re-run
                                                   from layer 1 every time

Activation checkpointing is a method that combines the advantages of both, storing activations at intervals.

   (c) checkpoint every √L layers
   layers:  1─2─3─4─5─6─7─8
   stored:  ●─○─○─●─○─○─●─○        memory: O(√L)  recompute: O(L)
            ▲     ▲     ▲          re-run only from the nearest checkpoint

Storing only at intervals like this lets you save computation time by not redoing forward from the very beginning every time, and greatly reduces memory consumption by removing almost all activations. This technique — storing activations at intervals and, when a forward is needed, running forward from the checkpointed location — is called activation checkpointing. PyTorch has checkpointing built in.

python
"""
src/checkpointing.py
"""
from torch import nn
from torch.utils.checkpoint import checkpoint
from transformers import AutoTokenizer, BertLayer, BertConfig

config = BertConfig.from_pretrained("bert-base-cased")
tokenizer = AutoTokenizer.from_pretrained("bert-base-cased")
tokens = tokenizer("Hello I am Kevin", return_tensors="pt")

embedding = nn.Embedding(tokenizer.vocab_size, config.hidden_size)
layers = nn.ModuleList([BertLayer(config) for _ in range(6)])

hidden_states = embedding(tokens.input_ids)
attention_mask = tokens.attention_mask

for i, layer_module in enumerate(layers):
    layer_outputs = checkpoint(
        layer_module,
        hidden_states,
        attention_mask,
        use_reentrant=False,      # required; see the note below
    )

    hidden_states = layer_outputs[0]

print(f"output: {hidden_states}")

Usage is simply changing what you used to write as module(a, b, c) into checkpoint(module, a, b, c) — that's it.

Also, the Hugging Face transformers we use frequently has this activation-checkpointing feature built into almost every model. You can simply turn it on and off with model.gradient_checkpointing_enable() and model.gradient_checkpointing_disable().

Note — the trade, quantified

The rule of thumb for transformers:

Activation memory Extra compute
No checkpointing 100% 0%
Checkpoint every layer ~1/L of the intermediates ~33% (one extra forward)
Selective (attention only) ~50–70% saved ~5–10%

An extra forward pass is roughly one third of a full training step (forward ≈ 1, backward ≈ 2), hence the ~33%. That is usually an excellent trade: 33% more compute to fit a batch 4× larger, or a model that otherwise wouldn't run at all.

Selective checkpointing — recompute only the expensive-to-store, cheap-to-recompute parts (attention scores) and keep the rest — gets most of the memory benefit for a fraction of the compute. Megatron's --recompute-granularity selective does this, and it's usually the better default than full recomputation.

`use_reentrant` is now required
python
layer_outputs = checkpoint(layer_module, hidden_states, attention_mask,
                           use_reentrant=False)

The old reentrant implementation had real limitations: it broke with torch.autograd.grad, didn't handle keyword arguments, mis-handled modules with no requires_grad inputs, and interacted badly with DDP's unused-parameter detection. use_reentrant=False is the non-reentrant implementation and is now the recommended path; omitting the argument raises a warning and will eventually change behaviour.

One more modern caveat: checkpointing re-runs the forward, so anything stochastic must be replayed identically. PyTorch handles RNG state for you by default (preserve_rng_state=True), but dropout inside a checkpointed region is a classic source of subtle bugs in hand-rolled implementations.

5. ZeRO-R

ZeRO-DP shards model state. ZeRO-R attacks what is left over — the paper calls it residual memory: activations, communication buffers, and memory lost to fragmentation. Three ideas, and they have aged very differently.

   1. Activation partitioning   shard checkpointed activations across MP ranks
   2. Constant-size buffers     cap communication buffers instead of growing
                                them with the model
   3. Defragmentation           preallocate contiguous regions for activations
                                and gradients
📝 Note — idea 1 has been superseded, and by something in this series

Activation partitioning targets the redundancy from chapter 07: under tensor parallelism the LayerNorm and dropout regions are replicated, so every TP rank holds an identical full [batch, seq, hidden] activation. ZeRO-R gathers those checkpointed activations and re-partitions them across the TP group.

That is the same problem sequence parallelism solves (chapter 07 §5), reached from the other direction — and sequence parallelism is the better answer today. It removes the replication structurally, at identical communication volume, instead of gathering and re-partitioning after the fact. Treat idea 1 as history.

Idea 2 is a tuning knob rather than a technique: allgather_bucket_size and reduce_bucket_size (default 5e8 elements) cap the communication buffers. Past roughly 50–500 MB a larger message buys no extra bandwidth but still costs memory, so a fixed cap sits past the knee. Lower it if you are tight; it is a small effect either way.

Idea 3 is the one still worth knowing, because it explains a failure that looks impossible: an OOM while the GPU reports plenty free.

   fragmented                          defragmented
   ┌──┬──┬─┬───┬─┬──┬────┬─┬──┐        ┌────────────────┬──────────────┐
   │██│  │█│   │█│  │████│█│  │        │████████████████│              │
   └──┴──┴─┴───┴─┴──┴────┴─┴──┘        └────────────────┴──────────────┘
    40% free but no contiguous          40% free, all contiguous
    block big enough → OOM              → allocation succeeds

   CUDA out of memory. Tried to allocate 2.00 GiB.
   GPU has 14.5 GiB free; 8.2 GiB reserved by PyTorch but unallocated.
                              ↑
              this line is the tell: it is fragmentation, not capacity

DeepSpeed’s answer is contiguous_gradients and contiguous_memory_optimization; PyTorch’s general one is PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True. Both appear in §9’s gotchas table, which is where you will actually reach for them.

Section 6 of 10

6. ZeRO-Offload and ZeRO-Infinity

ZeRO-Offload breaks the GPU capacity limit by moving part of the training state to CPU RAM. The split follows one principle: keep on the GPU only what needs GPU compute.

   ┌───────────── GPU (fast, small) ─────────────┐
   │  fp16 params  ██   fp16 grads  ██           │   4 bytes/param
   │  forward + backward   ← heavy compute       │
   └──────────────────┬──────────────────────┘
                      │ gradients down / params up  (PCIe)
   ┌──────────────────▼──────────────────────┐
   │  fp32 params ████  momentum ████  var ████  │  12 bytes/param
   │  optimizer.step()     ← light compute       │
   └───────────── CPU (slow, large) ─────────────┘
📝 Note — the argument is arithmetic intensity, and it is a good one 
                     work per parameter        where it belongs
   forward/backward  O(batch × seq) FLOPs      GPU  (compute-bound)
   optimizer step    O(1) FLOPs                CPU  (memory-bound)

The optimizer step does a constant amount of arithmetic per parameter regardless of batch size — a few multiplies and adds — so it is entirely memory-bandwidth-bound. Yet it holds 12 of the 16 bytes hostage on the GPU for no computational reason. Moving it to a device with hundreds of GB of RAM is the natural trade. (DeepSpeed ships a vectorized CPU Adam for exactly this.)

⚠️ What it costs — this is the section people over-apply 
   traffic per step ≈ 2 × Ψ × 2 bytes   (fp16 grads down, fp16 params up)

   7B model:      ≈ 28 GB per step over PCIe
   PCIe Gen4 x16  ≈ 25 GB/s effective   →  ~1.1 s/step of pure transfer

A well-fed A100 completes a 7B step in well under a second, so offload can cost more than 2× in step time. It is a capacity technique, not a performance one: reach for it when the alternative is not training at all, not when you want to go faster. If you can add GPUs instead, add GPUs.

ZeRO-Infinity is the same idea one tier further down: park tensors on NVMe by default and lift them to CPU or GPU only when needed. It buys capacity that nothing else can — NVMe is far larger than RAM — and DeepSpeed reports it beating ZeRO-Offload, because streaming from NVMe overlaps with compute where a synchronous PCIe round trip does not. Set offload_param / offload_optimizer device to nvme with an nvme_path. The same caveat applies, harder: it is what you use when the model will not otherwise fit at all.

The Delayed Parameter Update variant recovers some of that by letting the GPU run step k+1 with parameters from step k-1, overlapping CPU update with GPU compute. It is a staleness-for-throughput trade, and it changes the optimization problem — use it knowingly.

Section 7 of 10

7. FSDP, the PyTorch-native ZeRO

The single biggest change since 2021: you no longer need DeepSpeed to get ZeRO. PyTorch has it built in, it composes with the other parallelism axes via DeviceMesh, and it's the default choice for new projects.

The API you want is FSDP2 — fully_shard. It replaced the older FullyShardedDataParallel wrapper, and the difference is not cosmetic:

   FSDP1   FullyShardedDataParallel(model, ...)    a wrapper CLASS
           params flattened into one FlatParameter per unit
           -> state_dict surgery, awkward to compose with TP/PP

   FSDP2   fully_shard(module, ...)                a FUNCTION, applied
           each param becomes a DTensor, Shard(0)  per module
           -> composes on DeviceMesh, clean state_dict, per-param dtype

The move to DTensor is what makes 3-D and 4-D parallelism tractable: FSDP’s sharding is just another DeviceMesh dimension, so TP, PP and CP stack on top instead of fighting the flat-parameter layout. That is why chapter 09 builds its meshes the way it does.

📝 Note — reshard_after_forward is the ZeRO-2 / ZeRO-3 dial 
   reshard_after_forward=True    free params after forward, re-gather
                                 them in backward        → ZeRO-3
                                 minimum memory, second all_gather

   reshard_after_forward=False   keep params unsharded until backward
                                 ends                    → ZeRO-2-like
                                 more memory, no second all_gather

   reshard_after_forward=int     reshard onto a smaller group
                                 (hybrid: shard in-node, replicate across)

So the §3 stage table is a runtime flag here, not a different library. A common setup is True for the big transformer blocks and False for the last one, whose parameters are needed again almost immediately.

📝 Note — MixedPrecisionPolicy, and why FSDP needs no extra master copy

param_dtype sets the dtype of the unsharded parameter — so it governs the forward/backward compute and the parameter all-gather. reduce_dtype sets the dtype of the gradient reduce-scatter, independently (§3’s note on why you usually want float32 there).

Unlike autocast, this is module-level mixed precision, not op-level: casts happen at module boundaries and low-precision activations are what get saved for backward. The neat consequence is that FSDP keeps the high-precision sharded parameters resident anyway, so the fp32 master the optimizer needs costs no extra memory — it is already there.

python
"""
torchrun --standalone --nproc_per_node=8 fsdp_train.py
"""
import os
import torch, torch.distributed as dist
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group("nccl", device_id=torch.device(f"cuda:{local_rank}"))

model = build_model().to("cuda")

mp = MixedPrecisionPolicy(
    param_dtype=torch.bfloat16,      # compute in bf16
    reduce_dtype=torch.float32,      # reduce gradients in fp32 for stability
)

# shard each block, then the root — order matters
for layer in model.layers:
    fully_shard(layer, mp_policy=mp)
fully_shard(model, mp_policy=mp)

optimizer = torch.optim.AdamW(model.parameters(), lr=3e-5, fused=True)

for batch in loader:                 # DistributedSampler as usual
    loss = model(**batch).loss
    loss.backward()                  # reduce_scatter happens here
    optimizer.step()                 # each rank updates only its shard
    optimizer.zero_grad(set_to_none=True)

The unit you wrap is the unit that gets all_gathered. Wrap only the root and FSDP gathers the entire model before the forward — which defeats the purpose entirely. Wrap each transformer block and it gathers one block at a time, frees it, and prefetches the next:

   per-layer wrapping:      gather L1 → compute → free → gather L2 → compute → free
                            peak = full model / N  +  one layer

   root-only wrapping:      gather EVERYTHING → compute → free
                            peak = full model    ← no saving at all
Note — new in 2.13: FSDP2 can overlap its two collectives

Historically FSDP's reduce_scatter (gradients, on the backward) and all_gather (parameters, prefetching the next layer) shared a stream and serialized against each other. PyTorch 2.13 adds an opt-in dedicated process group so the two overlap, which directly attacks the 1.5× communication cost that §3 attributes to stage 3. Enable it per module with FSDPModule.set_separate_reduce_scatter_group(enable=True). If you are FSDP-bound, this is the first knob to try, ahead of anything in §9.

Note — reduce_dtype=torch.float32 is a detail worth keeping

Gradients are summed across the world; in bf16, with only 7 mantissa bits, summing many small values loses precision fast. Reducing in fp32 costs a bit of bandwidth and removes a class of subtle convergence problems. Most production configs do this.

Note — checkpointing under FSDP

State is sharded, so torch.save(model.state_dict()) gives you one rank's shard. Use torch.distributed.checkpoint, which saves DTensors with their sharding metadata and can resume at a different world size or parallel layout — a capability you will want and will not have if you roll your own.

Why a row is ✗. Three different reasons, worth separating. y1, y2 and r1 are cheap to rebuild from something already kept, so storing them is pointless. S, P and P_drop are a different matter — see below.

Q and K are kept for each other. Since S = QKᵀ, the gradient of each is written in terms of the other, so neither can be dropped alone. And O does double duty: it is the attention output and the output projection’s input — one tensor, counted once.

Where the 34 lands, and what to attack.

   LayerNorms   x, n1, n2                       4
   Attention    Q, K, V, O, mask1, lse         11
   MLP          z, g, mask2                    19   ← 56% of the layer
                                                     and 16 of it is z and g

The MLP dominates purely because of the 4h width: each tensor stashed there counts four times what an h-wide one does. That is why fusing bias+GeLU pays so well — a fused kernel recomputes z instead of storing it, deleting 8 of the 34 in one change.

And note what activation checkpointing really is in these terms: setting more rows to ✗. Full checkpointing keeps only x and replays the entire layer, taking c from 17 to roughly 2 at the cost of one extra forward (§4’s ~33%). Selective recomputation just picks which rows.

Why the range 10–20 rather than a constant. Fused bias+activation and fused dropout stash fewer tensors; dropping dropout removes both masks; SwiGLU-style gated MLPs use three matrices instead of two and push it back up. The chapter’s ~12 is a modern fused stack; 17 is the textbook unfused count.

⚠️ The three ✗ rows shaped [b,a,s,s] are the entire long-context problem

Every tensor in the 34 is shaped [b,s,h] and scales with s·h. S, P and P_drop are shaped [b,a,s,s] and scale with s². Stored, they would add 5·a·s²·b:

   at s=2048, h=4096, a=32

   5 × a × s² × b  =  80 × sbh bytes    ← the attention matrix
   everything else =  34 × sbh bytes

   over twice the rest of the layer — and QUADRATIC in sequence length

FlashAttention never materializes them. It keeps only lse, one float per query row — a factor of s smaller — and rebuilds P tile by tile during the backward. That is the same running max and log-sum-exp accumulator traced through ring attention in chapter 11 §4; it exists precisely so the backward can reconstruct the probabilities without ever forming them.

So c ≈ 10–20 is a post-FlashAttention constant. Before it, the coefficient grew with sequence length and the activation budget blew up quadratically — which is why long-context training was impractical, and why chapter 11’s context parallelism attacks activations rather than weights.

So the realistic budget on one 80 GB GPU:

   ZeRO-3 state          14 GB
   activations (ckpt)     3 GB
   comm buffers           2 GB
   fragmentation/slack    5 GB
                        ───────
                         24 GB used, 56 GB free → raise the batch size
Note — the diagnostic order when you OOM

Work down this list; each step is cheaper than the one after it.

  1. Reduce micro-batch size, use gradient accumulation to keep the global batch. Free.
  2. Enable activation checkpointing. ~33% compute for a large activation saving.
  3. ZeRO-1 → 2 → 3. Stages 1 and 2 are communication-neutral (same 4Ψ bytes as DDP, not zero); stage 3 costs 1.5×.
  4. reduce_bucket_size / allgather_bucket_size down. Small effect, no downside.
  5. Fuse the loss. nn.LinearCrossEntropyLoss (2.13) never materializes [batch, seq, vocab]. For large vocabularies this is frequently the single largest allocation in the model — up to 4× off peak memory, for one line.
  6. Cheapen the optimizer state. 8-bit AdamW (bitsandbytes) takes 12Ψ → ~3Ψ; bf16 moments take it to 4Ψ for one line of config; Muon keeps one moment rather than two. All three attack the same 12Ψ that ZeRO-1 shards, so count one of them, not both.
  7. Add tensor parallelism (chapter 07) — the only technique here that also cuts activation memory.
  8. Offload to CPU. Big capacity win, big speed cost.
  9. Offload to NVMe. Bigger win, bigger cost.

Measure between steps. torch.cuda.max_memory_allocated() and torch.cuda.memory_summary() tell you where you actually are.

9. Choosing a stage, and gotchas

Note — the decision, in one pass 
   Does 16Ψ fit on one GPU?
        yes → DDP.  (Still the fastest thing that works.)
        no  ↓
   Does 4Ψ + 12Ψ/N fit?
        yes → ZeRO-1.  Free memory, no extra communication.
        no  ↓
   Does 2Ψ + 14Ψ/N fit?
        yes → ZeRO-2.  Still communication-neutral.
        no  ↓
   Does 16Ψ/N fit (+ activations)?
        yes → ZeRO-3 / FSDP.  1.5× communication.
        no  ↓
   Add activation checkpointing, then TP, then more GPUs.
        still no ↓
   Offload (CPU → NVMe).  Accept the slowdown.

Gotchas:

Symptom Cause Fix
OOM at 60% utilization Fragmentation contiguous_gradients, PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
"OVERFLOW! Skipping step" for the first ~20 steps Dynamic loss scaling searching down from 2³² Normal. Lower initial_scale_power, or use bf16
Overflow warnings throughout training Genuine instability, or fp16 range Switch to bf16; check LR and for inf in the data
ZeRO-3 much slower than expected overlap_comm: false, or too-small sharding granularity Enable overlap; shard per transformer block. On FSDP2 (PyTorch ≥ 2.13) also enable the dedicated-process-group overlap
torch.compile(fullgraph=True) fails through FSDP2 PyTorch 2.12 stopped supporting graph-break-free compilation through FSDP2 hooks Compile before fully_shard, or allow graph breaks
Offload makes everything crawl Using torch.optim.Adam instead of DeepSpeedCPUAdam; or pin_memory: false Use the fused CPU optimizer, pin memory
Loss is identical on all ranks and training is 4× slow No DistributedSampler — every rank trains the same data Add one, with set_epoch
state_dict() gives a fragment Parameters are sharded torch.distributed.checkpoint, or gather first
Gradient clipping has no effect Clipping before unscale_ scaler.unscale_(optimizer) first
Slower than DDP for a model that fits You applied ZeRO-3 unnecessarily Drop to ZeRO-1, or plain DDP
Note — the last row is the most common mistake in practice

ZeRO-3 is not "better DDP." For a model that fits comfortably, ZeRO-3 does strictly more communication for memory you did not need. Use the smallest stage that fits.

10. Quick reference

   THE 16 BYTES  (mixed-precision Adam, per parameter)
   ─────────────────────────────────────────────────
     fp16 weights        2  ┐
     fp16 gradients      2  ├─ 4Ψ  "working set"
     fp32 master weights 4  ┐
     Adam momentum       4  ├─ 12Ψ "optimizer state"  ← 75% of the total
     Adam variance       4  ┘
                        ───
                        16 bytes/param

   THE STAGES        memory/GPU        comm
   ──────────        ──────────        ────
     DDP              16Ψ              1×
     ZeRO-1        4Ψ + 12Ψ/N          1×      ← shard optimizer state
     ZeRO-2        2Ψ + 14Ψ/N          1×      ← + gradients
     ZeRO-3           16Ψ/N            1.5×    ← + parameters

   WHY 1 AND 2 ARE FREE
   ────────────────────
     all_reduce = reduce_scatter + all_gather
     DDP already pays for both halves; ZeRO just doesn't reassemble in between.

   ZeRO-R  (residual states)
   ─────────────────────────
     partition_activations           shard replicated activations across MP ranks
     allgather/reduce_bucket_size    cap communication buffers
     contiguous_memory_optimization  defragment

   OFFLOAD LADDER
   ──────────────
     GPU HBM   40–192 GB   1–8 TB/s     ← the layer being computed
     CPU DRAM  0.5–4 TB    ~100 GB/s    ← optimizer states
     NVMe      10s of TB   2–14 GB/s    ← everything idle
python
# ── modern PyTorch (preferred) ─────────────────────────────
from torch.distributed.fsdp import fully_shard, MixedPrecisionPolicy
mp = MixedPrecisionPolicy(param_dtype=torch.bfloat16, reduce_dtype=torch.float32)
for layer in model.layers: fully_shard(layer, mp_policy=mp)
fully_shard(model, mp_policy=mp)

# bf16: no GradScaler needed
with torch.autocast("cuda", dtype=torch.bfloat16):
    loss = model(**batch).loss
loss.backward(); optimizer.step(); optimizer.zero_grad(set_to_none=True)

out = checkpoint(layer, x, use_reentrant=False)     # note the argument
