1. Intra-layer model parallelism

Tensor parallelism is an intra-layer model-parallelism method that splits the model at tensor granularity, inside a layer. Inter-layer model parallelism makes intuitive sense, but for intra-layer parallelism people seeing it for the first time often wonder how it's even possible.

   inter-layer cut                      intra-layer cut
   (split the stack of layers)          (split each layer's tensors)

   ┌─────────────┐                      ┌──────┬──────┐
   │  layer 4    │ ── GPU1              │      │      │
   │  layer 3    │ ── GPU1              │ GPU0 │ GPU1 │   every layer lives
   ├─────────────┤                      │      │      │   on BOTH devices,
   │  layer 2    │ ── GPU2              │      │      │   cut down the middle
   │  layer 1    │ ── GPU2              └──────┴──────┘
   └─────────────┘

The inner-product (matmul) operation we commonly use has the property that you can split the matrices being multiplied, do the work in parallel, and then add or concatenate the results without the final output changing. Parallelizing a model using this property of the matmul is what we call tensor parallelism.

The terminology can be a bit confusing: intra-layer refers to all parallelization that does not happen at layer granularity, so it is the broader category, and tensor parallelism is one way of implementing intra-layer parallelism.

Note — the one algebraic fact this entire chapter rests on

Write Y = X · A. There are exactly two ways to cut A, and each imposes a different way to reassemble:

   CUT A BY COLUMNS                     CUT A BY ROWS
   A = [A₁ | A₂]                        A = [A₁ ; A₂]   (stacked)
   X stays whole                        X must also be cut: X = [X₁ | X₂]

   Y = X·[A₁|A₂] = [X·A₁ | X·A₂]        Y = [X₁|X₂]·[A₁;A₂] = X₁·A₁ + X₂·A₂
        └── CONCATENATE ──┘                                    └── ADD ──┘

Concatenate versus add. That is the whole distinction, and everything else in this chapter — which collective to use, which order to chain layers in, why GeLU forces the ordering — follows from it.

Column & Row parallelism

The following illustrates the column parallelism and row parallelism used in Megatron-LM.

  • Column parallelism is a method that splits the model's parameters (A) vertically (A1, A2).
  • Row parallelism is a method that splits the model's parameters (A) horizontally (A1, A2).
   column parallel                       row parallel

        A                                    A
   ┌────┬────┐                          ┌─────────┐
   │    │    │                          │   A₁    │  → GPU0
   │ A₁ │ A₂ │                          ├─────────┤
   │    │    │                          │   A₂    │  → GPU1
   └────┴────┘                          └─────────┘
    GPU0 GPU1

Note — do the arithmetic by hand once; it makes everything after this obvious

Take the first output element, Y[0,0] = 74:

   unsplit:      0·10 + 1·11 + 2·12 + 3·13  =  0 + 11 + 24 + 39  =  74

   row-parallel: X₁·A₁ = 0·10 + 1·11 = 11      ← GPU 0's PARTIAL sum
                 X₂·A₂ = 2·12 + 3·13 = 63      ← GPU 1's PARTIAL sum
                                        ──
                              11 + 63 = 74      ← needs an ADD across devices

Notice what each device holds before the combine. Under row parallelism each device holds a partial sum of the same output element — neither is a usable answer, and you must add them. Under column parallelism each device holds different, complete output elements — each is already correct, and you only need to place them side by side.

That difference is exactly why the two need different collectives, and why one of them can sometimes be skipped entirely.

Column parallelism: (D, D) → (D, D/n) × n

As seen in the earlier example, column parallelism is the operation that copies the input tensor (X), splits the model's parameters (A) vertically (A1, A2), takes the inner products, and then concatenates.

              ┌──────────────── broadcast X ────────────────┐
              ▼                                             ▼
        ┌──────────┐                                 ┌──────────┐
   GPU0 │ X @ A₁   │                            GPU1 │ X @ A₂   │
        └────┬─────┘                                 └─────┬────┘
             │              all_gather                     │
             └────────────────► [ Y₁ | Y₂ ] ◄──────────────┘

In Megatron-LM the split parameters (A1, A2) are placed on different devices to parallelize the model. Consequently the matmul also happens simultaneously on several GPUs, and distributed programming is needed to handle that. For column parallelism we use the broadcast and all-gather operations.

  • Broadcast is used to send the same input to different GPUs.
  • All-gather is used to collect the matmul results.

Row parallelism: (D, D) → (D/n, D) × n

Row parallelism is the operation that splits the input tensor (X), splits the model's parameters (A) horizontally (A1, A2), takes the inner products, and then adds.

              ┌──────────────── scatter X ──────────────────┐
              ▼                                             ▼
        ┌──────────┐                                 ┌──────────┐
   GPU0 │ X₁ @ A₁  │  partial                   GPU1 │ X₂ @ A₂  │  partial
        └────┬─────┘                                 └─────┬────┘
             │              all_reduce (SUM)               │
             └───────────────► Y₁ + Y₂ ◄───────────────────┘

Likewise, running row parallelism on several GPUs needs distributed programming. For row parallelism we use scatter and all-reduce.

  • Scatter is used to split the input and send the pieces to different GPUs.
  • All-reduce is used to add the matmul results.
python
"""
Reference: RowParallelLinear in Megatron-LM megatron/core/tensor_parallel/layers.py
"""

def forward(self, input_):
    # Set up backprop all-reduce.
    if self.input_is_parallel:
        input_parallel = input_
    else:
        input_parallel = scatter_to_tensor_model_parallel_region(input_)

    # Matrix multiply.
    output_parallel = F.linear(input_parallel, self.weight)

    # All-reduce across all the partitions.
    output_ = reduce_from_tensor_model_parallel_region(output_parallel)

    if not self.skip_bias_add:
        output = output_ + self.bias if self.bias is not None else output_
        output_bias = None
    else:
        output = output_
        output_bias = self.bias
    return output, output_bias
Note — those four _tensor_model_parallel_region functions are the f/g operators from chapter 03

They look like plumbing. They are actually torch.autograd.Functions, and each one's backward is the adjoint of its forward. This is the part that makes tensor parallelism correct rather than merely fast:

Function Forward Backward Megatron name
copy_to_..._region identity all_reduce f
reduce_from_..._region all_reduce identity g
scatter_to_..._region split all_gather —
gather_from_..._region all_gather split —

Look at ColumnParallelLinear.forward: it opens with copy_to_..., which does nothing in the forward pass. Why call it at all? Because in the backward pass, every TP rank computes a gradient w.r.t. the shared input X, and those must be summed. copy_to_... is a no-op forward whose only job is to install that all-reduce on the backward. Communication operations come in adjoint pairs, and half of them are invisible in the forward pass.

Note — bias handling and skip_bias_add

Under column parallelism the bias splits with the columns, so each rank adds its own slice — fine. Under row parallelism the bias belongs to the full output, so it must be added after the all-reduce, not before (adding it on every rank would add it n times). That's why RowParallelLinear adds bias only after reduce_from_.... skip_bias_add exists so the caller can fuse the bias-add with a following operation like dropout or GeLU.

Transformer Block

Now that we understand column and row parallelism, let's look properly at how to parallelize a Transformer. The Transformer block we commonly know is composed as follows. In Megatron-LM, the Layer Norm layers — whose parameters are very small — are replicated to all devices, while the other layers (Attention, MLP) are parallelized via column and row parallelism as above.

   ┌──────────────────── Transformer block ────────────────────┐
   │  LayerNorm      ← replicated on every TP rank             │
   │  Attention      ← column (QKV) → row (out proj)           │
   │  Dropout                                                  │
   │  LayerNorm      ← replicated                              │
   │  MLP            ← column (fc) → row (proj)                │
   │  Dropout                                                  │
   └───────────────────────────────────────────────────────────┘
Note — "replicated" is cheap in parameters and expensive in activations

A LayerNorm has 2 × hidden parameters — nothing. But replicating it means every TP rank materializes the full [batch, seq, hidden] activation for those regions, n times over. For long sequences that redundancy is one of the largest single memory costs in the model. Chapter §5 below is entirely about removing it.

MLP Layer

First let's look at the MLP layer. The MLP layer proceeds in the order Linear1 → GeLU → Linear2 → Dropout.

Here, column parallelism is applied to the first Linear and row parallelism to the second Linear.

   X ──┬──▶ [A₁] ──▶ GeLU ──▶ [B₁] ──┐
       │   column              row   ├──▶ all_reduce ──▶ Z
       └──▶ [A₂] ──▶ GeLU ──▶ [B₂] ──┘
       ▲                              ▲
       f                              g

There are two reasons for applying parallelization in column→row order in the MLP layer.

The first reason is that you can omit the All-gather and Scatter operations.

   WITHOUT the optimization:

   X ─▶ [A₁] ─┐                        ┌─▶ [B₁] ─┐
              ├─ all_gather ─▶ Y ─ scatter ─┤     ├─ all_reduce ─▶ Z
   X ─▶ [A₂] ─┘   ▲                    └─▶ [B₂] ─┘
                  └──────────────────────┘
                  gather then immediately re-split
                  = exactly what you started with

The result of the computation in the green area on the left is the inner product of the input data X with the W parallelized onto each device. Then in the red area this result is All-gathered and concatenated, and then Scattered and split again. The interesting fact here is that because the concatenated tensor is split again, it is identical to what it was before concatenation. So the green area on the right and the green area on the left have the same values. As a result the red area (All-gather–Scatter) can be omitted, which brings a large speed benefit.

This is a peculiar phenomenon that appears only when parallelizing in column→row order. If you parallelized as column–column, row–column, or row–row, the communication occurring between the two Linear layers could not be omitted.

The technique of omitting All-gather and Scatter is implemented in Megatron-LM with the parameters input_is_parallel and gather_output.

Note — why the shapes line up so conveniently

It isn't a coincidence; it's forced by the algebra:

  • Column parallelism produces an output split along its last dimension.
  • Row parallelism consumes an input split along its first (contracted) dimension.

These are the same dimension of the intermediate tensor. So a column-parallel layer's output is already exactly the form a row-parallel layer wants as input. gather_output=False + input_is_parallel=True says "don't undo and redo something that cancels."

   c_fc:   [hidden → 4·hidden]  split by columns → each rank owns 4·hidden/n
   c_proj: [4·hidden → hidden]  split by rows    → each rank needs 4·hidden/n
                                                          ▲ same slice!

The saving is not small. The intermediate activation is [batch, seq, 4·hidden] — the largest tensor in the block. Naively you'd all-gather and re-scatter it twice per block (once forward, once backward). Column→row removes all of that.

The second reason for parallelizing in column–row order is that to omit Scatter and All-gather, the GeLU operation must be performed while parallelized.

The figure above inserts the GeLU operation between the two Linear layers in the situation where Scatter and All-gather are not omitted. If you then implement it so the two operations are omitted, the GeLU must necessarily be computed on each device separately.

But to parallelize GeLU so it runs on different devices, the output of the parallel GeLU must be identical to the output of GeLU computed unparallelized. That is, the following formula must hold. (The ⊚ symbol means concatenation.)

Row parallelism: GeLU(XW₁ + XW₂) = GeLU(XW₁) + GeLU(XW₂)
Column parallelism: GeLU(XW₁ ⊚ XW₂) = GeLU(XW₁) ⊚ GeLU(XW₂)

The problem is that the formula above holds only for column parallelism, and does not hold for row parallelism.

Row parallelism: GeLU(XW₁ + XW₂) ≠ GeLU(XW₁) + GeLU(XW₂)

Let's implement this in code and check.

python
"""
src/megatron_mlp_gelu.py
"""

import torch
from torch.nn.functional import gelu

w = torch.randn(6, 6)
x = torch.randn(6, 6)

class RowParallelLinear(torch.nn.Module):
    def __init__(self):
        super(RowParallelLinear, self).__init__()
        chunked = torch.chunk(w, 2, dim=0)

        # row parallelized parameters
        self.w1 = chunked[0]  # [3, 6]
        self.w2 = chunked[1]  # [3, 6]

    def forward(self, x):
        # GeLU(X1A1 + X2A2) != GeLU(X1A1) + GeLU(X2A2)
        x1, x2 = torch.chunk(x, 2, dim=1)

        # parallel output
        y1 = gelu(x1 @ self.w1) + gelu(x2 @ self.w2)

        # non-parallel output
        y2 = gelu(x1 @ self.w1 + x2 @ self.w2)

        return torch.all(y1 == y2)

class ColumnParallelLinear(torch.nn.Module):
    def __init__(self):
        super(ColumnParallelLinear, self).__init__()
        chunked = torch.chunk(w, 2, dim=1)

        # column parallelized parameters
        self.w1 = chunked[0]  # [6, 3]
        self.w2 = chunked[1]  # [6, 3]

    def forward(self, x):
        # GeLU(X1A1 cat X2A2) == GeLU(X1A1) cat GeLU(X2A2)

        # parallel output
        y1 = torch.cat([gelu(x @ self.w1), gelu(x @ self.w2)], dim=1)

        # non-parallel output
        y2 = gelu(torch.cat([(x @ self.w1), (x @ self.w2)], dim=1))

        return torch.all(y1 == y2)

# Row Parallelism
print("Is GeLU in RowParallelLinear same with non-parallel = ", end="")
print(RowParallelLinear()(x).item())

# Column Parallelism
print("Is GeLU in ColumnParallelLinear same with non-parallel = ", end="")
print(ColumnParallelLinear()(x).item())
Is GeLU in RowParallelLinear same with non-parallel = False
Is GeLU in ColumnParallelLinear same with non-parallel = True

Therefore, to parallelize the GeLU operation, the Linear layer before the GeLU must necessarily be parallelized in the column direction. So parallelizing in column→row order is the most efficient scheme.

Note — the one-sentence reason, in case the code obscured it

GeLU is an elementwise function. Elementwise functions commute with rearranging elements but not with summing them:

   concatenation just relabels positions   →  f(a ⊚ b) = f(a) ⊚ f(b)     ✓ always
   addition combines two values into one   →  f(a + b) ≠ f(a) + f(b)     ✗ unless f is linear

Column parallelism produces a concatenation. Row parallelism produces a sum. Any nonlinearity must therefore sit after a column-parallel layer and before the row-parallel one. The column→row ordering isn't an optimization; it's the only ordering the nonlinearity permits.

This generalizes past GeLU. SwiGLU (used by Llama-family models) has a gate and an up projection, both of which are column-parallel, with the down projection row-parallel — the same pattern, just with two column-parallel matrices feeding an elementwise product.

Multi-head Attention Layer

Next let's look at the multi-head attention layer. It proceeds in the order Linear1 → Split heads → ScaleDotProductAttention → Concat(Merge) heads → Linear2 → Dropout.

"""
Reference: transformers/models/gpt_neo/modeling_gpt_neo.py
"""

class GPTNeoSelfAttention(nn.Module):
    def __init__(self, config, attention_type):

        self.attn_dropout = nn.Dropout(config.attention_dropout)

Megatron-LM parallelizes the Q, K, V linear projections and the output projection of the attention layer. Likewise, the Q, K, V linear projections use column parallelism and the output projection uses row parallelism, creating the column→row pattern. Through this, the Scatter and All-gather operations can be omitted in the attention layer just as in the MLP layer.

Note — attention parallelizes even more naturally than the MLP, because heads are already independent

Splitting the QKV projections column-wise splits them along the head dimension. So each TP rank simply owns a subset of the attention heads and computes them start to finish, with no communication at all inside the attention:

   8 heads, TP = 2

   GPU 0:  heads 0 1 2 3   ──▶ softmax(QKᵀ/√d)V   ──▶ partial output
   GPU 1:  heads 4 5 6 7   ──▶ softmax(QKᵀ/√d)V   ──▶ partial output
                                      ▲
                        NO communication here — heads never interact
                                      │
                               out_proj (row-parallel) ──▶ all_reduce

The softmax — which, unlike GeLU, is not elementwise — is computed within a head, never across heads. So it never straddles a device boundary, and the awkward question that GeLU raised never arises for attention.

The constraint this imposes: num_heads must be divisible by the TP degree. 16 heads with TP=8 gives 2 heads per rank; TP=32 would not work at all.

GQA/MQA changed this constraint

Models written since ~2023 (Llama 2 70B onward, Mistral, most current open models) use grouped-query attention: many query heads share a smaller number of key/value heads. A model might have 64 query heads but only 8 KV heads.

The binding constraint is then the smaller number: TP degree must divide num_key_value_heads. A model with 8 KV heads cannot use TP=16 without replicating KV heads across ranks (which some frameworks do automatically, at a memory cost). This is a very common source of "why won't this model shard at TP=16" confusion, and it postdates most tensor-parallelism tutorials entirely.

Vocab Parallel Embedding

Megatron-LM also parallelizes the word embedding layer. What's unusual is that it parallelizes along the vocab-size dimension. For example, suppose there is a word embedding matrix with vocab size 50,000 — its size is (50000, embedding_dim). Megatron-LM parallelizes this matrix along the vocab-size dimension. This unusual parallelization technique is called Vocab Parallel Embedding.

The figure above shows word embedding without parallelization. When a sequence of length 6 is input, it creates an input tensor of size [6, embedding_dim].

The figure above shows how vocab parallel embedding works. The existing embedding matrix is cut in half into one matrix responsible for tokens 0–24999 and another responsible for tokens 25000–50000. Then when data comes in, tokens beyond the range covered by that matrix are masked. After that, the vectors in the masked portions are all zeroed out, and adding the two matrices' outputs gives a complete input tensor holding the vectors of every word.

   input token ids:   [ 7,  40123,  22,  49999 ]

   GPU 0  (covers 0–24999)          GPU 1  (covers 25000–49999)
   ┌──────────────────────┐         ┌──────────────────────┐
   │  7      → vec(7)     │         │  7      → MASKED → 0 │
   │  40123  → MASKED → 0 │         │  40123  → vec(40123) │
   │  22     → vec(22)    │         │  22     → MASKED → 0 │
   │  49999  → MASKED → 0 │         │  49999  → vec(49999) │
   └──────────┬───────────┘         └───────────┬──────────┘
              └────────── all_reduce (SUM) ─────┘
                              ▼
              [ vec(7), vec(40123), vec(22), vec(49999) ]

def forward(self, input_):
    if self.tensor_model_parallel_size > 1:
        # Build the mask.
        input_mask = (input_ < self.vocab_start_index) | \
                     (input_ >= self.vocab_end_index)

        # Mask the input.
        masked_input = input_.clone() - self.vocab_start_index
        masked_input[input_mask] = 0

    else:
        masked_input = input_
        # Get the embeddings.

    output_parallel = F.embedding(masked_input, self.weight,
                                  self.padding_idx, self.max_norm,
                                  self.norm_type, self.scale_grad_by_freq,
                                  self.sparse)

    # Mask the output embedding.
    if self.tensor_model_parallel_size > 1:
        output_parallel[input_mask, :] = 0.0

    # Reduce across all the model parallel GPUs.
    output = reduce_from_tensor_model_parallel_region(output_parallel)
    return output
Note — why zero-and-sum rather than gather

The masking trick turns a gather problem into an addition problem, and addition is what all_reduce does. Each rank produces a full-shape [batch, seq, hidden] tensor that is correct wherever it owns the token and exactly zero elsewhere. Summing them gives the right answer with one collective and no index bookkeeping.

Note the two-step masking. masked_input[input_mask] = 0 prevents an out-of-bounds index into the local table; then output_parallel[input_mask, :] = 0.0 throws away the garbage that lookup produced. Both are necessary — the first for safety, the second for correctness.

But a problem arises here. Tensor parallelism must be parallelized across an even number of GPUs, and 52527 is not even, so it cannot be divided by 2. To handle this, unused tokens are added to the word embedding matrix to make the vocab size even. This is called the padded vocab size, and in Megatron-LM you can adjust the vocab size with the make-vocab-size-divisible-by argument. (It makes the vocab size a multiple of the value you set.)

In conclusion, Megatron-LM can further increase memory efficiency by applying Vocab Parallel Embedding.

A detail people get wrong: it's not "even", it's "divisible by the TP degree"

With TP=4 a vocab of 52,526 is even but still unusable — it must be divisible by 4. The real requirement is vocab_size % tensor_parallel_size == 0.

In practice the default --make-vocab-size-divisible-by 128 pads much further than strictly necessary, for a second reason: tensor-core efficiency. Matrix dimensions that are multiples of 128 (and for fp16/bf16, of 8 at minimum) hit fast GEMM kernels; awkward sizes fall back to slower paths. So the padding serves both correctness and speed.

The padding tokens are never produced (their logits are masked out in the loss), so they cost a little memory and nothing else.

But a problem arises here. Normally, computing the loss between the logits emitted by the LM Head and the target data proceeds as follows.

However, because Megatron-LM uses Vocab Parallel Embedding, the embedding layer is split across several devices. So if you do weight tying, the output embedding (LM Head) is also split across several devices. Consequently the size of the logits emitted by the model becomes the split vocab size.

As in the figure above, if the vocab size is 50,000, then originally a tensor of (bsz, length, 50000) should be output — but if it is split across 2 devices as in the example, two logits of size (bsz, length, 25000) come out, and each device's logits have different values. This is called Parallel LM Logits. In that case, how should we compute the loss against the target sentence? The target data contains all tokens 0 through 49999, whereas the logits are only half that size.

In this case you must use a special loss function called vocab parallel cross entropy rather than the ordinary cross entropy. The vocab parallel cross-entropy loss computation proceeds as above. From the computed logits, everything except the part that device can cover is masked, and the loss is computed. Then the computed losses are all-reduced to produce the final loss.

@staticmethod
def forward(ctx, vocab_parallel_logits, target):
    # Maximum value along vocab dimension across all GPUs.
    logits_max = torch.max(vocab_parallel_logits, dim=-1)[0]
    torch.distributed.all_reduce(logits_max,
                                 op=torch.distributed.ReduceOp.MAX,
                                 group=get_tensor_model_parallel_group())

    # Subtract the maximum value.
    vocab_parallel_logits.sub_(logits_max.unsqueeze(dim=-1))

    # Get the partition's vocab indecies
    get_vocab_range = VocabUtility.vocab_range_from_per_partition_vocab_size
    partition_vocab_size = vocab_parallel_logits.size()[-1]
    rank = get_tensor_model_parallel_rank()
    world_size = get_tensor_model_parallel_world_size()
    vocab_start_index, vocab_end_index = get_vocab_range(
        partition_vocab_size, rank, world_size)

    # Create a mask of valid vocab ids (1 means it needs to be masked).
    target_mask = (target < vocab_start_index) | (target >= vocab_end_index)
    masked_target = target.clone() - vocab_start_index
    masked_target[target_mask] = 0

    # Get predicted-logits = logits[target].
    logits_2d = vocab_parallel_logits.view(-1, partition_vocab_size)
    masked_target_1d = masked_target.view(-1)

                             device=logits_2d.device)
    predicted_logits_1d = logits_2d[arange_1d, masked_target_1d]
    predicted_logits_1d = predicted_logits_1d.clone().contiguous()
    predicted_logits = predicted_logits_1d.view_as(target)
    predicted_logits[target_mask] = 0.0

    # All reduce is needed to get the chunks from other GPUs.
    torch.distributed.all_reduce(predicted_logits,
                                 op=torch.distributed.ReduceOp.SUM,

Note — this function is doing two separate clever things at once, and it's worth separating them

Thing 1: never materialize the full logits. This is the real motivation, and it is easy to miss. For vocab 50k, batch 8, sequence 2048, the full logit tensor is

   8 × 2048 × 50000 × 2 bytes (bf16) ≈ 1.6 GB      — for ONE tensor
   and its fp32 softmax intermediate ≈ 3.3 GB

That is frequently the single largest allocation in the entire model. Keeping it sharded across TP ranks and never gathering it saves that, times the TP degree. This is why the vocab-parallel loss exists at all — not merely because "the target has tokens the shard doesn't cover."

Thing 2: distributed log-sum-exp, done stably. Cross entropy is

   loss = log( Σ_v exp(z_v) )  −  z_target
          └──── needs ALL v ────┘   └─ lives on exactly one rank ─┘

Both terms straddle the shards, so each becomes a collective:

Step Collective Why
logits_max all_reduce(MAX) Subtract the global max before exp or you overflow. Standard log-sum-exp trick, made distributed
predicted_logits all_reduce(SUM) The target token lives on one rank; every other rank contributes 0
sum_exp_logits (below the truncation) all_reduce(SUM) The denominator sums over the whole vocabulary

Three all-reduces, all on tiny [batch, seq] tensors rather than [batch, seq, vocab]. The communication is negligible; the memory saving is enormous. That's the trade this function makes.

New in PyTorch 2.13: `nn.LinearCrossEntropyLoss` solves "thing 1" without any parallelism at all

The memory argument above — never materialize [batch, seq, vocab] — turned out to be worth solving even on a single GPU. PyTorch 2.13 ships a module that fuses the final linear projection with the cross-entropy computation, so the full logits tensor is never written to HBM. Reported effect: up to 4× lower peak GPU memory for large-vocabulary language-model training.

This does not replace VocabParallelCrossEntropy when your embedding is genuinely sharded across TP ranks — you still need the three collectives above to reduce across shards. But it does mean the memory motivation is no longer a reason to reach for tensor parallelism on its own. If [b, s, V] was the only thing pushing you toward TP, try the fused loss first.

The same idea, in the sharded setting, is what loss_parallel() gives you (see §4).

Note also the predicted_logits[target_mask] = 0.0 line: the same zero-and-sum idiom as VocabParallelEmbedding. Ranks that don't own the target contribute exactly zero to the sum, so all_reduce(SUM) selects the right value without anyone needing to know who owned it.

Note — why the data format matters here specifically

Once compute is spread over many GPUs, the data pipeline becomes the bottleneck. A tokenized pre-training corpus is hundreds of GB; you cannot hold it in RAM, and you cannot afford a Python-level parse per sample when 32 GPUs are each consuming thousands of tokens per second.

Historically there were three strategies, and it is worth knowing why one won:

Where data lives Cost per access Scales to 100s of GB?
lazy disk a syscall and file I/O on every __getitem__ yes, but slow
cached RAM, prefetched none no
mmap disk, mapped into virtual memory page fault on first touch only; OS page cache thereafter yes

mmap wins because it gets cached's access pattern with lazy's memory footprint — the OS page cache does the caching, at page granularity, and crucially it is shared physical memory across processes. With 8 dataloader workers per node, three caches would be 8 copies; one memory map is one copy.

The .bin/.idx split is the other half: fixed-width offsets in a small index file, raw token ids in a large binary. Random access becomes arithmetic rather than parsing.

This design came from fairseq's indexed_dataset, was copied into Megatron, and now lives in megatron.core.datasets (IndexedDataset, GPTDataset). The three-way choice is gone — mmap is the only implementation — but the file layout is unchanged, so this is still what your .bin/.idx files are.

Note — "packing", and why it costs a subtlety people forget

Concatenating documents and slicing at a fixed length is called sequence packing, and it's near-universal in pre-training because padding is pure waste: pad 30% of your tokens and you've thrown away 30% of your compute.

The cost: a packed sequence contains fragments of several documents, so attention can look across a document boundary. The <eod> token marks where the boundaries are but does not by itself prevent attention from crossing them. Strictly, you want a block-diagonal attention mask so each document only attends to itself. Many implementations don't bother — the model largely learns to treat <eod> as a reset — but modern packing implementations (and FlashAttention's variable-length API) do handle it properly. Worth knowing which behaviour your stack has.

Since PyTorch 2.10 this has a native op: torch.nn.attention.varlen_attn, which takes cumulative sequence-length offsets (cu_seq_q, cu_seq_k) and computes attention over ragged, packed batches without padding and without letting attention cross document boundaries. One signature note if you find older examples: is_causal was removed in 2.11 in favour of window_size — use window_size=(-1, 0) for causal, (W, 0) for a causal sliding window, and the default (-1, -1) for full attention. The optional arguments also became keyword-only.

VocabParallelEmbedding ColwiseParallel() on the embedding + RowwiseParallel on the head, or loss_parallel()
hand-computed rank groups mesh["tp"]

The column→row pairing is still yours to get right — note w1/w3 colwise and w2 rowwise for a SwiGLU MLP. The framework inserts the collectives; it does not choose the split for you. Everything you learned in §2 is still the knowledge you need; you just express it as annotations instead of layer rewrites.

5. Sequence parallelism — the free companion

Recall from §2: LayerNorm and dropout are replicated on every TP rank. Each rank materializes the full [batch, seq, hidden] activation for those regions. With TP=8 that's 8 identical copies of one of the largest tensors in the model.

Sequence parallelism (Korthikanti et al., 2022) fixes this by sharding those regions along the sequence dimension:

   vanilla TP
   ───────────
   [ LayerNorm ]────▶[ attention / MLP ]────▶[ LayerNorm ]
     replicated         column→row              replicated
     FULL b×s×h         sharded                 FULL b×s×h
     on every rank                              on every rank
                    └── all_reduce ──┘

   TP + SP
   ───────
   [ LN sharded by seq ]──all_gather──▶[ attn/MLP ]──reduce_scatter──▶[ LN sharded ]
     b×(s/n)×h per rank                  sharded                       b×(s/n)×h
     ▲ nothing is ever fully replicated
Note — why this is close to free, and it comes straight from chapter 03

The identity all_reduce = reduce_scatter + all_gather means the one all-reduce that TP already performed can be split into its two halves and moved outward — an all-gather on the way in, a reduce-scatter on the way out.

   TP alone:   ... all_reduce ...                  volume = 2D
   TP + SP:    all_gather ... reduce_scatter       volume = D + D = 2D

Identical communication volume. Strictly less memory. That's why it's essentially always on in modern Megatron configurations (--sequence-parallel), and why any tensor-parallel setup without it leaves real memory on the table.

The memory saved is roughly the LayerNorm/dropout activations divided by the TP degree, which for long sequences is substantial. Combined with selective activation recomputation (recompute only attention, keep the cheap parts), it's the standard recipe for making long-context training fit.

Note the naming overlap: this "sequence parallelism" is a companion to TP within a node. Context parallelism (Ring Attention, Ulysses) is a different, larger axis that shards the sequence for the attention computation itself. Chapter 10 touches on it.

Section 7 of 12

6. The cost model and where TP may live

Note — count the collectives, because the count is what constrains placement

Per transformer layer, per training step:

   forward:   1 all_reduce (attention out-proj)  +  1 all_reduce (MLP down-proj)
   backward:  1 all_reduce (f in attention)      +  1 all_reduce (f in MLP)
   ────────────────────────────────────────────────────────────────────
              4 all_reduces per layer per step

For a 40-layer model: 160 all-reduces per step, each on a [batch, seq, hidden] tensor, each on the critical path — the next operation literally needs the result, so unlike DDP's gradient reduction they cannot be overlapped with computation.

Compare across the axes:

Axis Collectives per step Overlappable? Volume per event
DP 1 (bucketed into ~8) yes, with backward model size
PP 2m P2P sends partially one activation
TP 4 × layers no activation size
The practical consequence, and it is close to a hard rule: keep the tensor-parallel group inside a single node, over NVLink

Rough per-GPU bandwidths, order of magnitude only:

Link Bandwidth Suitable for
NVLink / NVSwitch hundreds of GB/s TP
PCIe tens of GB/s marginal for TP
InfiniBand (per NIC) ~25–50 GB/s PP, DP
Ethernet often less DP only

A TP group spanning nodes produces correct results, several times slower, with no error to point at. If a multi-node job is inexplicably slow, check TP placement first. This also caps TP degree at GPUs-per-node — typically 8.

Note — when to reach for TP at all

In the decision order from chapter 04:

  1. Model fits → DDP.
  2. Doesn't fit → FSDP/ZeRO-3. Far less invasive, communication is prefetchable.
  3. Still doesn't fit, or activations (not parameters) are the constraint → add TP, degree ≤ node size.
  4. Still doesn't fit → add PP across nodes.

TP is the axis to add third, not first. Its distinctive advantage over FSDP is that it reduces activation memory too (each rank holds 1/n of the intermediate tensors), which FSDP does not. That's the specific situation where TP earns its communication cost.

Note — the RNG issue is subtle and worth expanding

Two regions of the model need different random-number behaviour under TP:

  • Replicated regions (LayerNorm, the dropout applied to the full activation) must produce the same dropout mask on every TP rank — otherwise the replicas compute different things and the model is inconsistent.
  • Parallel regions (attention dropout inside each rank's own heads) must produce different masks per rank, because each rank owns different heads and they should be dropped independently.

Megatron maintains two RNG states for exactly this reason (get_cuda_rng_tracker). If you implement TP by hand and ignore it, you'll get a model that trains but is subtly wrong — the worst failure mode there is.

Note — checkpointing under TP

Weights are physically sharded, so a checkpoint saved at TP=4 has four files that mean nothing individually. Converting between TP degrees requires gathering and re-splitting. Options:

  • Megatron Bridge — NVIDIA's bidirectional HF ↔ Megatron checkpoint converter, with ready-made recipes for common architectures. This is the current answer and much less painful than the old scripts.
  • Megatron's tools/checkpoint/ conversion scripts (TP/PP degree changes).
  • torch.distributed.checkpoint — the modern, resharding-aware format; saves DTensors with their sharding metadata so a job can resume at a different parallel layout.

Plan for this before a long run. "We need to resume at a different TP degree" is a very common request and a miserable surprise.

8. Quick reference

   THE ONE ALGEBRAIC FACT
   ──────────────────────
   Y = X·A

   column split:  A = [A₁|A₂]   →  Y = [X·A₁ | X·A₂]     CONCATENATE
   row split:     A = [A₁;A₂]   →  Y =  X₁·A₁ + X₂·A₂    ADD
                  (X must split too)

   THE PAIRING RULE
   ────────────────
   column → row,  with the nonlinearity in between
   because  f(a ⊚ b) = f(a) ⊚ f(b)   but   f(a+b) ≠ f(a)+f(b)

   COLLECTIVES
   ───────────
   column parallel:  broadcast in  /  all_gather out  (often skipped)
   row parallel:     scatter in    /  all_reduce out

   THE ADJOINT PAIRS  (f and g)
   ───────────────────────────
   f = copy_to_region     : forward identity   , backward all_reduce
   g = reduce_from_region : forward all_reduce , backward identity

   TRANSFORMER BLOCK
   ─────────────────
   LayerNorm          replicated  (→ shard it with sequence parallelism)
   Q,K,V proj         COLUMN      (= each rank owns a subset of heads)
   attention          local, no comm
   out proj           ROW         → all_reduce
   LayerNorm          replicated
   MLP w1 / w3 (gate,up)  COLUMN
   MLP w2 (down)          ROW     → all_reduce
                      ────────────────────────
                      4 all_reduces / layer / step

   EMBEDDING + LOSS
   ────────────────
   VocabParallelEmbedding : shard the VOCAB dim, mask out-of-range, all_reduce(SUM)
   VocabParallelCrossEnt  : all_reduce(MAX) for stability,
                            all_reduce(SUM) for the target logit,
                            all_reduce(SUM) for the denominator
                            → never materializes [b, s, V]

   CONSTRAINTS
   ───────────
   TP must divide:  num_heads, num_KV_heads (GQA!), hidden, ffn_hidden, vocab
   TP degree ≤ GPUs per node.  Always.
