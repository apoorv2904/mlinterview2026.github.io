0. Where this chapter sits

Note — the throughline from chapters 03 and 04

Chapter 03 taught you scatter, gather, broadcast, reduce, and all_reduce. Chapter 04 said data parallelism is "all_reduce of gradients." This chapter shows you the two implementations PyTorch actually ships, and the interesting part is that they use different primitives:

DataParallel DistributedDataParallel
Split the batch scatter DistributedSampler (no comm — each process reads its own slice)
Distribute the model broadcast, every step broadcast once, at construction
Collect outputs gather to GPU 0 nothing — loss stays local
Combine gradients reduce to GPU 0 all_reduce
Update on GPU 0, then re-broadcast independently on every rank

Read down the two columns and the entire design argument of this chapter is visible: DP has a master device, DDP does not. Replacing reduce-to-a-master with all_reduce-to-everyone is what removes the master, and removing the master is what removes the re-broadcast, the memory imbalance, and the single-process bottleneck all at once.

1. `torch.nn.DataParallel`

First let's look at how the familiar torch.nn.DataParallel works. torch.nn.DataParallel is a multi-thread module that operates on a single node with multiple GPUs.

1) Forward Pass

  1. Scatter the input mini-batch and send the pieces to each device.
  2. Broadcast the model parameters sitting on GPU 0 to GPUs 1, 2, 3.
  3. Forward through the model replicated on each device to compute logits.
  4. Gather the computed logits back onto GPU 0.
  5. Compute the loss from the logits (with loss reduction).
                          ┌── mini-batch (128) ──┐
                          └──────────┬───────────┘
                            1. scatter │
              ┌──────────────┬────────┴────────┬──────────────┐
              ▼              ▼                 ▼              ▼
          ┌───────┐      ┌───────┐         ┌───────┐      ┌───────┐
          │ GPU 0 │      │ GPU 1 │         │ GPU 2 │      │ GPU 3 │
          │ 32 ex │      │ 32 ex │         │ 32 ex │      │ 32 ex │
          └───┬───┘      └───┬───┘         └───┬───┘      └───┬───┘
              │  ▲           │  ▲              │  ▲           │  ▲
              │  └───────────┴──┴─ 2. broadcast model ────────┘  │
              │              │                 │                 │
              │  3. forward  │                 │                 │
              ▼              ▼                 ▼                 ▼
           logits         logits            logits            logits
              └──────────────┴────────┬────────┴─────────────────┘
                            4. gather │  ← all logits land on GPU 0
                                      ▼
                              ┌───────────────┐
                              │ GPU 0: loss   │   5. loss (reduction)
                              └───────────────┘
                               ▲ this device now holds
                                 4× the activations of the others

Expressed as code, it looks like this.

python
import torch.nn as nn

def data_parallel(module, inputs, labels, device_ids, output_device):
    inputs = nn.parallel.scatter(inputs, device_ids)
    # Scatter the input data to device_ids

    replicas = nn.parallel.replicate(module, device_ids)
    # Replicate the model onto device_ids

    logit = nn.parallel.parallel_apply(replicas, inputs)
    # The model replicated on each device forwards that device's data

    logits = nn.parallel.gather(outputs, output_device)
    # Collect the models' logits onto output_device (a single device)

    return logits
Note — this snippet has a typo, and it's instructive

parallel_apply returns into logit, but the next line gathers outputs, which is never defined. The intent is nn.parallel.gather(logit, output_device). Worth noticing because the four function names are the real content here: scatter, replicate, parallel_apply, gather are exactly the chapter-03 collectives, exposed as a public API you can call yourself. nn.DataParallel is little more than these four lines in a forward().

Note — replicate runs on every forward pass, and that is the expensive part

Step 2 isn't a one-time setup cost. Every single iteration, the parameters updated on GPU 0 are copied to GPUs 1–3 before the forward can proceed. For BERT-base (110M params, 440 MB in fp32) across 4 GPUs, that's ~1.3 GB of PCIe traffic per step doing nothing but undoing the fact that only one device did the update. Hold onto this — it's problem #2 in §2.

2) Backward Pass

  1. Scatter the computed loss to each device.
  2. Using the received loss, perform backward on each device to compute gradients.
  3. Reduce all computed gradients onto GPU 0, summing them there.
  4. Update the model on GPU 0 using the summed gradients.
                              ┌───────────────┐
                              │ GPU 0: loss   │
                              └───────┬───────┘
                            1. scatter │
              ┌──────────────┬────────┴────────┬──────────────┐
              ▼              ▼                 ▼              ▼
          ┌───────┐      ┌───────┐         ┌───────┐      ┌───────┐
          │backward│     │backward│        │backward│     │backward│   2.
          └───┬───┘      └───┬───┘         └───┬───┘      └───┬───┘
              │  ∇₀          │  ∇₁             │  ∇₂          │  ∇₃
              └──────────────┴────────┬────────┴──────────────┘
                            3. reduce │  ← sum onto GPU 0 only
                                      ▼
                            ┌────────────────────┐
                            │ GPU 0: step()      │  4. only this device
                            │ updates the model  │     has a valid model now
                            └────────────────────┘
                                      │
                                      └──▶ must broadcast again next step

For anyone who doesn't know…

  • loss.backward(): differentiates to compute the gradients.
  • optimizer.step(): updates the parameters using the computed gradients.
  • Computation cost: backward() > step().
   relative cost of one training iteration

   forward   ████████
   backward  ████████████████████        ← roughly 2× forward
   step      ███                         ← cheap: an elementwise update
Note — why "backward() > step()" is the load-bearing fact of this chapter

It looks like a throwaway remark. It isn't: it's the premise of the overlap argument in §3. backward() is a long, heavy, incremental computation, which means it offers a long window during which the network could be busy. step() is short and elementwise. If you want to hide communication behind computation, backward() is the only place with enough room to hide it.

Roughly: backward costs about twice forward (it computes gradients w.r.t. both inputs and weights), while step() is a handful of elementwise operations over the parameters.

python
"""
dp_demo.py  —  single process, 4 GPUs.  Shown for contrast; do not use in production.
"""
import torch
from torch import nn
from torch.optim import AdamW
from torch.utils.data import DataLoader
from datasets import load_dataset
from transformers import AutoModelForSequenceClassification, AutoTokenizer

ds = load_dataset("nyu-mll/multi_nli")["train"]
tok = AutoTokenizer.from_pretrained("bert-base-cased")

def collate(batch):
    enc = tok([b["premise"] for b in batch], [b["hypothesis"] for b in batch],
              padding=True, truncation=True, max_length=128, return_tensors="pt")
    enc["labels"] = torch.tensor([b["label"] for b in batch])
    return enc

# NOTE: batch_size here is the GLOBAL batch. DataParallel splits it internally.
loader = DataLoader(ds, batch_size=128, collate_fn=collate, num_workers=4)

model = AutoModelForSequenceClassification.from_pretrained(
    "bert-base-cased", num_labels=3
).cuda()
model = nn.DataParallel(model, device_ids=[0, 1, 2, 3], output_device=0)

optimizer = AdamW(model.parameters(), lr=3e-5)

for i, batch in enumerate(loader):
    optimizer.zero_grad(set_to_none=True)
    batch = {k: v.cuda() for k, v in batch.items()}
    loss = model(**batch).loss    # shape (4,) — one loss per device
    loss = loss.mean()            # -> scalar; backward() requires this
    loss.backward()
    optimizer.step()
Note — the one line that makes it data-parallel, and the one that trips people up

nn.DataParallel(model, device_ids=[0,1,2,3]) is the whole change. That convenience is exactly why DP was popular, and why it survives in old code you will inherit.

Two details to carry forward. First, batch_size=128 here is the global batch, split 32-per-device internally — under DDP the same number means something different (§3), which is a genuine source of confusion when porting scripts. Second, loss.mean(): because the model returns one loss per device, what comes back is a tensor of shape (4,), and backward() requires a scalar. Omitting it raises grad can be implicitly created only for scalar outputs, which is the most common error people hit the first time they wrap a Hugging Face model in DataParallel.

   nvidia-smi during DataParallel training

   GPU 0  ██████████████████████████  22.1 GB   ← logits + loss + master model
   GPU 1  ███████████                 9.4 GB
   GPU 2  ███████████                 9.4 GB
   GPU 3  ███████████                 9.4 GB
                                      ▲ the imbalance the next paragraph is about

Training works fine on multiple GPUs. The problem, though, is that because logits pile up on GPU 0, a GPU memory imbalance occurs. You can mitigate this to some extent by changing the design so that what gets gathered onto device 0 is the loss rather than the logits — because compared to logits, a loss is a scalar and therefore far smaller. This is the same idea as DataParallelCriterion from PyTorch-Encoding, and you can get it simply by overriding the forward function.

   Before: gather LOGITS            After: gather LOSS
   ───────────────────────          ──────────────────────
   [B/4, seq, vocab] per GPU        [1] per GPU
        │                                │
        ▼  gather                        ▼  gather
   GPU 0 holds [B, seq, vocab]       GPU 0 holds [4]
   = hundreds of MB → GBs            = 16 bytes

The key point is to make the loss computation and the loss reduction run inside the multi-thread region. Since the model's forward function is already running in multiple threads, if you put the loss computation inside the forward function it becomes very easy to implement.

One peculiarity is that implementing it this way makes the loss reduction happen twice. Inside the multi-thread region a reduction from batch_size//4 values down to 1 happens once (step 4 in the figure), and then the 4 losses emitted by each device get reduced to 1 again (step 5 in the figure). Even so, this is far more efficient, because the loss computation can be parallelized and the memory burden on GPU 0 is small.

python
"""
src/custom_data_parallel.py
"""

from torch import nn

# an ordinary model that outputs logits
class Model(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = nn.Linear(768, 3)

    def forward(self, inputs):
        outputs = self.linear(inputs)
        return outputs

# a parallel model that outputs the loss from the forward pass
class ParallelLossModel(Model):
    def __init__(self):
        super().__init__()

    def forward(self, inputs, labels):
        logits = super(ParallelLossModel, self).forward(inputs)
        loss = nn.CrossEntropyLoss(reduction="mean")(logits, labels)
        return loss
Note — why the double reduction is harmless here, and when it wouldn't be

mean of means equals the overall mean only when every group has the same size. With batch_size=128 over 4 GPUs, each device gets exactly 32, so the two-stage mean is exact.

It stops being exact on the last batch of an epoch, when the batch may not divide evenly — say 100 examples split as 25/25/25/25 is fine, but 99 split as 25/25/25/24 is not. The device with 24 examples contributes each of its examples with weight 1/24 instead of 1/25, so those examples are slightly over-weighted in the final average.

   equal split:     mean(mean(32), mean(32), mean(32), mean(32)) == mean(128)   ✓
   ragged split:    mean(mean(25), mean(25), mean(25), mean(24)) != mean(99)    ✗

In practice the error is tiny and everyone ignores it. But it is the same class of bug that bites much harder in DDP with variable-length sequences, where per-device token counts genuinely differ — there, if you want token-level averaging, you must sum the losses and all-reduce the token counts rather than averaging the averages.

Fortunately, the Huggingface Transformers models we use often have the ability to compute the loss right in the forward pass built in. So we'll skip that step and use the transformers feature instead. The code below passes labels to the Transformers model's labels argument and gets the loss directly.

python
"""
src/efficient_data_parallel.py
"""

# 1 ~ 4 omitted...

# 5. start training
for i, data in enumerate(data_loader):
    optimizer.zero_grad()
    tokens = tokenizer(
        data["premise"],
        data["hypothesis"],
        padding=True,
        truncation=True,
        max_length=512,
        return_tensors="pt",
    )

    loss = model(
        input_ids=tokens.input_ids.cuda(),
        attention_mask=tokens.attention_mask.cuda(),
        labels=data["labels"],
    ).loss

    loss = loss.mean()
    # (4,) -> (1,)
    loss.backward()
    optimizer.step()

    if i % 10 == 0:
        print(f"step:{i}, loss:{loss}")

    if i == 300:
        break
Note — that loss.mean() is not cosmetic

With DP, the model's forward now returns one loss per device, so what comes back is a tensor of shape (4,), not a scalar. backward() requires a scalar. The .mean() is step 5 of the figure — the second reduction — written out explicitly. Omitting it raises grad can be implicitly created only for scalar outputs, which is one of the most common errors people hit the first time they wrap a Huggingface model in DataParallel.

2. Problems with `torch.nn.DataParallel`

1) It's a multi-thread module, which is inefficient in Python.2) The model updated on one device has to be replicated to the other devices at every step.Solution? ➝ All-reduce!! 👍But… 🤔The Reduce + Broadcast implementationThe All-to-All implementation

1) It's a multi-thread module, which is inefficient in Python.

Because of the GIL (Global Interpreter Lock), Python cannot run multiple threads simultaneously within a single process. So fundamentally we need to build this as a multi-process program rather than a multi-threaded one, so that several processes can run at the same time.

Note — what the GIL costs you concretely

The GPU kernels themselves release the GIL, so the actual matmuls do overlap. What does not overlap is everything the Python interpreter must do to launch them: building the autograd graph, dispatching ~1,000+ operator calls per BERT forward, indexing tensors, and running the replicate/scatter/gather bookkeeping. With one process driving four GPUs, that Python work is serialized and becomes the bottleneck — the GPUs sit idle waiting to be fed.

The practical consequence: DP typically delivers well under half the scaling of DDP on the same 4 GPUs, and the gap widens with more devices and with smaller models (smaller kernels = less GPU time to hide the Python overhead behind).

   4 GPUs, same model, same batch

   ideal      ████████████████  4.0×
   DDP        ██████████████    3.5× ish
   DP         ██████            1.5–2.5× ish, model-dependent
   1 GPU      ████              1.0×

2) The model updated on one device has to be replicated to the other devices at every step.

The current scheme gathers the gradients computed on each device onto a single device and updates there, so the updated model must be broadcast to the other devices every time — and that process is quite expensive. But if, instead of gathering the gradients, each device performed step() on its own, we wouldn't need to replicate the model every time. How can we implement that?

Solution? ➝ All-reduce!! 👍

   before all_reduce                    after all_reduce
   GPU0: ∇₀                             GPU0: ∇₀+∇₁+∇₂+∇₃
   GPU1: ∇₁            ═══════▶         GPU1: ∇₀+∇₁+∇₂+∇₃
   GPU2: ∇₂                             GPU2: ∇₀+∇₁+∇₂+∇₃
   GPU3: ∇₃                             GPU3: ∇₀+∇₁+∇₂+∇₃

   every device now has the same gradient
   → every device can run step() itself
   → no device is special → nothing to broadcast

The answer is the all-reduce operation we learned earlier. If we sum the gradients computed on each device and distribute the result evenly to all devices, each device can run step() on its own. Then there's no need to copy the model from a particular device every time. So we should improve the existing approach by making use of all-reduce.

Note — this is the pivotal paragraph of the chapter

Read the causal chain once more, because it explains every design decision in DDP:

   use all_reduce instead of reduce
        └─▶ every rank has identical gradients
              └─▶ every rank runs an identical optimizer step
                    └─▶ every rank has identical weights, always
                          └─▶ no master, no re-broadcast, no memory imbalance,
                              no single process bottleneck

The invariant at the end — all replicas hold identical weights at the start of every step — is what data parallelism actually rests on. DP maintains it by copying from a master. DDP maintains it by having every rank independently compute the same thing. The second is strictly better, and the only reason it works is that all_reduce gives everyone the same bytes.

But… 🤔

However, all-reduce is a very expensive operation. Why is that? Let's look at how all-reduce is implemented in detail.

The Reduce + Broadcast implementation

   phase 1: reduce to master        phase 2: broadcast from master

        ∇₀ ─┐                              ┌─▶ GPU0
        ∇₁ ─┼──▶ ┌────────┐                ├─▶ GPU1
        ∇₂ ─┼──▶ │ GPU 0  │ ──────────────▶┼─▶ GPU2
        ∇₃ ─┘    │ sums   │                └─▶ GPU3
                 └────────┘
                     ▲
        GPU 0 sends and receives (N−1)·D bytes.
        Its link is the bottleneck; cost grows with N.

The All-to-All implementation

   every device sends its gradient to every other device,
   then each sums locally

        GPU0 ⇄ GPU1        each device sends D bytes to (N−1) peers
         ⇅  ╳  ⇅           total traffic = N·(N−1)·D
        GPU2 ⇄ GPU3        no master bottleneck, but traffic explodes as N²
Note — the scorecard, so the next section's punchline lands
Implementation Bytes sent per rank Bottleneck
Reduce + Broadcast (N−1)·D at the master; D up + D down on every other rank one device's link; grows linearly with N
All-to-All (N−1)·D on every rank total traffic grows as N²
Ring all-reduce 2·(N−1)/N·D ≈ 2D no hot spot; volume bounded in N, though the 2(N−1) steps mean latency still grows

Both naive schemes get worse as you add GPUs, which is fatal for a technique whose entire purpose is adding GPUs. The next section's algorithm is the fix.

Ring All-reduce 💍

Ring all-reduce comes from HPC — Patarasuk and Yuan described the bandwidth-optimal ring algorithm in 2009. Baidu's 2017 release brought it into deep learning, where it showed dramatically better performance than the existing approaches and became the core of DDP's design.

  • https://github.com/baidu-research/baidu-allreduce
   Arrange the ranks in a ring. Split each gradient tensor into N chunks.

              ┌──────▶ GPU0 ──────▶ GPU1 ──────┐
              │                                 ▼
            GPU3 ◀────────────────────────── GPU2

   Phase 1 — reduce-scatter (N−1 steps)
     each step: send one chunk right, add the chunk you receive
     after N−1 steps: rank i holds the fully-summed chunk i

   Phase 2 — all-gather (N−1 steps)
     circulate the finished chunks around the ring
     after N−1 steps: everyone holds every finished chunk

   Bytes per rank = 2·(N−1)/N·D  →  ≈ 2D, CONSTANT in N
   Every link is busy the whole time; no device is special.
Note — the identity from chapter 03, made concrete

That two-phase structure is exactly

   all_reduce  =  reduce_scatter  +  all_gather

which chapter 03 introduced as an algebraic curiosity. It isn't a curiosity — it is the implementation. And it explains the factor of 2 in the cost: an all-reduce moves twice what either half moves alone, which is the reason ZeRO-2 (chapter 08) can drop the gradient step to half its cost by keeping only the reduce-scatter half. Note that ZeRO-2's total volume still matches DDP's: it all-gathers the updated parameters after the step instead of all-reducing the gradients before it.

You will not implement this yourself. NCCL picks ring or tree automatically based on message size and topology — ring for large tensors (bandwidth-optimal), tree for small ones (latency-optimal, O(log N) depth instead of 2(N−1) steps). This is also why bucketing matters so much: it converts many latency-bound small reductions into a few bandwidth-bound large ones.

What is DDP?

DDP is a data-parallel-processing module that appeared to fix the problems of the existing DataParallel. It is a multi-process module that works on single/multi-node with multiple GPUs. Because it uses all-reduce, the concept of a master process disappears, so the training process becomes very simple.

   ┌── process 0 ──┐ ┌── process 1 ──┐ ┌── process 2 ──┐ ┌── process 3 ──┐
   │   GPU 0       │ │   GPU 1       │ │   GPU 2       │ │   GPU 3       │
   │   own data    │ │   own data    │ │   own data    │ │   own data    │
   │   forward     │ │   forward     │ │   forward     │ │   forward     │
   │   backward    │ │   backward    │ │   backward    │ │   backward    │
   └───────┬───────┘ └───────┬───────┘ └───────┬───────┘ └───────┬───────┘
           └─────────────────┴────── all_reduce ┴────────────────┘
   ┌───────────────┐ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
   │   step()      │ │   step()      │ │   step()      │ │   step()      │
   └───────────────┘ └───────────────┘ └───────────────┘ └───────────────┘

   Symmetric. Every process runs the same code. No rank is special.
Note — where the batch splitting went

DP scattered the batch at runtime, which meant one process had to read all 128 examples and then ship them out. DDP has no such step: each process independently loads only the examples assigned to it. That's what DistributedSampler does — it's a sampler, not a collective. It deterministically partitions the index space so that rank i reads indices i, i+N, i+2N, …, with no communication at all.

This is a small design detail with a large consequence: data loading also parallelizes, whereas under DP the single process's dataloader was a shared bottleneck.

python
"""
ddp.py  —  torchrun --standalone --nproc_per_node=4 ddp.py
"""
import os

import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.optim import AdamW
from torch.utils.data import DataLoader, DistributedSampler
from datasets import load_dataset
from transformers import AutoModelForSequenceClassification, AutoTokenizer

# 1. initialize the process group.  set_device FIRST, then init.
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
dist.init_process_group("nccl", device_id=torch.device(f"cuda:{local_rank}"))
rank, world_size = dist.get_rank(), dist.get_world_size()

# 2. dataset
ds = load_dataset("nyu-mll/multi_nli")["train"]
tok = AutoTokenizer.from_pretrained("bert-base-cased")

def collate(batch):
    enc = tok([b["premise"] for b in batch], [b["hypothesis"] for b in batch],
              padding=True, truncation=True, max_length=128, return_tensors="pt")
    enc["labels"] = torch.tensor([b["label"] for b in batch])
    return enc

# 3. DistributedSampler partitions the index space — no communication involved
sampler = DistributedSampler(ds, num_replicas=world_size, rank=rank,
                             shuffle=True, drop_last=True)
loader = DataLoader(ds, batch_size=32,          # PER PROCESS, not global
                    sampler=sampler, collate_fn=collate,
                    num_workers=4, pin_memory=True, drop_last=True)

# 4. model
model = AutoModelForSequenceClassification.from_pretrained(
    "bert-base-cased", num_labels=3
).to(local_rank)
model = DDP(model, device_ids=[local_rank], bucket_cap_mb=25)

optimizer = AdamW(model.parameters(), lr=3e-5, fused=True)

# 5. train
try:
    for epoch in range(3):
        sampler.set_epoch(epoch)                # NOT optional — see the note below
        for batch in loader:
            optimizer.zero_grad(set_to_none=True)
            batch = {k: v.to(local_rank, non_blocking=True) for k, v in batch.items()}
            with torch.autocast("cuda", dtype=torch.bfloat16):
                loss = model(**batch).loss
            loss.backward()                     # all_reduce happens in here, overlapped
            optimizer.step()
finally:
    dist.destroy_process_group()

Note — batch_size=32 here, batch_size=128 in the DP script. This is the single most important line to understand when porting

Under DDP, batch_size is per process. The global batch is:

global_batch = batch_size × world_size × grad_accumulation_steps
             = 32 × 4 × 1 = 128

So both scripts above train on the same global batch of 128 — deliberately. But this trips up almost everyone at least once: taking a single-GPU script with batch_size=128 and launching it on 8 GPUs silently gives you a global batch of 1,024, an 8× effective change, which usually needs a learning-rate change too (chapter 04's linear scaling rule). Nothing errors. The loss curve just looks different and you don't know why.

Note — no .mean() this time, and no loss_fn

Compare to the DP loop: DP needed loss.mean() because forward returned one loss per device. Under DDP each process computes exactly one scalar loss for its own shard, so backward() works directly. Notice too that no all-reduce appears anywhere in this loop — DDP registers autograd hooks at construction time, so the gradient synchronization happens invisibly inside loss.backward(). That invisibility is the point of §3's final part.

Three lines in that script that are silently wrong if you omit them

Every one of these produces a job that runs, converges, and is quietly worse or less portable. None of them errors.

  1. sampler.set_epoch(epoch). DistributedSampler derives its shuffle from an internal epoch counter that defaults to 0 and never advances on its own. Without this call every epoch sees the data in the identical order — a real quality regression that is very hard to spot, because nothing about the run looks unusual.
  2. LOCAL_RANK, not rank, for set_device. On node 1 of a 2-node job, rank is 4–7 but the node only has cuda:0–cuda:3. Single-node code that uses rank works fine right up until you add a second node.
  3. dist.destroy_process_group() in a finally. Leaves NCCL communicators dangling otherwise; recent PyTorch warns on exit and it can hang at shutdown. A crashing rank should not take the rest of the job's teardown with it.

Two smaller ones: call set_device before init_process_group, or ranks can bind to device 0 and hang; and pass drop_last=True to both the sampler and the loader, or ranks can run different numbers of steps and deadlock on a collective nobody else joins.

On launching: since PyTorch 2.12, plain torchrun --nproc_per_node=4 script.py — with neither --standalone nor --master-port — picks an OS-assigned free port rather than hard-coding 29500, which stops concurrent jobs colliding with "Address already in use". --standalone is unaffected.

But wait — when is the best time to run the all-reduce?

  • Is it better to do the all-reduce together with the backward() computation?
  • Or after backward() is completely finished, before step() begins?
   Option A — sequential: wait for all gradients, then communicate

   compute  ████████████████████                        (backward)
   network                      ████████████            (all_reduce)
            └──────────── total ────────────────────┘   GPU idle during comm

   Option B — overlapped: communicate each bucket as it fills

   compute  ████████████████████                        (backward)
   network      ███  ███  ███  ██                       (all_reduce per bucket)
            └───────── total ──────┘                    both busy at once

In the end, overlapping backward() and all-reduce is better.

Overlapping backward() and all-reduce turns out to be the most efficient approach. all_reduce is network communication while backward(), step() and so on are GPU computation, so they can be processed at the same time. Overlapping them — i.e. making computation and communication overlap as much as possible — greatly increases computational efficiency.

From the analysis, comparing backward() and step(), backward() was by far the heavier operation.

Naturally, the heavier the operation you overlap with, the shorter the total training time. The analysis showed that performing all-reduce alongside backward() was much faster than waiting for backward() to finish.

Note — why backward() and not step() is the thing to hide behind

This is the payoff of the "backward > step" remark from §1. You can only overlap communication with computation that is (a) long enough to hide it and (b) incremental, so partial results become available early. backward() satisfies both: it takes roughly twice as long as forward, and it produces gradients layer by layer. step() satisfies neither — it's short, and it can't start until all gradients exist anyway.

There's a subtlety worth naming: on NCCL, "overlap" doesn't mean threads. Collectives are enqueued on a separate CUDA stream, and the copy engines / NIC operate independently of the SMs running your backward kernels. The overlap is at the hardware level, which is why it's nearly free when it works.

Questions that might come up here…

  • Q1: During the backward() computation, the gradients haven't all been computed yet — how can you run all-reduce?
  • A1: Because backward() proceeds sequentially starting from the later layers, you can send the layers whose computation has finished first.
  • Q2: Then how often do you run all-reduce? Does it happen per layer?
  • A2: No. It performs gradient bucketing. When a bucket is full, it runs all-reduce.
Note — why per-layer all-reduce would be a disaster

BERT-base has ~200 parameter tensors. Firing 200 separate all-reduces means paying the fixed latency cost 200 times, on messages far too small to reach peak bandwidth. Every collective has a startup cost (kernel launch, NCCL handshake, network round trip) of order tens of microseconds; a 4 KB bias vector's all-reduce is essentially 100% overhead.

   200 tiny all-reduces:  ▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌▌  mostly latency, near-zero bandwidth
   8 bucketed all-reduces: ████ ████ ████ ████   latency amortized, full bandwidth

Gradient Bucketing

Gradient bucketing is a scheme that stores gradients in buckets of a fixed size and sends them to the other processes when a bucket fills up. During the backward() computation, the gradients computed starting from the back are stored in a bucket in order, and when the bucket's capacity is full it performs all-reduce to deliver the sum of the gradients to each device. This may be confusing because of the figure, but what gets stored in the bucket is not the model's parameters but the gradients output at that layer. Every bucket has a fixed size, and you can set the capacity in megabytes via the bucket_cap_mb argument.

   backward proceeds right → left (output layer first)

   layers:   [ 1 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ][ 7 ][ 8 ]
                                              ◀────── backward starts here

   grads arrive:                          g8 g7 g6 g5 g4 g3 g2 g1
                                          └─bucket 0─┘└─bucket 1─┘ …
                                                │            │
                                          all_reduce   all_reduce
                                          fires as soon as a bucket is full,
                                          while earlier layers still compute
the argument is `bucket_cap_mb`, not `bucket_size_mb`
python
model = DistributedDataParallel(model, device_ids=[local_rank], bucket_cap_mb=25)

The default is 25 MB. Tuning guidance:

  • Slow interconnect (Ethernet, no NVLink): larger buckets (50–100 MB) amortize latency better.
  • Fast interconnect: smaller buckets start communicating earlier, improving overlap.
  • It rarely moves the needle more than a few percent. Profile before spending time here.
Note — the one ordering assumption bucketing makes, and how it breaks

DDP builds its buckets in reverse parameter-registration order, on the assumption that this approximates the order gradients will actually become ready. That assumption holds for ordinary feed-forward models. It breaks when:

  • some parameters get no gradient on some steps (conditional branches, unused heads) — DDP waits forever for a bucket that will never fill. This is what find_unused_parameters=True fixes, at the cost of traversing the autograd graph every iteration to detect it.
  • the model has genuinely dynamic control flow, where the ready-order changes step to step.

Prefer restructuring the model over enabling find_unused_parameters. If you must enable it, know that you're paying for it on every single iteration.

4. The production version

The script in §3 is correct but minimal. A real job needs logging, checkpointing, gradient clipping, and usually gradient accumulation. Here is the same training loop with those added — and the reasoning for each addition in the table below it.

python
"""
ddp_production.py  —  torchrun --standalone --nproc_per_node=4 ddp_production.py
"""

import os

import torch
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.optim import AdamW
from torch.utils.data import DataLoader, DistributedSampler
from datasets import load_dataset
from transformers import AutoModelForSequenceClassification, AutoTokenizer

EPOCHS = 3

def setup():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)          # BEFORE init_process_group
    dist.init_process_group(
        backend="nccl",
        device_id=torch.device(f"cuda:{local_rank}"),   # eager init, clearer errors
    )
    return local_rank, dist.get_rank(), dist.get_world_size()

def main():
    local_rank, rank, world_size = setup()
    is_main = rank == 0

    # ---- data: index by NAME, not by column position
    ds = load_dataset("nyu-mll/multi_nli")["train"]

    tok = AutoTokenizer.from_pretrained("bert-base-cased")     # fast tokenizer

    def collate(batch):
        enc = tok(
            [b["premise"] for b in batch],
            [b["hypothesis"] for b in batch],
            padding=True, truncation=True, max_length=128, return_tensors="pt",
        )
        enc["labels"] = torch.tensor([b["label"] for b in batch])
        return enc

    sampler = DistributedSampler(
        ds, num_replicas=world_size, rank=rank, shuffle=True, drop_last=True
    )
    loader = DataLoader(
        ds, batch_size=32, sampler=sampler, collate_fn=collate,
        num_workers=4, pin_memory=True, persistent_workers=True, drop_last=True,
    )

    # ---- model
    model = AutoModelForSequenceClassification.from_pretrained(
        "bert-base-cased", num_labels=3
    ).to(local_rank)
    model = DDP(model, device_ids=[local_rank], bucket_cap_mb=25)

    optimizer = AdamW(model.parameters(), lr=3e-5, fused=True)
    # No GradScaler: bf16 has fp32's exponent range, so gradients do not
    # underflow and loss scaling is unnecessary. Use one only for fp16.

    try:
        for epoch in range(EPOCHS):
            sampler.set_epoch(epoch)           # <-- reshuffles each epoch. NOT optional.
            model.train()

            for step, batch in enumerate(loader):
                batch = {k: v.to(local_rank, non_blocking=True) for k, v in batch.items()}

                optimizer.zero_grad(set_to_none=True)
                with torch.autocast("cuda", dtype=torch.bfloat16):
                    loss = model(**batch).loss

                loss.backward()                # all_reduce happens in here, overlapped
                torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
                optimizer.step()

                if step % 50 == 0:
                    # loss is this rank's LOCAL loss; reduce it before logging
                    reported = loss.detach().clone()
                    dist.all_reduce(reported, op=dist.ReduceOp.AVG)
                    if is_main:
                        print(f"epoch {epoch} step {step} loss {reported.item():.4f}")

            if is_main:
                # save the UNWRAPPED module, from one rank only
                torch.save(model.module.state_dict(), f"ckpt_{epoch}.pt")
            dist.barrier()                     # others wait for the write to finish
    finally:
        dist.destroy_process_group()

if __name__ == "__main__":
    main()
Note — what each addition buys you
Change Why
LOCAL_RANK for set_device The only value that is a valid device index on every node
set_device before init_process_group Otherwise ranks can bind to device 0 and hang or OOM
device_id= in init_process_group Eager NCCL init — failures surface here, not at a confusing later collective
sampler.set_epoch(epoch) Without it the shuffle never changes across epochs
drop_last=True on both sampler and loader Guarantees every rank runs the same number of steps. Uneven step counts hang the job — some ranks call an all-reduce nobody else joins
collate_fn instead of tokenizing in the loop Tokenization moves into the worker processes, off the training thread
AutoTokenizer Rust-backed fast tokenizer; often a large fraction of step time in this script
torch.autocast with bf16 Mixed-precision compute — typically 2–3× throughput on modern GPUs. bf16 needs no GradScaler; add one only for fp16
zero_grad(set_to_none=True) Frees the gradient buffers rather than filling them with zeros
clip_grad_norm_ before step() Bounds the update. Under fp16 it must come after scaler.unscale_(), so clipping sees true gradients
all_reduce(..., AVG) before logging loss on rank 0 is rank 0's shard only, not the global loss
model.module.state_dict() Saving the DDP wrapper prefixes every key with module. and breaks single-GPU loading
barrier() after saving Stops other ranks racing ahead into a partially written file
try/finally + destroy_process_group() A crashing rank shouldn't leave the rest hanging
Note — the no_sync() idiom, for gradient accumulation

If you accumulate over k micro-steps, DDP would otherwise all-reduce on every one of them — k× the necessary communication. Suppress it on all but the last:

python
import contextlib

for i, batch in enumerate(loader):
    is_last = (i + 1) % accum == 0
    ctx = contextlib.nullcontext() if is_last else model.no_sync()
    with ctx:
        loss = model(**batch).loss / accum
        loss.backward()          # gradients accumulate locally; no all_reduce
    if is_last:
        optimizer.step()
        optimizer.zero_grad(set_to_none=True)

Note the / accum: without it you're effectively multiplying the learning rate by k.

5. The correctness checklist

Data-parallel bugs are mostly silent. The job runs, the loss goes down, and the result is quietly worse than the single-GPU baseline. These are the ones that actually happen:

Symptom Likely cause Fix
Loss curve differs from 1-GPU run Global batch changed but LR didn't Linear scaling rule + warmup
Every epoch learns the same thing sampler.set_epoch() missing Call it at the top of each epoch
Job hangs at a random step Ranks ran different numbers of steps drop_last=True; make control flow rank-independent
Job hangs, no error, ~10 min later a NCCL timeout A rank-conditional collective Every rank must call every collective, same order
Checkpoint won't load on 1 GPU Saved the DDP wrapper model.module.state_dict()
Corrupted checkpoint No barrier after rank-0 save dist.barrier() after saving
Logged loss looks noisy/wrong Reporting one rank's local loss all_reduce with ReduceOp.AVG first
Slower than 1 GPU DP not DDP; or TP-style comm over Ethernet; or tiny model Check you're using DDP; profile
Validation metrics inconsistent across ranks Uneven eval shards Gather counts and totals, or evaluate on rank 0
find_unused_parameters error on step 1 Some params get no grad Restructure model, or enable the flag knowingly
The cardinal rule, restated from chapter 03

Every rank must call every collective, in the same order, with matching shapes and dtypes.

Under DDP this is mostly handled for you — until you add your own all_reduce for metrics, or an early break, or a rank-conditional validation pass. Then it's yours to get right.

Note — the reproducibility question people always ask

DDP is not bitwise reproducible run-to-run by default, and that's expected. Floating-point addition isn't associative, and NCCL may choose different reduction orders depending on message size and topology. Two "identical" runs will diverge after a few thousand steps. If you need determinism, you need torch.use_deterministic_algorithms(True), fixed seeds per rank, and a fixed NCCL algorithm — and you will pay for it in speed. For ordinary training the drift is harmless.

Note — seeding, which is subtler than it looks

You want:

  • Identical model initialization across ranks — DDP handles this by broadcasting parameters from rank 0 at construction, so you don't have to.
  • Different data order per rank — DistributedSampler handles this.
  • Different dropout masks per rank — arguably desirable; set torch.manual_seed(base_seed + rank) if you care.

The common mistake is seeding everything identically and then wondering why dropout is correlated across replicas.

6. Performance tuning

Roughly in order of how much they usually matter:

Lever Typical gain Notes
Mixed precision (bf16) 2–3× Biggest single win. bf16 needs no GradScaler on modern GPUs
Fix the dataloader often 1.5×+ num_workers, pin_memory, persistent_workers, tokenize in collate_fn

Note — DDP communication hooks

You can replace the default all-reduce with a custom one:

python
from torch.distributed.algorithms.ddp_comm_hooks import default_hooks as hooks

# communicate gradients in bf16 instead of fp32 — halves gradient traffic
model.register_comm_hook(state=None, hook=hooks.bf16_compress_hook)

There's also powerSGD_hook for aggressive low-rank gradient compression, which can cut communication by an order of magnitude at some cost in convergence. Only worth reaching for when you have measured that you're communication-bound — on a single NVLink node you almost never are.

Note — two newer things worth knowing about the layer underneath all of this

Differentiable collectives (PyTorch 2.11). Chapter 07 will show you Megatron hand-writing torch.autograd.Functions so that a forward all_reduce has an identity backward and vice versa. PyTorch now ships that natively — collectives that participate in autograd directly, no wrapper class required. If you are writing custom parallel layers, check these before rolling your own adjoint pairs.

torchcomms (landed 2.13). A new communications backend layer. c10d — init_process_group, all_reduce, ProcessGroup — remains the surface you write against and isn't going anywhere soon. What torchcomms replaces is the layer beneath: instead of a single generic ProcessGroup, you get a communicator object that owns setup, split, finalize, window/RMA operations, and backend-specific hints. The motivations are the ones this chapter's failure modes hint at — fault tolerance at 100k+ GPU scale, heterogeneous hardware, one-sided communication, and eager (rather than lazy) communicator setup. It ships with NCCL, RCCL, Gloo, and NCCLX backends and integrates with DeviceMesh, so FSDP2 works over it.

Nothing in this chapter needs changing for it. It's worth knowing because it explains the 2.13 renames: all_gather_into_tensor → all_gather_single and reduce_scatter_tensor → reduce_scatter_single, aligning c10d's names with torchcomms'.

Note — how to know whether you're communication-bound at all

Don't guess:

bash
NCCL_DEBUG=INFO torchrun --standalone --nproc_per_node=4 ddp_modern.py

prints the topology NCCL detected and the algorithm it chose. For the real answer, use torch.profiler and look at whether the NCCL kernels overlap the backward kernels or sit in their own gap. A gap means the overlap isn't working — usually because of an unused parameters stall, a synchronizing .item() call inside the loop, or buckets that are too large to start early.

The most common self-inflicted wound: calling loss.item() or print(loss) every step. That forces a device synchronization, which stalls the CPU, which prevents it from running ahead to enqueue the next iteration's kernels, which destroys the overlap the whole design is built around.

7. Beyond DDP — when to switch to FSDP

DDP's assumption is the one chapter 04 flagged: the full model state must fit on one device. At the textbook ~16 bytes per parameter for mixed-precision Adam — see chapter 04 §2 for why that figure ranges from about 5 to 20 depending on optimizer and state precision, which shifts the crossover below but not its existence:

Model State Fits 80 GB? Use
BERT-base (110M) ~1.8 GB ✓ easily DDP
1.5B ~24 GB ✓ DDP
7B ~112 GB ✗ FSDP
70B ~1.1 TB ✗✗ FSDP (+ TP/PP)

The switch is small, because FSDP is still data parallelism — same batch splitting, same programming model:

python
from torch.distributed.fsdp import fully_shard

for layer in model.bert.encoder.layer:
    fully_shard(layer)
fully_shard(model)
# then train exactly as before

What changes underneath: instead of every rank holding all 16 bytes/param and doing one gradient all_reduce, each rank holds 1/N of the state and does an all_gather of each layer's parameters just before using it, plus a reduce_scatter of gradients. Chapter 08 covers the reasoning in full.

Note — DDP is not obsolete

For models that fit, DDP is still the right answer: it communicates less than FSDP (one gradient reduction vs. per-layer parameter gathers), it's simpler, and it's better tested. Reach for FSDP when memory forces you to, not by default.
