MHA, MQA, GQA from the bytes up

These three architectures differ in exactly one integer. Everything else — the quality gap, the throughput win, the reason 8 is the number everybody picked — falls out of what that integer does to the byte count during decode.

The notation clash to pre-empt

G and nkv are reciprocals, and both get called “groups” in conversation. Config files expose nkv (num_key_value_heads), so “GQA-8” always means nkv = 8, which for H = 32 is G = 4. Savings scale as G, not nkv. Say which one you mean out loud before you write the first line.

~300FLOPs per byte — H100 ridge point, 990 TFLOP/s over 3.35 TB/s

The one hardware fact. An H100 does ~990 TFLOP/s dense BF16 against 3.35 TB/s of HBM. Divide: a kernel doing fewer than ~300 FLOPs per byte it touches is memory-bound, and its runtime is set entirely by byte count. Everything below is byte counting; the roofline check at the end is what licenses that.

01One integer, three names

MHA, MQA and GQA are the same architecture at three settings of nkv. Nothing else differs.

NamenkvGQuery heads
MHAH1H
GQAbetweenH/nkvH
MQA1HH

The sharing operation. Each KV head is broadcast to the G query heads in its group — a repeat_interleave along the head axis in naive implementations, or a stride-0 read in a fused kernel. Query heads are never shared. The output projection stays d × d, because after broadcast you still concatenate H·dh values.

What stays invariant

  • Query heads: H in all three. GQA does not reduce the number of attention patterns computed.
  • Score and AV FLOPs: identical. Every query head still attends over the full context.
  • Attention output dimensionality: identical, hence WO unchanged.

What does shrink: the K and V projection matrices, and therefore their GEMM FLOPs and their gradients. That is a side effect, not the point.

What the sharing costs

A KV head is a retrieval system: K is the index (what makes a token findable), V is the payload (what gets copied forward), Q is the query. Sharing collapses the first two and leaves the third alone.

  • K: a shared basis, not a shared pattern. Each query head keeps its own WQ, so heads in a group can still attend to completely different tokens. What is lost is that they must all search the same key space — one WK is a compromise projection serving G different notions of what to index by.
  • V: the larger loss. Even two heads attending to the identical token with identical weights now receive the same vector. MHA would read different features from it. Per layer you go from H independent read channels to nkv; only the fixed WO mixing differs afterwards.

Degradation ordering, predictable from that: precise retrieval and verbatim copying first (rare tokens, proper nouns, numbers, code identifiers — induction behaviour needs an exact index and a faithful payload), then multiple simultaneous retrievals (multi-hop, multi-needle), then long inputs generally. Barely affected: short-form fluency — and perplexity, which is dominated by easy high-frequency tokens while the loss lives in the tail. A model can look near-identical on validation loss and be measurably worse at retrieval.

Which term in the KV formula each technique attacks

5 axesindependent and multiplicative — GQA owns exactly one of them

KV bytes per token = 2 · nl · nkv · dh · b. Each published technique reduces a different factor, which is precisely why they compose:

GQA-8 (4×) with fp8 (2×) with a sliding window is 8×+ compounding. Knowing which row a technique occupies tells you instantly whether it stacks with another.

Scope discipline

k as written includes nl: it is whole-model bytes per token. When analysing a single attention op (section 05) drop nl. Mixing the two scopes mid-derivation gives an answer off by 32× and it will look plausible.

04The crossover

One number decides whether GQA is worth anything for a given workload. It is a property of the workload, not the architecture.

Per decode step the GPU reads weights once (shared across the batch) and each sequence's KV cache separately:

bytes/step = W + B·L·k

05Prefill vs decode intensity

The asymmetry that makes this whole subject exist. Prefill's intensity carries L; decode's carries only B and G.

Prefill — one sequence, L tokens at once

Weight GEMMs. Each of P weights does one multiply-accumulate (2 FLOPs) per token, for L tokens. The weights are read once:

I_W = 2PL / bP = 2PL / 2P = L

Attention, per layer, flash-style so the score matrix never reaches HBM, causal masking halving the work:

FLOPs = 2L²d (QKᵀ) + 2L²d (AV) = 4L²d  → causal: 2L²d
bytes = b(Ld [Q] + 2Ld/G [K,V] + Ld [O]) ≤ 8Ld
I_A   = 2L²d / 8Ld = L/4

At L = 4096: I_W = 4096, I_A = 1024. Both an order of magnitude above the 300 ridge — prefill is compute-bound, and the reuse of each weight across L tokens is literally the intensity.

Decode — B sequences, 1 new token each

Weight GEMMs. Same weights, but now only B tokens amortise the read:

I_W = 2PB / bP = B

Attention, per layer per sequence: one query row against L cached keys.

FLOPs = 2Ld (QKᵀ) + 2Ld (AV) = 4Ld    → total 4Ld·n_l·B
bytes = B L k = B L · 4n_l d / G
I_A   = 4Ld n_l B / (4 B L n_l d / G) = G
IA = Gdecode attention intensity — independent of both B and L

Everything cancels but G. Not B, not L. The reason is structural: every sequence owns a private KV cache, so batching buys no reuse whatsoever in attention. You read B separate caches to do B separate GEMVs. Decode attention is permanently batch-1-shaped, and G is the only lever on it.

Aggregate

With x = BLk, and using 2PB = B·W and 4Ldn_lB = G·x:

I = (B·W + G·x) / (W + x)

A byte-weighted average of B and G, which reads off directly: raising L drags I toward G (long context makes you more memory-bound), raising B pulls it toward B but simultaneously inflates x, which fights back.

The consequence worth stating

Even MQA reaches only IA = 32 against a ridge of 300. GQA never makes decode compute-bound — it makes it less memory-bound. Anywhere GQA matters you are memory-bound by construction, because the thing that makes it matter (KV dominating traffic) is the same thing that pins I near G.

Compute only binds at large B and small L together: B=512, L=128 gives I ≈ 310. Short prompts at huge batch — reranking, classification, embedding — which is exactly the regime where GQA is worth ~1.1×. The regimes are complementary.

Why it saturates. The weight read is an irreducible serial cost that GQA barely touches (17% floor, section 02). The ceiling as k → 0 is:

S_max = (W + B L k₁) / W

= 6.0× here. MQA is 8× more aggressive than GQA-8 and delivers only 2.1× more speed. Diminishing returns are real at fixed batch — and this is the number single-user latency benchmarks report, which is why they make GQA look unimpressive.

07At capacity: throughput is linear

Same equations, opposite behaviour. This is the result to lead with, because it is the one the serving economics actually turn on.

Refill the memory GQA frees, instead of holding batch fixed:

B_max = (M - W) / (L k)

The trick that makes this clean. At B_max, by construction:

bytes/step = W + B_max·L·k = M

You read the entire HBM once per decode step — so step time is identical for every G:

T_step = M / BW = 80 GB / 3.35 TB/s = 23.9 ms
Θ ∝ Gthroughput is linear in group size — no saturation
Θ = B_max / T_step = (M - W)·BW / (M · L · k)

Since k ∝ 1/G and W is nearly constant, Θ ∝ G exactly — in fact slightly super-linear (34.3× at 32×) because W shrinks a little too, freeing extra room for cache.

Roofline check. At G=32, B=515: I = (515×10.8 + 32×69.1)/79.9 ≈ 97. Under 300, so the bytes-over-bandwidth model still holds. It stops holding near B ≈ 300 at short context, where the FFN GEMMs go compute-bound and none of this arithmetic applies.

The contrast to have ready

Fixed batch → saturates (6× ceiling). W is a fixed serial cost you cannot amortise further.

At capacity → linear in G (4.3×, 34×). You move exactly M bytes per step either way; G only decides how many tokens you harvest from that fixed traffic. Weight bytes per generated token fall from 12.9/15 = 0.86 GB to 12.9/64 = 0.20 GB — GQA converts a fixed overhead into a shared one.

Run the capacity calculation before the latency one. If you can refill freed memory with work, you are in the linear regime. If you are pinned by a latency SLA at fixed batch, you are in the saturating one.

Caveats to volunteer unprompted: this assumes every sequence sits at full 8k simultaneously, which continuous batching and PagedAttention avoid — real occupancy is lower, so effective batch is higher. Activation and workspace memory take ~10% off both columns.

08Tensor parallelism erodes it

Every number above assumed one GPU. Sharding is in direct tension with sharing — both want the same heads — and TP caps the saving before you have even chosen nkv.

How TP shards attention. By head. Each GPU computes H/T query heads end-to-end, then one all-reduce over the output projection. GPU i must therefore hold, in its own HBM, whichever KV heads its query heads attend to — a GPU cannot attend to a tensor living on another device.

The sharding rule

KV heads per GPU  =  max(n_kv / T, 1)
replication factor R  =  max(T / n_kv, 1)

When nkv < T there are not enough KV heads to go round, so the surviving ones are replicated — every GPU keeps its own copy.

per GPU, per token  =  4 n_l d_h · max(n_kv/T, 1)
aggregate over T    =  4 n_l d_h · max(n_kv, T)

T cancels in the aggregate when nkv ≥ T, and floors at T below that. The floor is the whole result. Handy unit: one KV head costs 4 × 32 × 128 = 16 KiB per token.

4×, not 32×MQA's real saving at TP=8 — identical to GQA-8

Nominal is 32/nkv, what the single-GPU formula promises and what papers report. Actual is max(32,T)/max(nkv,T), what the machine delivers. The gap between them is exactly R — a pure systems artifact that appears nowhere in the architecture.

Read the per-GPU column: 16 KiB/token for nkv = 8, 4 and 1 alike. Same capacity, same bytes per decode step, same latency, same batch ceiling. At TP=8, GQA-8 and MQA are the same model from the systems side — and GQA-8 has better quality. Nobody would ship MQA on an 8-way node.

The design rule

nkv > T → no waste, but savings left on the table. nkv = T → the knee: smallest cache with zero replication. nkv < T → strictly dominated — identical memory, strictly worse quality.

And the ceiling: each GPU goes from H/T KV heads under MHA to exactly 1 at the knee, so the most GQA can ever deliver is H/T. 4× at TP=8, 2× at TP=16, and 1× — nothing at all — at TP=32. TP divides your saving before you get to use it.

Llama-3 ships nkv = 8 at every size because TP=8 is one NVLink node. The architecture has a deployment topology baked into it.

Why replicate rather than route?

  • Route the KV to the GPU that needs it — fatal. You would move the cache over NVLink (~450 GB/s) instead of reading it from local HBM (3.35 TB/s), every layer, every step. Shipping precisely the bytes the technique exists to avoid, over the slowest available path. Sharding KV along dh is the same mistake wearing a different hat: it forces an all-gather of the full cache each layer.
  • Route the queries instead — viable. At decode Q is one token, ~1 KB per GPU per layer. But it strands bandwidth (with nkv=4 only half the GPUs do attention work), and it breaks TP's symmetry, adding a scatter and gather per layer — 64 extra latency-bound collectives per step at 32 layers.
  • Replication is bounded and cheap. Replicating an MQA cache 8× just returns you to GQA-8-equivalent, still 4× better than MHA, for a far simpler system.

Getting past TP=8

  1. Data-parallel attention. Decouple attention's parallelism from the FFN's: each GPU owns different sequences and holds their full KV locally, so R=1 at any TP. Costs an all-to-all at the attention boundary. This is the modern answer — DeepSeek's MLA deployments do exactly this.
  2. Change the axis. nkv is exhausted, so attack a different row of the table in section 01 — dh via MLA (a ~512-dim latent, which shards cleanly), or nl via cross-layer sharing.
  3. Do not scale TP. Spend extra devices on pipeline or expert parallelism and pin TP at 8. Past 8 you leave NVLink for InfiniBand (~50 GB/s) on a latency-critical all-reduce twice per layer, and H/T heads per GPU gets too small for efficient GEMMs.

09Speculative decoding interaction

Orthogonal in the algebra, competing in practice. Both techniques spend the same finite resource — the headroom between current intensity and the ridge.

Verification runs s draft tokens through one forward pass, of which αs are accepted. The query becomes s rows rather than 1, so decode attention is a skinny GEMM rather than a GEMV. Extra Q/O bytes are O(sd) against O(Ld/G) of KV — negligible at long context.

I_W = 2PBs / 2P     = B·s        (weights still read ONCE per step)
I_A = 4sLD n_l B / (BLk) = s·G
IA = sGs=5, G=4 → 20, still 15× under the ridge
B=32, s=5, L=4096, G=4FLOPsBytesI
Weight GEMMs1.80 TF11.3 GB160
Attention0.34 TF17.2 GB20
Total2.15 TF28.5 GB75

Attention would need s = 75 to reach the ridge. In this regime it never goes compute-bound.

Why they are orthogonal on paper

Bytes per step do not depend on s. The same weights and the same cache are read whether you verify 1 token or 5 — verification is one forward pass. Only the numerator changes:

bytes per generated token = (W + BLk) / (B · αs)

GQA shrinks k; speculation divides by αs. The ratio W : KV is untouched by s, so GQA's speedup factor is identical with or without speculation. They multiply: S ≈ SGQA × αs.

Where they actually collide

Both techniques do the same thing — raise arithmetic intensity toward the ridge — and there is only 300 of headroom to spend. IW = Bs: at B=32, s=5 that is 160, comfortably memory-bound. At B=64, s=5 it is 320 > 300 and the verify pass has gone compute-bound — those s−1 extra tokens now cost real FLOP time instead of riding free on a memory-bound step.

And running B=64 instead of B=15 is precisely what GQA is for. So GQA erodes speculative decoding, not the reverse. Speculation is a low-batch latency technique: it converts idle tensor cores into tokens and only pays while they are idle. Serving stacks shorten or disable it under high load, and it shines in single-user local inference — exactly the regime where GQA is worth 1.2×.

The residual asymmetry. IW = Bs scales with both knobs; IA = sG does not scale with B at all. As batch grows the weight GEMMs approach the roofline while attention stays pinned near sG, so attention's share of runtime rises monotonically with batch and context. GQA gets more valuable exactly where speculation gets less.

10Provenance and limits

The parts that are recall, not derivation. These are the ones an interviewer treats as free.

Where GQA models come from

5%of original pre-training compute to uptrain MHA → GQA

Ainslie et al., 2023: Training Generalized Multi-Query Transformer Models from Multi-Query Checkpoints. The contribution is uptraining, not the architecture:

  1. Take an already-trained MHA checkpoint.
  2. Mean-pool the K and V projection matrices within each group to initialise the shared head. Beats both “select one head” and random init.
  3. Continue pre-training for α ≈ 5% of the original compute.

Result: MQA degrades noticeably; GQA-8 lands close to MHA quality at close to MQA speed. Mean-pooling works because the grouped heads are already correlated — the pooled head is a reasonable centroid, and 5% of compute is enough for the query heads to re-specialise around it.

Why 8, specifically

Half the reason is quality. The other half is tensor parallelism: with TP=8 on an 8-GPU node, nkv = 8 gives each GPU exactly one KV head — no replication, no cross-device KV traffic. Below nkv = TP you must replicate the cache across devices and the saving stops. 8 is a systems constant as much as a quality one.

Where it stops paying

  • Weights dominate — small B·L, below crossover (section 04)
  • nkv hits the TP degree — below that you replicate rather than shard
  • nkv = 1 — the axis is exhausted; switch to a different row of the table in section 01
  • Compute-bound regimes — prefill, and very high batch at short context

11Is GQA the right shape?

Everything above answers “given GQA, what does it do?” This section answers the harder question: is it the right point in the design space, and how would you find out?

MLA — the actual competitor

DeepSeek's MLA projects K and V into a shared low-rank latent (~512 dims) and caches only that, decompressing per head at compute time. It reports a smaller cache than GQA-8 and better quality than MHA.

rank, not countthe reason harder compression costs less quality

Why compressing harder costs less. GQA constrains count: G query heads receive literally one index and one payload, so independent read channels fall from H to nkv. MLA constrains rank: each head keeps its own up-projections WUK(i), WUV(i), so at compute time there are still H distinct keys and values — heads specialise within a shared subspace rather than stopping. A rank constraint is far softer than a head-count constraint, and low-rank KV is a good inductive bias: these matrices are empirically near-low-rank already, so the bottleneck removes mostly noise. Beating MHA is not paradoxical — the up/down projections add parameters, so it is not iso-param, and the bottleneck regularises.

Why MLA's extra decode FLOPs are free. Decode sits at I ≈ 4–30 against a ridge of 300 — tensor cores idle 90–99% of the time. Trading bytes for FLOPs is the correct direction of trade in a memory-bound regime, and the intensity gap is the number that says so. MLA spends idle FLOPs to buy bytes, moving you toward the ridge. (WUK also absorbs into WQ at inference, so per-head K is never materialised.)

So why did Llama-3 ship GQA?

Timing — DeepSeek-V2 landed mid-2024, Llama-3 in April. No conversion path — GQA uptrains from an MHA checkpoint for 5%; MLA must be pretrained from scratch. Kernel cost — MLA needs custom kernels and a decoupled-RoPE scheme, since RoPE does not commute with the low-rank absorption; GQA is a config integer every serving stack already supported. Risk — GQA was proven at 70B.

The honest lesson: GQA won on deployability, not on being the best point in the design space. It is a local optimum reached because it was cheap to adopt.

The ablation nobody runs

GQA is always benchmarked iso-parameter or iso-compute. Hold inference throughput fixed instead and spend the KV savings on capacity.

Design. Fix a target Θ* at a stated operating point (B, L, TP). For each G, grow depth or dff until Θ(G, model) = Θ*. Train each arm on the same token budget. Evaluate on retrieval and long-context, not perplexity.

Confounds that invalidate the naive version:

  1. Training compute is not equal across arms. Bigger arms cost more to train — report both iso-token and iso-train-FLOP, and say which you mean.
  2. The answer is a function of (B, L). Below crossover the throughput edge is 1.06× and buys almost nothing. A single operating point proves nothing; sweep it.
  3. Perplexity hides the effect (section 01). Without multi-needle, multi-hop and verbatim-copy evals the ablation reports “no difference”.
  4. Uptraining asymmetry. GQA arms cost 5% to obtain; MHA arms cannot be converted at all. Cost-per-quality differs from FLOP-per-quality.

What it almost certainly shows. Θ ∝ G is linear; quality is roughly logarithmic in parameters. Trading a 4× linear throughput gain against a 17% parameter gain worth a fraction of a loss-point means GQA wins decisively in the KV-dominated regime — the standard benchmark understates it. Below crossover the edge collapses and MHA's quality wins. The workload decides, again.

A deployment where it is a mistake

On-device code completion. 7B model, single user, batch 1, 2–4k context, hard TTFT SLA under 200 ms, 16 GB unified memory.

  • TTFT is prefill — compute-bound, GQA contributes nothing.
  • B·L ≈ 4k, far below the 24.6k crossover — decode is weight-bound, GQA gives ~1.1×.
  • The behaviour that degrades first is verbatim identifier copying and precise retrieval — which is what code completion is.

You pay the quality cost precisely where you collect no speed.

13Cold self-test

No notes. Answer aloud, with a number, before opening each one.

Derive k(G) from scratch, state its scope, and give MHA's value in MB/token.

Per token per layer, K and V each hold nkv·dh = d/G elements → 2bd/G bytes → k = 2b n_l d/G = 4n_l d/G, whole model. G=1: 4×32×4096 = 524 KB = 0.524 MB.

Why is decode attention intensity independent of batch size, when weight-GEMM intensity equals batch size?

Weights are shared across the batch, so B tokens amortise one read → I = B. KV caches are private per sequence, so batching adds proportional FLOPs and proportional bytes — nothing amortises, and both B and L cancel to leave I = G. Decode attention is permanently batch-1-shaped.

Solve for the crossover B·L and evaluate at G=1 and G=4. What does the scaling in G mean?

BLk = W with k = 4n_l d/G and W = 2n_l d²(10+2/G) → BL = d(5G+1). G=1: 24,576. G=4: 86,016. Crossover ∝ G: each cut to the cache pushes the KV-dominated regime 4× further out, so the next cut is worth proportionally less at fixed workload.

Same model, same GPU: give a workload where GQA-8 buys 1.2× and one where it buys 4×. Why the difference?

B=1, L=2k → 1.21× (weight-bound, well below crossover). At capacity, L=8k → 4.27× throughput. The difference is not the architecture but whether you hold batch fixed (Amdahl on the weight read, saturating) or refill freed memory (you always move M bytes per step, so throughput ∝ G).

Does GQA improve time-to-first-token? Justify from the intensity numbers.

No. TTFT is prefill, which has I_W = L and I_A = L/4 — both far above the 300 ridge, so it is compute-bound and there is no cache to read yet. GQA improves TPOT, the inter-token latency. Saying “decode is memory-bound so TTFT drops” attaches the right mechanism to the wrong stage.

Why nkv = 8 rather than 4 or 16? Give both halves.

Quality: GQA-8 sits near MHA after 5% uptraining while MQA degrades. Systems: at TP=8 it gives exactly one KV head per GPU, so no replication and no cross-device KV traffic. Below nkv = TP you must replicate and the saving stops accruing.

How were GQA models actually obtained, and with what initialisation?

Uptrained from existing MHA checkpoints (Ainslie et al. 2023) — mean-pool K and V projections within each group, then continue pre-training for ~5% of original compute. Mean-pooling beat both selecting a single head and random init.

What capacity does MHA have that MQA lacks? Name the K loss and the V loss separately.

K: heads keep their own WQ so patterns can still differ — what is lost is that all G heads must index into one shared key space. V: even on identical attention weights, all G heads now receive the same vector, so independent read channels drop from H to nkv. Retrieval and verbatim copying degrade first; perplexity barely moves, which is why it is the wrong metric here.

At TP=8, how much does MQA actually save over MHA — and why isn't it 32×?

4×. One KV head cannot be split across 8 GPUs, so it is replicated: 8 copies in HBM for 1 head of data. Aggregate floors at max(nkv, T), so nkv = 8, 4 and 1 all land at 16 KiB/token per GPU — same capacity, same latency, same batch ceiling. Below the knee you lose quality for nothing.

Give the maximum saving GQA can deliver at TP=8, TP=16 and TP=32.

H/T: 4×, 2×, 1×. Each GPU holds H/T KV heads under MHA and exactly 1 at the knee. At TP=32 with H=32, MHA already gives one head per GPU — GQA has nothing left to remove. Sharding and sharing compete for the same heads.

Why replicate the KV cache below the knee rather than routing to whichever GPU owns it?

Routing the KV moves the cache over NVLink (~450 GB/s) instead of local HBM (3.35 TB/s) — shipping exactly the bytes the technique exists to avoid, over a 7× slower path. Routing the queries is viable (Q is ~1 KB/GPU/layer at decode) but strands bandwidth on idle GPUs and adds a scatter/gather per layer. Replication is bounded: it only puts you back at knee-equivalent.

Does GQA compound with speculative decoding, or compete with it?

Algebraically orthogonal: bytes per step are independent of s, so the W : KV ratio is unchanged and the speedups multiply. In practice they compete for headroom below the ridge — IW = Bs, so at B=64, s=5 the verify pass goes compute-bound and the extra draft tokens stop being free. GQA raises batch, so GQA erodes speculation. Meanwhile IA = sG has no B in it, so attention's share of runtime only grows.

MLA caches less than GQA-8 and scores better than MHA. How, mechanistically — and why are its extra decode FLOPs free?

GQA constrains head count; MLA constrains rank. Each head keeps its own up-projection, so H distinct keys and values still exist at compute time — heads specialise within a shared subspace instead of stopping. The FLOPs are free because decode runs at I ≈ 4–30 against a ridge of 300: trading bytes for FLOPs is the correct direction in a memory-bound regime. Llama-3 shipped GQA anyway — no uptraining path from MHA, custom kernels, decoupled RoPE, and timing.

Give a deployment where MHA → nkv=8 is a mistake.

On-device code completion: batch 1, 2–4k context, TTFT SLA. Prefill is compute-bound so TTFT is unchanged; B·L is far below crossover so decode gains ~1.1×; and verbatim identifier copying is exactly the behaviour that degrades first. If the savings are spent on a larger model it is strictly worse — 14.97 GB/step against 13.97 GB, 7% slower.

Name the five terms in the KV formula and what attacks each. Which does GQA touch?

2 · n_l · nkv · dh · b. GQA touches nkv only. dh → MLA; n_l → cross-layer sharing; sequence length → windowing/eviction; b → quantization. They are multiplicative and compose.

14Traps I fell into

Recorded from a live run at this material. These are personal, not generic.

  • Notation collision. Using one symbol for both group size and KV-head count, then dividing by the wrong one. Fix G and nkv explicitly at the top of the page and never write “groups” unqualified.
  • Elements vs bytes, inverted. Counting traffic in elements, then multiplying intensity by 2 to “convert”. Bytes are in the denominator — converting elements to bytes divides intensity. Convert once, at the end, deliberately.
  • Stopping at the shape. Answering “GQA stops helping when the FFN dominates” instead of setting W = BLk and solving. The condition was right but attached to architecture, when the swing factor is the workload B·L — the same model varies from 1.06× to 4×. When you can name the two competing terms, you are two lines from the crossover. Go and get it.
  • TTFT vs TPOT. Correctly saying prefill is compute-bound, then claiming GQA improves time-to-first-token. Right mechanism, wrong stage. Name the stage before naming the effect.
  • FFN arithmetic. Writing 6d² per layer instead of 12d². Check against a known model size: 12 × 4096² × 32 = 6.4B.
  • Conclusion without mechanism. Knowing “MQA hurts, GQA-8 is the sweet spot” but not uptraining, mean-pooled init, or the 5%. The pattern to break: carrying the field's conclusions without the field's numbers.
  • Assuming compute catches up. Suspecting that large B and L would eventually make decode compute-bound. It does not — IA = G has neither variable in it. Long context makes you more memory-bound.
  • Treating GQA as settled. It won on deployability — uptrainable, one config integer, existing kernels — not on being the best point in the design space. MLA compresses harder for less quality cost by constraining rank rather than head count.
  • Writing weight bytes as 2PB. Weights are read once per step regardless of batch — that is the entire reason batching works. It cancels out of an intensity ratio, so the final answer can survive while the reasoning does not.
  • Judging the quality cost by perplexity. The loss is concentrated in tail behaviour — retrieval, rare tokens, long context. Val loss can look unchanged while multi-needle accuracy has moved.
  • Quoting single-GPU savings for a sharded deployment. MQA's 32× is nominal; at TP=8 it is 4×, the same as GQA-8. Always ask what T is before quoting a KV saving — the ceiling is H/T, fixed before nkv is even chosen.
  • Reaching for dh-sharding to get past TP=8. It looks like the natural next axis, but it forces an all-gather of the whole cache every layer — an HBM read converted into a network read. The real answers are data-parallel attention, a different KV term (MLA, cross-layer), or simply not scaling TP.
  • Scope drift. Mixing per-layer and whole-model quantities inside one derivation. Off by nl = 32×, and it looks plausible.
